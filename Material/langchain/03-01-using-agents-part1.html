2. Introduction to Agents and the ReAct Pattern

2.1 What Is an Agent?

An agent is a system that uses a language model to decide which tools to use and how to use them in order to accomplish a goal. Agents follow the ReAct (Reasoning + Acting) pattern: they think, act with tools, observe, and repeat until they can give a final answer.

We will start with a simple agent that can calculate expressions and tell the current time.

2.2 ReAct Pattern: How Agents Work

ReAct = Reasoning + Acting. Agents follow this loop:

  1. Reason: Think about what to do next.
  2. Act: Use a tool or provide an answer.
  3. Observe: Look at the tool result.
  4. Repeat: Continue until the task is complete.

For example, if the user asks: "What's 15 × 23 and the weather in Paris?", the agent:

  • Reasons: it needs a calculation and weather data.
  • Acts: calls a calculator tool → gets 345.
  • Acts: calls a weather tool → gets something like sunny, 22°C.
  • Responds with a combined, natural-language answer.
Your Task

Create a basic agent that can perform calculations and tell the current time. Copy the code below into a new notebook cell and run it. 

from langchain.agents import create_agent
from langchain.tools import tool
from langchain_openai import ChatOpenAI

# Initialize the model
model = ChatOpenAI(model="gpt-4o-mini", temperature=0)

# Define simple tools
@tool
def calculator(expression: str) -> str:
    """Perform basic mathematical calculations."""
    try:
        result = eval(expression)
        return f"Result: {result}"
    except Exception as e:
        return f"Error: {str(e)}"

@tool
def get_time() -> str:
    """Get the current time."""
    from datetime import datetime
    return f"Current time: {datetime.now().strftime('%Y-%m-%d %H:%M:%S')}"

# Create the agent with tools
basic_agent = create_agent(
    model=model,
    tools=[calculator, get_time],
    system_prompt="You are a helpful assistant that can perform calculations and tell time."
)

print("Basic agent created successfully!")

3. Defining and Using Tools

3.1 What Are Tools?

Tools are functions that agents can call to interact with the outside world: APIs, databases, files, web search, and more. LLMs alone cannot access real-time data or perform reliable calculations – tools bridge that gap.

Good tools have:

  • Clear, descriptive docstrings (so the model knows when to use them).
  • Typed arguments (often with Pydantic models) for validation.
  • Safe error handling.

4.3 Same toolkit, three specialists (system prompt drives behavior)

Imagine an e‑commerce fraud team. Every analyst connects to the same SQLite database and uses the same SQL tools from Section 4.2. What makes each analyst different is their job brief—the system_prompt you pass to create_agent(...).

You will build three specialists who look at the same suspicious shopper from different angles:

  • Agent A (Frequency) — “Is this person returning items too often?”
  • Agent B (Value) — “Is this return expensive, and does this person already have a history of large refunds?”
  • Agent C (Reason) — “Is the excuse they typed suspicious or copied from past returns?”

The Python tool list never changes. Only the system prompt changes—and that is enough to steer SQL queries and the final answer.

The demo story (read this first)

Section 4.1 seeded two shoppers in fraud_demo.sqlite3:

  • good_user@example.com — a normal customer with a few legitimate returns (e.g. “arrived damaged”).
  • fraudster@example.com — a repeat returner with many recent returns, large refunds, and vague reasons like “changed my mind”.

All three agents below investigate the same flagged shopper: fraudster@example.com. They are filing yet another return for order ORD_BAD_2 (a webcam, ~$1,099) with the reason “changed my mind”. Your agents should generally score this account as higher risk than good_user@example.com would receive.

Shared safeguards (every agent)
  • Read-only SQLite — no INSERT, UPDATE, or DELETE.
  • Safe workflow: list tables → inspect schema → run bounded queries (use LIMIT).
  • Each agent ends its reply with one line of JSON so you can later parse it with json.loads (strip any prose or markdown fences first if the model adds them).
System prompt structure (use this pattern for every agent)

Each specialist below uses the same four-part system prompt layout:

  • ROLE: who the agent is (job title / specialist type)
  • GOAL: the one outcome it must deliver
  • BACKSTORY: context, database scope, what to focus on and what to ignore
  • OUTPUT FORMAT: how to structure the reply (plain-language summary + trailing JSON line)

SQL safety rules are shared in shared_sql_instructions and prepended to every agent. Only the role block changes between Agents A, B, and C.

4.3.1 Agent A — return frequency

Business question: “How many returns has this shopper made recently?”

A customer who returns items every few days may be abusing the policy—even if each individual return looks fine. Agent A counts non-rejected returns in the last 30 days for the given email. It ignores dollar amounts and return-reason text.

The agent assigns a risk_score from 0 (safe) to 100 (very suspicious) using a fixed rubric based only on how many returns it finds. The table below is also embedded in the system prompt so the model applies the same rules every time:

Returns in last 30 days Risk band Meaning
0 0–10 No recent returns — low risk
1–2 10–25 Normal occasional returns
3–5 25–50 Worth monitoring
6–9 50–75 Elevated — possible policy abuse
10 or more 75–100 High — likely repeat abuser

For fraudster@example.com you should land in the 75–100 band because the seeded data contains many recent returns. Pick one integer inside the band (higher counts → higher end of the band).

What you type to the agent (return ticket format — same structure as Agents B and C):

Return ticket — frequency risk check
Shopper email: fraudster@example.com

How many non-rejected returns has this shopper made in the last 30 days?
Give a brief explanation and a frequency risk score.

frequency_role = """
ROLE:
Return-frequency risk analyst on an e-commerce fraud team.

GOAL:
When given a shopper email, count their non-rejected returns in the last 30 days
and assign a frequency risk_score (0–100) using the rubric below.

BACKSTORY:
You investigate whether a customer is returning items too often — a common sign
of policy abuse. You query a read-only SQLite database with tables: users, orders,
order_items, returns. You focus ONLY on return counts and timing. Ignore refund
dollar amounts and return-reason text; other specialists on the team handle those.

WORKFLOW:
1. Query the returns table — count rows where:
   - user_email matches the shopper
   - return_date is within the last 30 days
   - status is NOT 'REJECTED'
2. Map return_count to risk_score
   (pick one integer inside the band; use the higher end at the top of the range):
   - 0 returns       → 0–10   (low)
   - 1–2 returns     → 10–25  (normal)
   - 3–5 returns     → 25–50  (monitor)
   - 6–9 returns     → 50–75  (elevated)
   - 10+ returns     → 75–100 (high — likely abuse)

OUTPUT FORMAT:
1. Write 2–4 sentences in plain language summarizing what you found.
2. End with ONE line of strict JSON only (no markdown fences). Example shape:
   {"check_type": "frequency", "risk_score": 0, "reason": "short explanation",
    "details": {"return_count": 0, "period_days": 30}}

JSON field rules:
- risk_score: integer 0–100 from the rubric (use the real count, not a placeholder)

4.3.2 Agent B — value & refund history patterns

Business question: “Is this return expensive, and has this shopper already received large refunds before?”

Agent B looks at money, not how often someone returns. It computes two numbers from SQL:

  • Current return value — from order_items (unit_price × quantity for the SKUs being returned).
  • High-refund history — count of past returns where refund_amount > 500 and status is not REJECTED.

The final risk_score combines a base score from the current return value plus a history bump from past large refunds (capped at 100). The rubric below is embedded in the system prompt:

Step 1 — base score from current return value

Return value (approx.) Base score
Under $200 10–25
$200 – $499 25–45
$500 – $999 45–65
$1,000 or more 65–80

Step 2 — add history bump for past high refunds

Past returns with refund > $500 Add to base score
0 +0
1–2 +5 to +15
3–5 +15 to +25
6 or more +25 to +35

Final score: risk_score = min(100, base_score + history_bump). For our demo ticket (~$1,099 webcam + many past high refunds), expect a score in the 85–100 range.

5. Short-Term Memory and Checkpointers

So far our agents have been stateless: each call starts fresh. In real applications you almost always want the agent to remember previous messages in a conversation thread. In LangChain 1.0 agents, this is handled by a checkpointer, which stores and reloads the agent state between calls for each conversation thread.

Short-term vs long-term memory
  • Short-term memory: thread-level state (conversation history, tool results, interrupts) stored via a checkpointer.
  • Long-term memory: user or application data stored in a separate vector store or database.

In this lab we focus on short-term memory using LangChain agents, based on the official LangChain short-term memory docs.

5.1 InMemorySaver – simple short-term memory

The simplest way to add short-term memory is to pass checkpointer=InMemorySaver() when you create your agent. This keeps state in RAM for as long as your Python process is running, which is perfect for local notebooks, demos, and experiments.

LangChain’s create_agent manages short-term memory as part of the agent state. When you specify a thread_id in the configurable section, all calls with the same thread_id share the same conversation history.

Your Task

Turn one of your existing agents into a stateful agent that remembers your name across turns using InMemorySaver. Copy the code below into a new cell and run it. 

from langgraph.checkpoint.memory import InMemorySaver
from langchain.agents import create_agent

# Reuse the ChatOpenAI model and tools (calculator, get_time) defined earlier
memory_agent = create_agent(
    model=model,
    tools=[calculator, get_time],
    checkpointer=InMemorySaver(),  # Enable short-term memory
)

config = {"configurable": {"thread_id": "memory-demo-1"}}

print("=== First turn (introduce yourself) ===")
result = memory_agent.invoke(
    {"messages": [{"role": "user", "content": "Hi! My name is Bob."}]},
    config,
)
print(result["messages"][-1].content)

print("\n=== Second turn (same thread) ===")
result = memory_agent.invoke(
    {"messages": [{"role": "user", "content": "What's my name?"}]},
    config,
)
print(result["messages"][-1].content)

What to notice

- Both calls use the same thread_id ("memory-demo-1"), so they share short-term memory.
- The agent can answer "Your name is Bob" in the second turn because the checkpointer replayed the first user message.

5.2 SqliteSaver – lightweight local persistence

InMemorySaver is great for quick experiments, but its state disappears when the process restarts. For local notebooks and demos where you still want state to persist between sessions, you can use a file-based checkpointer such as SqliteSaver from langgraph.checkpoint.sqlite. This stores the thread state in a SQLite file so it survives restarts while staying easy to set up.

Your Task

Install the SQLite checkpointer and try it out. Only the checkpointer changes – the agent API and thread_id usage stay the same. 

# Install dependency (run in your terminal, not in the notebook):
pip install langgraph-checkpoint-sqlite

import sqlite3
from langgraph.checkpoint.sqlite import SqliteSaver
from langchain.agents import create_agent

# Create or reuse a local SQLite file for checkpoints
conn = sqlite3.connect("checkpoints.sqlite", check_same_thread=False)
checkpointer = SqliteSaver(conn=conn)
checkpointer.setup()  # Creates tables if they don't exist

persistent_memory_agent = create_agent(
    model=model,
    tools=[calculator, get_time],
    checkpointer=checkpointer,  # Use SQLite-backed short-term memory
)

config = {"configurable": {"thread_id": "user-123"}}
result = persistent_memory_agent.invoke(
    {"messages": [{"role": "user", "content": "Hi! I'm Alice."}]},
    config,
)
print(result["messages"][-1].content)

5.3 PostgresSaver – production-ready persistent memory

For production you should move to a database-backed checkpointer such as PostgresSaver from langgraph.checkpoint.postgres. This stores short-term memory in Postgres so it survives restarts and scales.

Your Task

Review the example below and note that only the checkpointer changes – the agent API and thread_id usage stay the same.
