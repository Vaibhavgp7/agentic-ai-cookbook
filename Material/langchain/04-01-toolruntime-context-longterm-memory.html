Part A — ToolRuntime context

1. What is ToolRuntime?

ToolRuntime is a LangChain feature that gives your tools rich access to runtime information such as context, state, memory, and streaming helpers. Instead of manually wiring all of this into every tool, you can inject a single object: runtime: ToolRuntime[YourContextType].

Key capabilities you will explore in this lab:

  • Context access: user‑specific data such as IDs, roles, session information.
  • State management: full conversation state (messages, tool calls, etc.).
  • Memory store: persistent key–value store shared across sessions.
  • Commands: a way to modify agent state and control flow.
  • Stream writer: send incremental progress updates during long‑running tools.

In the following sections, you will build realistic tools that use these capabilities in a customer support scenario with context‑aware tools. Later in this same guide, you will use the same ToolRuntime pattern to read and write long-term memory via runtime.store.

3. Understanding ToolRuntime

Before writing tools, let’s clarify what ToolRuntime actually gives you. Think of it as a single object that carries everything your tool needs to know about the current run.

3.1 Key ToolRuntime Capabilities

  • Context access: immutable, typed context such as user_id, role, or workspace_id.
  • State management: access to the full conversation state (messages, tool calls, etc.).
  • Memory store: a shared, persistent store for long‑term memory across conversations.
  • Stream writer: send partial outputs back to the user during long operations.
  • Config access: read runtime configuration/settings that influence tool behavior.

The example below shows how to use these capabilities in practice with context‑aware tools.

4. Context‑Aware Tools with ToolRuntime

ToolRuntime gives your tools a unified way to access user context, state, and a shared store. Instead of manually passing user IDs or configuration into every tool, you can define a context TypedDict and receive it via runtime.context.

You will now build a customer‑support style agent that uses runtime.context to personalize responses based on the current user.

# Real-world Example: Customer Support System with Context
# This demonstrates how ToolRuntime provides context to tools

USER_DATABASE = {
    "user123": {
        "name": "Alice Johnson", 
        "account_type": "Premium",
        "balance": 5000,
        "email": "alice@example.com",
        "support_tier": "Priority"
    },
    "user456": {
        "name": "Bob Smith",
        "account_type": "Standard", 
        "balance": 1200,
        "email": "bob@example.com",
        "support_tier": "Standard"
    }
}

class UserContext(TypedDict):
    user_id: str
    session_id: str

@tool
def get_account_info(runtime: ToolRuntime[UserContext]) -> str:
    """Get the current user's account information."""
    user_id = runtime.context["user_id"]
    
    if user_id in USER_DATABASE:
        user = USER_DATABASE[user_id]
        return f"""Account Information:
        Name: {user['name']}
        Type: {user['account_type']}  
        Balance: ${user['balance']}
        Email: {user['email']}
        Support Tier: {user['support_tier']}"""
    return "User not found in system"

@tool
def update_support_tier(new_tier: str, runtime: ToolRuntime[UserContext]) -> str:
    """Update user's support tier (Priority, Standard, Basic)."""
    user_id = runtime.context["user_id"]
    
    if user_id in USER_DATABASE:
        USER_DATABASE[user_id]['support_tier'] = new_tier
        return f"Support tier updated to {new_tier} for user {USER_DATABASE[user_id]['name']}"
    return "User not found"

# Create agent with context
agent = create_agent(
    model,
    tools=[get_account_info, update_support_tier],
    context_schema=UserContext,
    system_prompt="You are a customer support assistant. Help users with their account inquiries."
)

# Test with real agent - Context is automatically injected into tools
print("=== Testing Context Access ===")
result = agent.invoke(
    {"messages": [{"role": "user", "content": "What's my current account information?"}]},
    context=UserContext(user_id="user123", session_id="session_001")
)

Part B — Long-term memory (Store, namespaces & ToolRuntime)

5. Why long-term memory matters

Agents need two different kinds of “memory”:

  • Short-term (conversation) memory is usually the running list of messages in the current chat, optionally trimmed or summarized. In LangGraph, this is often tied to a thread via a checkpointer (for example InMemorySaver).
  • Long-term memory is data that should survive across turns, sessions, or even different threads, such as user preferences, approved policies, or facts the user asked you to remember.

This part of the guide focuses on long-term memory using the LangGraph store exposed to tools as runtime.store on ToolRuntime. You will persist facts per user, read them back from a different conversation thread (same user), and confirm another user cannot see them.

6. Checkpointer vs store (mental model)

Mechanism Typical role Keyed by
checkpointer (e.g. InMemorySaver) Saves and resumes graph state per conversation (messages, etc.). Often thread_id in config["configurable"].
store (e.g. InMemoryStore) Application long-term key–value data; partition by user/tenant in the namespace. Namespace tuple + string key.

In the lab below, you will use both: the checkpointer keeps each thread's messages separate, while the store holds long-term facts under ("app", "memory", user_id) — shared across threads for the same user, isolated between users.

7. Understanding namespaces in the store

The store is not a single flat dictionary. It is organized by namespace and key.

7.1 What is a namespace?

A namespace is like a path or folder structure that groups related values. It is a tuple of strings (and optionally other stable identifiers you choose). It helps you:

  • Organize data by domain (app area, feature, user, workspace).
  • Isolate tenants or users in multi-user apps.
  • Avoid key collisions: the same key string can exist in different namespaces safely.
  • Align with access control: you can document which namespaces a tool may read or write.
# Namespace structure (tuple of segments)
namespace = ("category", "subcategory", "user_id")

# Examples:
("preferences", "user_prefs")
("notes", "personal")
("tasks", "user123", "workspace_alpha")
("app", "memory", "user123")   # per-user LTM bucket (used in this lab)

7.2 Basic store operations

Tools receive the same store instance that you pass into create_agent(..., store=...). Typical operations: 

# Write (value must be serializable — lists, dicts, strings, etc.)
store.put(namespace, key, value)

# Read — returns an Item (or None), not always the raw value
item = store.get(namespace, key)
if item is None:
    data = None
else:
    data = item.value

Always read item.value after get when you need the stored Python object. The lab notebook uses a minimal pattern; the code in section 9 below uses .value explicitly so behavior is clear across LangGraph versions.

7.3 Namespace design — per-user from the start (best practice)

A common beginner mistake is storing everything under one global namespace such as ("app", "memory"). That works in a solo notebook demo, but in any app with more than one user, everyone would share the same long-term memory — user A could read user B's facts.

Best practice: always include a user id (or tenant id) in the namespace from your first implementation. Each user gets an isolated bucket; the store is still shared infrastructure, but data is partitioned by namespace.

  • ("app", "memory", user_id) — long-term snippets for one user (key "messages" in this lab).
  • user_id comes from runtime context on ToolRuntime, not from the LLM — the agent cannot spoof another user's id if you inject context server-side.

In this lab you will use a small UserContext TypedDict and pass context=UserContext(user_id="...") on every agent.invoke(...) call — the same pattern you used earlier in Part A for customer-support tools. Because a TypedDict is a dict at runtime, read fields with runtime.context["user_id"]. 

class UserContext(TypedDict):
    user_id: str


def memory_namespace(user_id: str) -> tuple[str, ...]:
    """One LTM bucket per user — use this in every save/retrieve tool."""
    return ("app", "memory", user_id)

9. Tools: save and retrieve long-term memory (per user)

These tools append text blobs to a list under key "messages", scoped to memory_namespace(runtime.context["user_id"]). The LLM never chooses the namespace — your code derives it from injected context.

Your Task

Add a new cell with the two tools below. Notice runtime.store and explicit use of item.value when reading. 

LTM_KEY = "messages"


@tool
def save_ltm(data: str, runtime: ToolRuntime[UserContext]) -> str:
    """Save a line of information to this user's long-term memory."""
    store = runtime.store
    ns = memory_namespace(runtime.context["user_id"])

    item = store.get(ns, LTM_KEY)
    if item is None:
        messages: List[str] = []
    else:
        messages = list(item.value) if isinstance(item.value, list) else [str(item.value)]

    messages.append(data)
    store.put(ns, LTM_KEY, messages)
    print(f"Saving to LTM for {runtime.context['user_id']}:", data)
    return "Data saved to long-term memory."


@tool
def retrieve_ltm(data: str, runtime: ToolRuntime[UserContext]) -> str:
    """Retrieve this user's long-term memory (data arg can hint what to look for)."""
    store = runtime.store
    ns = memory_namespace(runtime.context["user_id"])

    print(f"Retrieving from LTM for {runtime.context['user_id']}")
    item = store.get(ns, LTM_KEY)
    if item is None:
        return "No data in long-term memory."
    return str(item.value)

10. Create the agent with store, checkpointer, and context

Pass store=InMemoryStore() so tools can read and write LTM. Pass checkpointer=InMemorySaver() so each thread_id has its own saved conversation state. Pass context_schema=UserContext so every invoke can supply user_id and tools receive it via runtime.context.

Your Task

Add a new cell to define the agent. The system prompt tells the model when to save and to retrieve before answering. 

agent = create_agent(
    tools=[save_ltm, retrieve_ltm],
    model=model,
    store=InMemoryStore(),
    checkpointer=InMemorySaver(),
    context_schema=UserContext,
    system_prompt="""You are a helpful assistant that can answer any queries.
If the user shares personal information, preferences, or explicit approvals,
save that information using the save_ltm tool.
Before answering a query when prior facts might matter, retrieve long-term
memory using retrieve_ltm and use that context in your answer.
""",
)

11. Lab: cross-thread recall and user isolation

You will run three scenarios. Always pass context=UserContext(user_id=...) on agent.invoke — in a real app this id comes from auth (logged-in user), not from chat text.

  1. User Siva, thread 1 — say “My name is Siva”; agent calls save_ltm.
  2. User Siva, thread 2 — ask “What is my name?”; agent calls retrieve_ltm and answers Siva (cross-thread, same user).
  3. User Alex, thread 3 — ask “What is my name?”; Alex has no LTM yet — must not see Siva's name.

Different thread_id values simulate separate conversations. Different user_id values simulate separate users. LTM is shared across threads for the same user, but isolated between users.

What you should observe

  • Console prints such as Saving to LTM for siva: and Retrieving from LTM for siva.
  • Siva's second thread recalls the name; Alex's thread does not.
  • Final assistant messages reflect stored facts only for the matching user_id.
Why context, not a global namespace?

thread_id scopes conversation history (checkpointer). user_id in the namespace scopes long-term facts (store). Using both from the start mirrors production: many chats per user, many users per app, no memory leaks.

12. Summary

  • ToolRuntime injects runtime information into tools — especially typed runtime.context (user ids, session data) so tools can personalize behavior without hard-coding identities into prompts.
  • Long-term memory in this pattern is application data in runtime.store, organized by namespaces and keys.
  • Namespaces should include user_id (or tenant id) from day one — not added later as an afterthought.
  • ToolRuntime context injects user_id into tools; derive memory_namespace(runtime.context["user_id"]) inside save/retrieve — never trust the model to pick a namespace.
  • Checkpointers scope conversation state by thread_id; the store scopes LTM by namespace — cross-thread recall works for the same user, not across users.
