1. RAG Overview

RAG (Retrieval Augmented Generation) combines two ideas: you first retrieveaugmentgenerate

1.1 What is RAG?

Conceptually, RAG has two big phases:

  • Indexing: Prepare your knowledge base once (load documents, split into chunks, embed, store in a vector DB).
  • Retrieval & Generation: At query time, find relevant chunks and use them as context for the LLM.

In this lab, you will build a RAG system over an employee handbook PDF and explore each step in the pipeline in a practical way.

4. Step 2 – Text Splitting

Large documents rarely fit into a single LLM context window. To make retrieval effective, we split documents into smaller, overlapping chunks.

For your information – text chunking strategies

The following overview explains the main text chunking approaches used in production RAG systems.

In this lab we will implement only size-based chunking using LangChain’s RecursiveCharacterTextSplitter. The other strategies below are for context and comparison—you do not need to run them now.

4.1 Why chunk? The chunking paradox

Chunk size is a trade-off. Chunks that are too small lose surrounding context, so retrieval may return fragments that are hard to interpret. Chunks that are too large dilute relevance—a single chunk may contain several unrelated topics, making similarity search less precise.

Goal: chunks large enough to be meaningful, small enough to match a specific query.

4.2 Text chunking strategies (overview)

Production RAG pipelines typically choose among four strategies. Each balances simplicity, speed, and retrieval quality differently.

4.2.1 Size-based (fixed) chunking

The simplest approach: split text every N characters or tokens. It is fast and predictable, but ignores sentence, paragraph, and word boundaries—so a chunk can end in the middle of a word.

Without overlap

With zero overlap, each character belongs to exactly one chunk. Consider a 325-character source document split into three chunks of roughly 108 characters each. Notice how words are broken across chunk boundaries—signific / ant, Engineeri / ng—which can hurt retrieval quality.

Size-based chunking without overlap

Please contact the central Human Resources offices, and the Engineeri|ng team if a request needs a review before the quarter closes. Keep the full written approvals on file today.

With overlap

A common fix is to add a fixed overlap so content at chunk boundaries appears in two adjacent chunks. That way, if a query matches text that would have been split, at least one chunk still contains the full phrase. 

# Informational example only – fixed-size chunking WITH overlap
def fixed_size_chunk(text: str, chunk_size: int = 500, overlap: int = 50) -> list[str]:
    chunks = []
    start = 0
    while start < len(text):
        end = start + chunk_size
        chunks.append(text[start:end])
        start = end - overlap  # step back so boundaries overlap
    return chunks

sample = "Employee vacation policy allows 15 days per year. Sick leave is separate..."
print(fixed_size_chunk(sample, chunk_size=40, overlap=10))

4.2.2 Recursive character splitting

A refinement of size-based chunking: try to split on natural boundaries first (paragraphs, then lines, then words), and only fall back to raw characters when a section still exceeds chunk_size. LangChain’s RecursiveCharacterTextSplitter implements this pattern—it is still fundamentally size-based, but respects document flow better than a blind character cut. 

# Informational example only – separator hierarchy (concept behind RecursiveCharacterTextSplitter)
SEPARATORS = ["\n\n", "\n", ". ", " ", ""]

def recursive_split(text: str, chunk_size: int, separators: list[str]) -> list[str]:
    if not separators or len(text) <= chunk_size:
        return [text] if text else []
    sep = separators[0]
    parts = text.split(sep) if sep else list(text)
    chunks, current = [], ""
    for part in parts:
        candidate = (current + sep + part) if current else part
        if len(candidate) <= chunk_size:
            current = candidate
        else:
            if current:
                chunks.append(current)
            if len(part) > chunk_size:
                chunks.extend(recursive_split(part, chunk_size, separators[1:]))
                current = ""
            else:
                current = part
    if current:
        chunks.append(current)
    return chunks

4.2.3 Document structure-aware chunking

When documents have clear structure—Markdown headings, HTML sections, PDF titles—split at those boundaries instead of arbitrary character counts. Each chunk stays within one logical section, and metadata (section title, heading level) improves filtering and citations at retrieval time.

Structure-aware chunking preserves semantic units defined by the document itself.

# Informational example only – LangChain Markdown header splitter
from langchain_text_splitters import MarkdownHeaderTextSplitter

headers_to_split_on = [
    ("#", "Header 1"),
    ("##", "Header 2"),
    ("###", "Header 3"),
]
markdown_splitter = MarkdownHeaderTextSplitter(headers_to_split_on=headers_to_split_on)
# md_docs = markdown_splitter.split_text(markdown_document)

4.2.4 Semantic chunking

Instead of fixed sizes or headings, semantic chunking detects topic shifts. Each sentence is embedded; when cosine similarity between adjacent groups drops below a threshold, a new chunk begins. Chunks vary in length but tend to contain one coherent idea—useful for narrative or mixed-topic prose where structure is weak.

4.3 Strategy comparison

Strategy                  | Speed   | Respects structure | Best for
--------------------------|---------|--------------------|----------------------------------
Size-based (fixed)        | Fast    | No                 | Baselines, uniform text
Recursive character       | Fast    | Partially          | General-purpose docs (our lab)
Document structure        | Medium  | Yes                | Markdown, HTML, structured PDFs
Semantic                  | Slower  | By meaning         | Narrative / mixed-topic prose

4.4 What we implement in this lab

For the employee handbook PDF, we use size-based chunking via RecursiveCharacterTextSplitter. It enforces a maximum chunk size and overlap while preferring paragraph and sentence boundaries— a practical default before moving to structure-aware or semantic approaches.

Text Splitters do this job. RecursiveCharacterTextSplitter is recommended because it:

  1. Splits on paragraphs (\n\n)
  2. Then lines (\n)
  3. Then spaces ( )
  4. Finally, raw characters

Key parameters:

  • chunk_size: Max characters per chunk (for example, 1000).
  • chunk_overlap: Overlap between chunks to preserve context (for example, 200).
  • add_start_index: Track where in the original document the chunk came from.

5. Step 3 – Embeddings

Embeddings turn text into numerical vectors that capture meaning. Similar texts have vectors that are close to each other in high‑dimensional space. 

Text: "vacation policy"          → [0.23, -0.45, 0.67, ...]
Text: "time off guidelines"      → [0.25, -0.43, 0.65, ...]  (similar meaning)
Text: "employee benefits"        → [0.12, -0.89, 0.34, ...]  (different topic)

Why embeddings matter:

  • Semantic search: Find content by meaning, not just exact keywords.
  • Similarity matching: Compare texts using cosine similarity or related metrics.
  • Better retrieval: They power the “retrieve” step in RAG.

Here we use OpenAI’s text-embedding-3-small model via OpenAIEmbeddings. You’ll also see a simple cosine similarity function to compare embeddings.

Your Task

Create a new cell, paste the code below, and run it to generate embeddings for a few sample texts and compare their similarities. Observe how related sentences have higher similarity scores. 

from langchain_openai import OpenAIEmbeddings

# Initialize OpenAI embeddings
embeddings = OpenAIEmbeddings(
    model="text-embedding-3-small"
)

# Let's create embeddings for sample texts to understand how they work
sample_texts = [
    "Employee vacation policy and time off",
    "Annual leave and holiday guidelines",
    "Company dress code requirements"
]

# Generate embeddings
sample_embeddings = [embeddings.embed_query(text) for text in sample_texts]

print(f"Each embedding has {len(sample_embeddings[0])} dimensions")
print(f"\nFirst 10 values of embedding 1: {sample_embeddings[0][:10]}")

# Calculate similarity between embeddings (using dot product as approximation)
import numpy as np

def cosine_similarity(vec1, vec2):
    return np.dot(vec1, vec2) / (np.linalg.norm(vec1) * np.linalg.norm(vec2))

sim_1_2 = cosine_similarity(sample_embeddings[0], sample_embeddings[1])
sim_1_3 = cosine_similarity(sample_embeddings[0], sample_embeddings[2])

print(f"\nSimilarity between text 1 and 2 (both about time off): {sim_1_2:.4f}")
print(f"Similarity between text 1 and 3 (different topics): {sim_1_3:.4f}")
print("\n✅ Higher similarity = more related content!")

6. Step 4 – Vector Store with Chroma

A Vector Store (or vector database) stores embeddings and lets you run fast similarity search over thousands or millions of chunks.

Conceptually:

1. Store phase:
   Document → Embedding → Vector DB

2. Query phase:
   Question → Embedding → Find similar vectors → Return documents

In this lab, we use Chroma, an easy‑to‑use local vector store that persists data to disk and supports fast similarity search.

Your Task

Create a new cell, paste the code below, and run it to create a Chroma vector store from your document chunks and persist it to a local directory. 

from langchain_community.vectorstores import Chroma

# Create Chroma vector store and add documents
# This will:
# 1. Generate embeddings for all chunks
# 2. Store them in Chroma
# 3. Enable similarity search

vector_store = Chroma.from_documents(
    documents=all_splits,
    embedding=embeddings,
    persist_directory="./chroma_db"  # Save to disk for reuse
)

print(f"✅ Created vector store with {len(all_splits)} document chunks")
print(f"📁 Data persisted to: ./chroma_db")

7. Step 5 – Similarity Search

Similarity Search (also called semantic search) finds the most relevant chunks for a user query by comparing embeddings.

The typical flow is:

  1. Embed the user question.
  2. Compare with stored embeddings using a distance metric (often cosine similarity).
  3. Return the top‑k most similar chunks.

8. Step 6 – Retrievers

A Retriever is a higher‑level abstraction that returns documents for a query. It wraps vector stores (and other backends) behind a consistent interface and integrates nicely with LCEL chains and agents.

Common retrieval strategies include:

  • Similarity: Standard “top‑k by similarity” search.
  • MMR (Maximum Marginal Relevance): Balances relevance with diversity between returned chunks.
  • Score threshold: Only return documents above a certain similarity score.

8.1 Basic Retriever

9. Step 7 – RAG with Agents

A RAG Agent uses tools (like your retriever) and decides when and how to call them. This gives you more flexible, conversational behavior than a simple one‑shot chain.

High‑level behavior:

  1. The user asks a question.
  2. The agent decides whether to search the handbook.
  3. If needed, it calls the retrieval tool (possibly multiple times).
  4. It combines the retrieved context with its reasoning to produce a final answer.

This usually means more LLM calls (tool decisions + answering) and slightly higher latency, but better behavior for complex, multi‑step queries.

9.1 Build a Retrieval Tool and Agent

Your Task

Create a new cell, paste the code below, and run it to define a retrieval tool over your employee handbook and create a LangChain 1.0 agent that can use this tool. 

from langchain_openai import ChatOpenAI
from langchain.agents import create_agent  # LangChain 1.0 way
from langchain.tools import tool

# Initialize the LLM
llm = ChatOpenAI(model="gpt-4o-mini", temperature=0)

# Create a retrieval tool using the @tool decorator
@tool
def retrieve_employee_handbook(query: str):
    """
    Searches the employee handbook for information.
    Use this tool when you need to find specific information about:
    - Company policies
    - Employee benefits
    - Working hours and time off
    - Code of conduct
    - Any other employee-related information
    
    Args:
        query: The question or topic to search for
    
    Returns:
        Relevant information from the employee handbook
    """
    # Retrieve relevant documents
    retrieved_docs = vector_store.similarity_search(query, k=3)
    
    # Format and return the content for the LLM
    return "\n\n".join([
        f"Source (Page {doc.metadata.get('page', 'N/A')}):\n{doc.page_content}"
        for doc in retrieved_docs
    ])

# Create tools list
tools = [retrieve_employee_handbook]

# Create the agent using LangChain 1.0's create_agent
# This is simpler than the old create_tool_calling_agent + AgentExecutor approach
system_prompt = """You are a helpful HR assistant with access to the company employee handbook.

Use the retrieve_employee_handbook tool to search for information when answering questions about:
- Company policies and procedures
- Employee benefits and perks  
- Working hours, holidays, and time off
- Code of conduct and guidelines
- Any other employment-related topics

When you receive information from the tool, provide a clear and helpful answer based on that context.
If you can answer without the tool (like greetings), feel free to do so.
If the information isn't found, say so honestly."""

agent = create_agent(llm, tools, system_prompt=system_prompt)

print("✅ RAG Agent created successfully using LangChain 1.0!")

10. Step 8 – RAG with dynamic prompt middleware

A fixed retrieval‑first pipeline is a simpler pattern: it always retrieves context and then calls the LLM once with that context.

Compared to agents, this pattern is typically:

  • Faster – usually one LLM call per query.
  • More predictable – always retrieves, no tool‑use decisions.
  • Cheaper – fewer model calls overall.

It is also less flexible: it cannot skip retrieval when retrieval is unnecessary, and it cannot do multi‑step searches on its own.

10.1 Build a Retrieval Pipeline with Middleware

Here you use LangChain 1.0’s middleware to inject retrieved context into the system prompt right before the LLM is called.

Your Task

Create a new cell, paste the code below, and run it to define a dynamic prompt that fetches context from the vector store and to create a rag_pipeline. 

from langchain.agents.middleware import dynamic_prompt, ModelRequest

# Create a dynamic prompt that injects retrieved context
@dynamic_prompt
def prompt_with_context(request: ModelRequest) -> str:
    """Inject context from vector store into the system message."""
    # Get the last user message
    last_query = request.state["messages"][-1].content
    
    # Retrieve relevant documents
    retrieved_docs = vector_store.similarity_search(last_query, k=3)
    
    # Format the context
    docs_content = "\n\n---\n\n".join([
        f"Page {doc.metadata.get('page', 'N/A')}:\n{doc.page_content}"
        for doc in retrieved_docs
    ])
    
    # Create system message with context
    system_message = (
        "You are a helpful HR assistant. Use the following context from the employee handbook to answer the question.\n\n"
        "If the answer is not in the context, say \"I don't have that information in the employee handbook.\"\n"
        "Be specific and cite relevant policies when possible.\n\n"
        f"Context:\n{docs_content}"
    )
    
    return system_message

# Create the RAG pipeline using create_agent with middleware
rag_pipeline = create_agent(llm, tools=[], middleware=[prompt_with_context])

print("✅ RAG pipeline created successfully!")
print("\nHow it works:")
print("1. User asks a question")
print("2. Middleware retrieves relevant context from vector store")
print("3. Context is injected into system prompt")
print("4. LLM generates answer with context (single call)")
