06 · Review Artifacts: Shopping Cart

The useful skill is reading the plan and sending a bad sentence back, before it becomes code. Each scenario still needs a test.

Lesson 06 of 10 ~80 minutes Review discipline
CatalogSearchCart CheckoutOrdersInventory
What you will do
  • Propose a shopping cart (Amazon’s cart, without saved-for-later).
  • Review proposal, specs, design, and tasks with a strict checklist.
  • Practice behavior vs implementation on quantity and persistence.
  • Apply and archive only after the plan would survive a teammate’s questions.
Review is the step the tool does not do for you

OpenSpec is happy to draft files and then write code. The quiet middle step is you, reading the folder. The tool cannot know whether the cart should survive a refresh in the browser or only in the server’s memory. The assistant will pick one. Review is where you catch a code decision hiding inside a SHALL, or an Amazon-sized extra hiding in the scope.

/opsx:update exists because the four files depend on each other. If you delete checkout from the proposal, the spec, design, and tasks may still mention it until something rewrites them together. By hand, you would open all four and fix them. The command does that pass after you decide the edit.

The cart is the review lesson because it hides a lot of questions. Does a second add make a new line? What does the header count? What happens on refresh? Each unanswered question becomes a guess in the code. And each scenario you keep needs a test.

Think

If propose is “draft the PR description” and apply is “write the code,” what job is review? It is the same job as refusing to approve a design doc that says “handle edge cases appropriately.”

1. Why the cart is the review lesson

A cart looks obvious until you write it down. Amazon’s cart answers dozens of questions: merge quantities, persist after refresh, line subtotals, remove, empty cart, what happens if the product disappears. If you skip review, the agent will pick answers you may not want — and those answers will calcify in code.

This lesson slows down on purpose. Applying early is the failure mode.

3. Propose the cart

Your Task

New chat. Use this prompt. Notice how many decisions are named up front — that is how you steer the draft.

/opsx-propose add-shopping-cart

Add a ShopLite shopping cart, analogous to Amazon's cart (simplified).

Shopper-visible behavior:
- From product detail (and optionally the grid), the shopper can add a product to the cart.
- Adding a product already in the cart increases its quantity by one (does not create a duplicate line).
- The cart page lists each line: name, unit price, quantity, line subtotal (unit price × quantity).
- The cart shows a cart subtotal equal to the sum of line subtotals. No tax yet (checkout is a later change).
- The shopper can increase/decrease quantity. Quantity 0, or a Remove action, removes the line.
- An empty cart explains that it is empty and links back to the catalog.
- Cart contents persist across page refresh in the same browser. They do not need to persist across devices or logins (we have no accounts).
- A header cart indicator shows how many items are in the cart (sum of quantities).

Out of scope:
- Checkout, tax, shipping, promo codes, saved-for-later, wishlists, inventory reservation, accounts.

Read existing catalog and search specs so we do not contradict them.
Change name: add-shopping-cart.
Every scenario needs one automated test. The test name includes the scenario title.
The spec must say that. tasks.md must list those tests.

5. Deep review: specs (the contract)

Open the delta under openspec/changes/add-shopping-cart/specs/.

5.1 One SHALL per requirement

If you see a paragraph with three “and also” clauses, split it. Example of a fat requirement to reject:

The system SHALL let users add products, change quantities, persist the cart
in Redis, and display tax-inclusive totals in a React modal.

Split into add, quantity, persist, totals — and throw Redis/React out of the spec entirely.

5.2 Behavior, not storage

Keep in specMove to design.md
Cart survives refresh in the same browserlocalStorage vs cookie vs server session
Duplicate add increments quantityHash map keyed by product id
Line subtotal = price × qtyWhether math happens in JS or Python

5.3 Scenarios that earn their keep

You want at least these cases. Add any that are missing:

#### Scenario: Add from detail
- GIVEN a product detail page
- WHEN the shopper adds the product to the cart
- THEN the cart contains that product with quantity 1

#### Scenario: Add duplicate
- GIVEN the product is already in the cart with quantity 1
- WHEN the shopper adds it again
- THEN the cart still has one line for that product
- AND the quantity is 2

#### Scenario: Line subtotal
- GIVEN a line with unit price 10.00 and quantity 3
- WHEN the shopper views the cart
- THEN the line subtotal is 30.00
- AND the cart subtotal includes that 30.00

#### Scenario: Quantity zero removes
- GIVEN a line with quantity 1
- WHEN the shopper sets quantity to 0 (or removes the line)
- THEN that product is no longer in the cart

#### Scenario: Empty cart
- GIVEN the cart has no lines
- WHEN the shopper opens the cart
- THEN the page states the cart is empty
- AND the shopper can return to the catalog

#### Scenario: Refresh
- GIVEN the cart has at least one line
- WHEN the shopper refreshes the browser
- THEN those lines are still present

### Requirement: Test for each scenario
The project SHALL include one automated test for each scenario in this spec.
The test name SHALL include the scenario title.
The test SHALL fail when that scenario's THEN is not met.

If the AI only wrote the happy-path add, it drafted a demo script, not a spec. Fix it before apply.

5.4 The two-developer test

Read the spec once more. Could two implementers produce the same observable cart? Ambiguous spots to tighten:

  • Is the header count number of lines or sum of quantities? Pick one in the spec (we asked for sum of quantities).
  • Can quantity go above some max? If unspecified, the agent may invent 99. Either specify or explicitly leave it unbounded for ShopLite.
  • Does add from the grid exist, or only from detail? Align spec with the proposal.

6. Deep review: design.md

Design is allowed to name FastAPI routes, localStorage keys, and HTML pages. Watch for:

  • Too much: user accounts “so the cart can sync.” Out of scope.
  • Too little: “we will add a cart.” That is not a design.
  • Contradiction: spec says persist across refresh; design uses an in-memory Python dict (lost on uvicorn reload). Call that out — for a teaching app, localStorage or a JSON file is fine; pick one and make spec+design agree.
Abstraction level

Design should say where state lives and which endpoints exist, not paste 200 lines of imagined Python. If design.md is a novel, ask the agent to shorten it to decisions and rejected alternatives.

7. Deep review: tasks.md

Good tasks are checkable. Poor tasks hide work:

- [ ] 1.1 Implement cart   ← too big
- [ ] 1.1 Cart model / storage
- [ ] 1.2 Add-to-cart endpoint or client action
- [ ] 1.3 Cart page with lines and subtotals
- [ ] 1.4 Quantity update and remove
- [ ] 1.5 Header count
- [ ] 1.6 Empty state
- [ ] 1.7 Persistence across refresh
- [ ] 1.8 One test per scenario, named with the scenario title

Use update if you need a rewrite:

/opsx-update add-shopping-cart

Split tasks.md into small checkboxes matching the scenarios.
Include one test task per scenario. The test name includes the scenario title.
Do not add checkout. Do not write application code yet.

8. Apply, verify in the browser, archive

Your Task

Only after the checklist is green: new chat, apply, then click like a shopper.

/opsx-apply add-shopping-cart

Browser script:

  1. Add headphones twice — one line, quantity 2.
  2. Change quantity to 3 — line subtotal updates.
  3. Refresh — cart remains.
  4. Set quantity 0 or Remove — line gone.
  5. Empty cart message appears.
  6. Header count matches sum of quantities.
  7. Search still works (old specs still true).
  8. The tests pass. Each scenario title from the spec appears in a test name.
/opsx-archive add-shopping-cart

9. You now have a spec suite

Pause and open openspec/specs/. You should see catalog, search, and cart living together. This is the “product” OpenSpec is building besides the app. Future checkout must respect cart subtotals — lesson 07 will depend on that.

Your Task

Skim all main specs (not the archive). Write one sentence: “ShopLite today can …” If you cannot, the suite is not yet a useful onboarding doc — tighten a Purpose section.

10. Challenge (optional)

Amazon shows “Saved for later.” That is a new capability, not a cart tweak. If you want it, it deserves its own change after this one is archived — do not bolt it onto add-shopping-cart mid-flight unless it was always in scope (it was not).

11. Common issues

SymptomFix
Cart vanishes on refreshSpec said persist; implementation didn’t. Fix code, or you failed review on design. Apply again.
Two lines of the same productDuplicate-add scenario missing or ignored. Add scenario, then fix.
Agent added checkoutYou skipped out-of-scope in review. Delete checkout UI, update artifacts, re-apply cart only.
Subtotal is a string concat (“1010” instead of 20)Classic type bug. Spec is fine; code is not. This one really is a code bug.
