01 · Build a tiny OpenSpec yourself

No npm package yet. You write the Markdown folders and the slash-command files. Then you use them to ship a tiny catalog page — the same loop OpenSpec will run later.

Prefer skills instead of slash commands? Use the skills version of this lesson.

Lesson 01 of 10 ~90 minutes Hands-on homemade protocol
How this lesson works
  1. Feel why chat-only coding fails.
  2. Create a shoplite folder with protocol/specs and protocol/changes — the same two-folder idea OpenSpec uses.
  3. Copy-paste three command (or skill) files so your AI assistant learns propose / apply / archive.
  4. Run that loop to build a one-page Nile Retail catalog. No FastAPI yet. No OpenSpec CLI yet.
  5. Only then we name OpenSpec: it is this ritual, generated and merged more carefully.

1. Why we bother

Nile Retail asks you to add checkout. You type into the agent: 

Add checkout like Amazon. Collect shipping and show a total.

Code appears. Then tax is 8% because the model guessed. On Monday a teammate adds promo codes in a new chat and guesses a different tax rule. The rule lived only in the old chat. That is fast for a quick try, and useless as an agreement the next person can trust.

Think

Before creating any files, answer in one line each:

  1. Where should a business rule live so a new chat can find it?
  2. How do you stop the agent from writing code until you agreed on the rule?
  3. How do you teach the agent this ritual once, instead of pasting a paragraph every time?

This lesson’s answers: a specs/ folder, a change folder you review first, and a slash-command Markdown file in .cursor/commands/ (or .claude/commands/).

2. The homemade protocol (HomeSpec)

We will not install OpenSpec. We will fake it with folders plus three prompts saved as commands. Names:

Your jobHomeSpec commandOpenSpec later
Draft the plan, write no app code/homespec-propose/opsx-propose
Build only what the plan lists/homespec-apply/opsx-apply
Merge the spec delta into the source of truth, file the change away/homespec-archive/opsx-archive

Folders (these are protocol/, not openspec/, so lesson 02 can add the real tool beside them):

shoplite/
├── protocol/
│   ├── specs/                 # truth: how the app behaves TODAY
│   └── changes/               # one folder per in-flight change
│       └── archive/           # finished changes
├── .cursor/commands/          # Cursor slash commands (if you use Cursor)
│   ├── homespec-propose.md
│   ├── homespec-apply.md
│   └── homespec-archive.md
└── (later) index.html         # the tiny store we will build
What you are building

A spec is the written agreement about how the shop works today. A change is one piece of work that is not finished yet. A command is the instruction file the assistant reads so you do not paste that agreement process every time. OpenSpec later creates the folders and copies the rules for you. The ideas stay the same. Each scenario in a spec also asks for a test.

3. Create the project

Your Task

In a terminal, create the folder tree. Lesson 02 will keep using this same shoplite directory.

mkdir shoplite
cd shoplite
mkdir protocol
mkdir protocol\specs
mkdir protocol\changes
mkdir protocol\changes\archive
mkdir .cursor
mkdir .cursor\commands

macOS / Linux: use mkdir -p protocol/specs protocol/changes/archive .cursor/commands.

Open the shoplite folder as the Cursor (or Claude Code) workspace. Slash commands only appear for the workspace root.

4. Install the three commands by copy-paste

A slash command is a Markdown file. The filename becomes the command. Cursor looks in .cursor/commands/. Claude Code looks in .claude/commands/. You are doing by hand what openspec init will generate later.

4.1 Cursor (primary for this course)

Your Task

Create .cursor/commands/homespec-propose.md with exactly this content:

---
description: Draft a HomeSpec change. Write planning Markdown only. Do not implement.
---

You are running HomeSpec propose. Create the files yourself, in the order below.
Planning only: do not create or edit implementation files (source, markup, styles, scripts, tests, or config).

1. Understand the request.
   - If the user gave a kebab-case change name, use it. Otherwise derive one: lowercase words joined by hyphens.
     Example: "add user authentication" becomes add-user-auth.
   - If you cannot tell what observable behavior should change, ask one question and wait.
   - If a detail is small, choose a reasonable assumption and record it under Impact in the proposal.
   - If protocol/changes/<name>/ already exists, ask whether to continue it or pick a new name. Do not overwrite it.

2. Create protocol/changes/<name>/ and write four artifacts, in this order.
   Later files depend on earlier ones, so finish and re-read each file before starting the next.
   Write them in this order: proposal, then specs, then design, then tasks.

3. proposal.md — why this change exists, and what is in or out.
   Use this shape:

   A capability is one area of behavior, named in kebab-case.
   Write "None." when a Capabilities subsection has no entries.

   # Proposal: <name>

   ## Why
   <one or two sentences: the problem, and the outcome when this change is done>

   ## What Changes
   - <behavior this change adds, changes, or removes>

   ## Capabilities

   ### New Capabilities
   - `<capability>`: <one line>

   ### Modified Capabilities
   - `<capability>`: <one line>

   ## Impact
   - <what parts of the system this touches>
   - <assumptions you made>
   - Out of scope: <behavior you will not add in this change>

4. specs/<capability>/spec.md — the delta. One file per capability.
   A delta is the diff for this change, not a rewrite of all current behavior.
   If protocol/specs/<capability>/spec.md already exists, read it first.
   Reuse that capability name. Do not invent a second name for the same behavior.
   Use ADDED only for new rules, MODIFIED only when replacing an existing requirement
   with the same title, and REMOVED only when a requirement should disappear.
   Describe what a person can observe. Do not name languages, frameworks, libraries, or file paths.
   Include one unhappy path (empty, missing, or rejected input) when the request has one.
   Every scenario needs a test. End the delta with this requirement:

   ### Requirement: Test for each scenario
   The project SHALL include one automated test for each scenario in this spec.
   The test name SHALL include the scenario title.
   The test SHALL fail when that scenario's THEN is not met.

   Use only the sections you need:

   # Delta for <capability>

   ## Purpose
   <one sentence; include this section only when the capability is new>

   ## ADDED Requirements

   ### Requirement: <short title>
   The system SHALL <observable behavior>.

   #### Scenario: <short case name>
   - GIVEN <starting state>
   - WHEN <action>
   - THEN <observable result>

   ## MODIFIED Requirements

   ### Requirement: <same title as the living spec>
   The system SHALL <full replacement text, including its scenarios>.

   ## REMOVED Requirements

   ### Requirement: <title that should disappear>
   <one line on why it goes away>

5. design.md — how to build what the spec describes. Read the proposal and the delta first.

   # Design: <name>

   ## Context
   <what exists today that this change must fit; say so if nothing exists yet>

   ## Goals / Non-Goals

   **Goals:**
   - <outcome this change must achieve>

   **Non-Goals:**
   - <same items as Out of scope in the proposal>

   ## Decisions

   ### 1. <decision title>
   <what you will do, in concrete terms>

   - Why: <one sentence>
   - Alternative not chosen: <one sentence>

   Add more numbered decisions only when a real choice exists. Do not start building.

6. tasks.md — small steps the implementer will tick. Read the design and the delta first.
   Every in-scope requirement needs at least one task. Out-of-scope items get no task.
   Every scenario needs its own task: write the automated test for that scenario and make it pass.
   Each checkbox is one checkable step, not "build the feature."

   # Tasks: <name>

   ## 1. <group name>

   - [ ] 1.1 <one small step, including how to tell it is done>
   - [ ] 1.2 <the next step>

7. Stop. List each file you created with a one-line summary.
   Tell the user to review them, then run /homespec-apply <name>.
   Do not implement in this turn, even if the user asked you to build it.
Your Task

Create .cursor/commands/homespec-apply.md:

---
description: Implement one HomeSpec change from its tasks, specs, and design.
---

You are running HomeSpec apply. The plan already exists; implement that plan.

1. Choose the change.
   - If the user named one, use protocol/changes/<name>/.
   - If not, and exactly one folder sits directly under protocol/changes/ (ignore archive/), use it and say which one.
   - If several are open, list them and ask. Do not guess.

2. Read these files from disk, in this order, before you change anything:
   proposal.md, every file under specs/, design.md, tasks.md.
   Implement from those files. Do not rebuild the plan from an earlier chat.

3. Work unchecked tasks from top to bottom.
   - Make the smallest change that finishes that one task.
   - When the spec behavior for that task is actually done, change `- [ ]` to `- [x]` in tasks.md.
   - Leave the box unchecked if the task is only partly done.
   - Say which task you are on (for example, "2/5") before you start it.

4. Stay inside the proposal.
   Do not add behavior listed as out of scope.
   Do not invent requirements that are not in the delta spec.
   For each scenario, write the automated test named in the spec and make it pass.
   A scenario with no passing test is not done.

5. Stop and ask when:
   - a task is unclear
   - building it would need behavior the spec does not describe
   - the design conflicts with the spec
   Do not silently shrink, skip, or rewrite a requirement to make the task easier.

6. Do not edit anything under protocol/specs/.
   Do not move the change folder into archive/.
   Merging and filing happen only in /homespec-archive.

7. When every task is checked, list what you completed and tell the user they can run /homespec-archive <name>.
   If you paused, say why and wait.
Your Task

Create .cursor/commands/homespec-archive.md:

---
description: Merge HomeSpec delta specs into protocol/specs and archive the change folder.
---

You are running HomeSpec archive. You merge Markdown. You do not change implementation code.

1. Choose the change the same way apply does.
   Use the name the user gave, or the only open folder under protocol/changes/ (not inside archive/).
   If several are open, list them and ask.
   Say which change you are archiving.

2. Read tasks.md.
   A task is complete only when its box contains x or X, as in `- [x]`.
   If any task is still open, say how many and ask whether to continue.
   Continue only if the user says yes. If there is no tasks.md, continue and mention that.

3. Merge each delta into the living spec.
   For every file protocol/changes/<name>/specs/<capability>/spec.md,
   the living spec is protocol/specs/<capability>/spec.md.
   A requirement's identity is its heading: ### Requirement: <title>. Match on that exact title.

   - If the living spec does not exist:
     Create it from the delta's ADDED requirements only.
     Keep ## Purpose when the delta has one.
     Drop the word "Delta" so the file reads as current truth, under a heading ## Requirements.
     If the delta has MODIFIED or REMOVED but no ADDED, stop. There is no living spec to change.
   - If the living spec exists:
     ADDED: append each new requirement. If that title is already there, do not add a second copy; say so.
     MODIFIED: replace the whole requirement with that title, including its scenarios.
     If the title is missing, stop and name the title you could not find.
     REMOVED: delete the requirement with that title. If the title is missing, say so and continue.
   - Leave every other requirement in the living spec unchanged.

4. Move the change folder only after the merge is done.
   From: protocol/changes/<name>/
   To:   protocol/changes/archive/YYYY-MM-DD-<name>/
   Use today's date. If that archive folder already exists, stop and ask. Do not overwrite it.
   If the change name already starts with YYYY-MM-DD-, do not add a second date.

5. Do not edit implementation code.
   Report the change name, the archive path, and for each capability which requirement
   titles were added, replaced, or removed.

4.2 Claude Code (if that is your agent)

4.4 Reload and confirm

Your Task

Reload the editor window (Cursor Command Palette → “Developer: Reload Window”). In a new chat type:

/homespec

You should see autocomplete for propose, apply, and archive. If not: confirm the workspace root is shoplite, not its parent; confirm the filenames; reload again.

If slash commands still do not appear

You can still run the protocol: open a new chat and paste the contents of homespec-propose.md as the first message, then your feature request. The file is the ritual. Autocomplete is convenience. OpenSpec later is the same idea with more tools pre-wired.

What those files actually are

Those three Markdown files are the whole method. The model does not already know “HomeSpec.” It reads the command file and follows it. Later, openspec init writes longer versions of the same instructions, and a terminal command that creates folders and copies rules more carefully. You now know why init exists.

5. Propose a tiny catalog — Markdown only

Amazon’s home page is a wall of products. We want the smallest possible slice: a single HTML page with three items and prices. No search, no cart. Keep the change small so you can watch every file.

Your Task

New chat. Run propose. Then do not apply until you have opened the generated Markdown.

/homespec-propose add-hello-catalog

Build ShopLite's first slice for Nile Retail: a single index.html catalog page.

In scope:
- A heading "ShopLite"
- At least three products, each with a name and a price
- A short note that this is a teaching store, not amazon.com

Out of scope:
- Search, cart, checkout, accounts, FastAPI, databases

Use capability name catalog. Change name add-hello-catalog.
Stop after the Markdown artifacts. No application code yet.
Your Task — review like a teammate

Open the folder the agent created. You should see something like:

protocol/changes/add-hello-catalog/
  proposal.md
  design.md
  tasks.md
  specs/catalog/spec.md

Check:

  • Proposal lists search/cart as out of scope.
  • Spec describes shopper-visible behavior (names and prices), not “use flexbox.”
  • Spec has at least one Given / When / Then scenario.
  • The spec includes “Test for each scenario”: one automated test per scenario, and the test name includes the scenario title.
  • Tasks include a checkbox to write that test. Propose still does not write the test. Apply does.
  • Tasks are small checkboxes, not one line “build the site.”
  • There is still no index.html. If the agent wrote the page already, it ignored the command. Delete the HTML and remind it: propose writes Markdown only.
Think

Would you merge a colleague’s design unread because it “looks like Markdown”? The review step is the whole protocol. OpenSpec will not do this for you either.

If the spec is vague, edit the file by hand or tell the same chat: “Add a scenario for an empty product list. Do not write HTML.”

A healthy spec delta looks like this (yours need not match word for word):

# Delta for catalog

## ADDED Requirements

### Requirement: Product listing
The home page SHALL list at least three products, each with a name and a price.

#### Scenario: Shopper opens the page
- GIVEN the catalog has seed products
- WHEN the shopper opens index.html
- THEN at least three products are visible
- AND each shows a name and a price

### Requirement: Test for each scenario
The project SHALL include one automated test for each scenario in this spec.
The test name SHALL include the scenario title.
The test SHALL fail when that scenario's THEN is not met.

6. Apply — now the agent may write code

Your Task

New chat (clean context). Apply the change you just reviewed.

/homespec-apply add-hello-catalog

When it finishes, open index.html in a browser (double-click, or Live Preview). You should see ShopLite and three products.

Manual check
  • Heading ShopLite (or Nile Retail) is visible.
  • Three products with prices.
  • A test exists for the catalog scenario, the test name includes that scenario’s title, and the test passes.
  • tasks.md checkboxes are mostly ticked.
  • No search box that works. No cart. The command said out of scope.
What apply just did

Apply did not go back to your first sentence, “like Amazon.” It read tasks.md, the spec, and the design. That is why we split propose and apply. A vague spec produces a confident wrong page. A clear spec produces a plain correct page, plus a test for each scenario. OpenSpec’s apply command is the same idea, with a bit more bookkeeping around the files.

7. Archive — fold the change into truth

Right now the catalog rules live only in the change folder. A new chat would not know ShopLite already lists products. Archive copies the delta into protocol/specs/ and moves the change into archive/.

Your Task

New chat, or the apply chat if it is still focused:

/homespec-archive add-hello-catalog

Then confirm:

dir protocol\specs
dir protocol\changes\archive

You want protocol/specs/catalog/spec.md (living truth) and a dated folder under archive/. The open change folder should be gone.

What archive just did

You asked the model to copy the new rules into the main spec. That works until two rules share a vague title. OpenSpec’s archive command does that copy with a program, so ADDED, MODIFIED, and REMOVED are followed exactly. You would not want a tax rule copied “creatively.”

8. Prove the spec is memory

Your Task

Brand-new chat. Do not mention what you built. Ask:

Using only files under protocol/specs/, what can a ShopLite shopper do today?
Do not invent features that are not in those files.

If the answer is “see a list of products with prices,” the protocol worked. If the agent invents checkout, it did not stay inside protocol/specs/ — that is what OpenSpec’s spec suite is for, at larger scale.

9. Optional second change (same commands)

You already have a living spec under protocol/specs/catalog/. This second loop is tiny on purpose: a footer line “Nile Retail · teaching store.” You will reuse the same three commands. The only new idea is archive appending an ADDED requirement onto an existing spec, instead of creating the file from scratch.

Think first — skip the protocol?

A footer that is only copy, with no shopper behavior, is a fair “just edit index.html” call. Making that call is part of the skill. If you skip, add the line by hand, say why, and jump to section 10. If you want muscle memory on propose → review → apply → archive, follow the commands below in a new chat each time (clean context, same as sections 5–7).

9.1 Propose — Markdown only

Your Task

New chat. Run propose. Then do not apply until you have opened the generated Markdown.

/homespec-propose add-store-footer

Add a footer to ShopLite's existing index.html.

In scope:
- A footer line that reads exactly: Nile Retail · teaching store
- Visible on the same catalog page the shopper already opens

Out of scope:
- New pages, links, copyright years, social icons
- Search, cart, checkout, accounts, FastAPI, databases
- Changing product names or prices

Use capability name catalog (this is more catalog page behavior, not a new capability).
Change name add-store-footer.
Stop after the Markdown artifacts. No application code yet. Do not edit index.html.
Your Task — review like a teammate

Open the folder the agent created. You should see:

protocol/changes/add-store-footer/
  proposal.md
  design.md
  tasks.md
  specs/catalog/spec.md

Check:

  • Proposal lists search/cart/new pages as out of scope.
  • The delta is ## ADDED Requirements (a new footer rule). It must not rewrite or delete the product-listing requirement you already archived.
  • Spec describes shopper-visible text, not “use a <footer> tag” as the requirement.
  • Spec has at least one Given / When / Then scenario.
  • The spec includes “Test for each scenario”: one automated test per scenario, and the test name includes the scenario title.
  • Tasks include a checkbox to write that test. Propose still does not write the test. Apply does.
  • Tasks are small checkboxes (add footer, keep the three products, do not add search).
  • index.html is still unchanged. If the agent edited it, undo that and remind it: propose writes Markdown only.

A healthy spec delta looks like this (yours need not match word for word):

# Delta for catalog

## ADDED Requirements

### Requirement: Store footer
The home page SHALL show a footer line that reads "Nile Retail · teaching store".

#### Scenario: Shopper reaches the bottom of the page
- GIVEN the shopper opens index.html
- WHEN the page has loaded
- THEN the line "Nile Retail · teaching store" is visible
- AND the existing products and ShopLite heading are still present

### Requirement: Test for each scenario
The project SHALL include one automated test for each scenario in this spec.
The test name SHALL include the scenario title.
The test SHALL fail when that scenario's THEN is not met.

9.2 Apply — now the agent may edit the page

Your Task

New chat (clean context). Apply only this change.

/homespec-apply add-store-footer

When it finishes, refresh index.html in the browser. You should still see ShopLite and the three products, plus the new footer.

Manual check
  • Footer text is exactly Nile Retail · teaching store (or the wording you approved in the spec).
  • The three products and prices did not change.
  • tasks.md checkboxes are mostly ticked.
  • Still no search box, cart, or extra pages.

9.3 Archive — append the footer rule onto living truth

After the first change, “the home page lists products” already lives in protocol/specs/catalog/spec.md. Archive should keep those requirements and append the footer requirement. If the agent replaces the whole file and drops product listing, the protocol failed — put the old requirements back.

Your Task

New chat, or the apply chat if it is still focused:

/homespec-archive add-store-footer

Then confirm:

dir protocol\specs\catalog
dir protocol\changes
dir protocol\changes\archive

You want protocol/specs/catalog/spec.md to mention both products and the footer, a new dated folder protocol/changes/archive/YYYY-MM-DD-add-store-footer/, and no open protocol/changes/add-store-footer/ folder.

Open the living spec and check it now contains (order can vary):

  • Product listing (from the first archive)
  • Store identity / teaching-store note (from the first archive)
  • Store footer (just merged)
The second archive should add, not replace

The first archive created protocol/specs/catalog/spec.md. This one should add the footer rule onto that file. The old product-listing rule stays. If the model rewrote the file and dropped a requirement, you just saw why a careful copy matters. A vague title can overwrite the wrong rule, including a tax rule later.

9.4 Prove the spec grew

Your Task

Brand-new chat. Do not mention the footer. Ask:

Using only files under protocol/specs/, what can a ShopLite shopper do today?
Do not invent features that are not in those files.

You now want two answers, not one: see products with prices, and see the Nile Retail teaching-store footer. If the agent only remembers the first change, archive did not merge. If it invents checkout, it left protocol/specs/.

10. What still hurts (why OpenSpec exists)

You already have a working spec-driven store. A weekend protocol. Pain you will not want to maintain:

  • Every AI tool wants commands in a different directory.
  • Teammates will “improve” the three Markdown files until propose starts writing code again.
  • Archive merge is only as careful as today’s model.
  • No list / validate / dashboard of open changes.
  • No explore command, no review gates for huge features, no shared dialect across 30 tools.

The painful part is keeping those files tidy across tools. You already understand the idea, because you just ran it.

These are the habits I want you to keep:

You can go back and edit.
You can change the plan when you learn something.
Keep each change small.
The same folders work on a new shop and on a shop that already exists.
The same idea works for one person and for a team.

OpenSpec drafts the Markdown. It does not replace your reading. If you accept a bad plan, apply builds a bad page, and the tests only prove that bad plan.

Think

If the OpenSpec website disappeared tomorrow, could you keep shipping with HomeSpec? You just did. Later lessons show what the package adds (validation, explore, continue/ff, portable skills). You will never need to treat slash commands as magic: you have written them.
