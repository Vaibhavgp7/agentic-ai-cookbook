The three commands, in plain words

These are the same three jobs you did by hand in lesson 01.

You typeWhat happensWhat you did by hand
/opsx:propose The instruction file tells the assistant: make a change folder, write the proposal, the spec difference, the design, and the tasks, then stop. The spec must say that each scenario gets a test. The tasks must list those tests. The assistant writes no shop code yet. Your propose file, plus creating the folder
/opsx:apply The assistant reads the tasks, the spec, and the design. It does the checkboxes in order, including the tests, and ticks them as it goes. It should not add features you left out. Your apply file
/opsx:archive The new rules are copied into openspec/specs/, including the test requirement. The change folder moves to changes/archive/YYYY-MM-DD-name/. A changed rule is found by its heading, so the title must match. Your archive file, plus a careful copy

You still have to read the plan between propose and apply. The tool will not do that reading for you.

Think

After propose, the code still should not exist. If the agent starts writing FastAPI during propose, it violated the skill. Stop it. The split exists to protect you from exactly that.

Check your thought

Propose is planning only. A finished run leaves openspec/changes/add-product-catalog/ with Markdown — proposal, delta specs, design, tasks — and no FastAPI files. If app/main.py appears, the skill was ignored and the review gate never happened. Stop the agent, delete the premature code, keep the artifacts. You apply later, in a new chat, after you have agreed the plan. That split is what stops rejected ideas from becoming the storefront.

1. The feature (intentionally small)

Amazon’s home experience is a wall of products. ShopLite’s first slice is smaller: a home page that lists products with name and price, plus a simple detail page. No search box yet. No cart. Scope stays small so you can feel the whole loop in about ten minutes of agent time — then we slow down for review.

Why we skip the thinking step this time

Lesson 05 is where we practice thinking out loud before we write a spec. Here I am handing you the feature, the way a clear ticket sometimes does. When you can already say the change in one sentence, going straight to propose is the right move.

2. Start a clean chat

Your Task

Open the shoplite folder as the workspace. Start a new agent chat. Do not reuse a long setup conversation from lesson 02.

3. Propose the catalog

In Cursor:

/opsx-propose add-product-catalog

Build ShopLite's first slice: a mini-Amazon product catalog.

In scope:
- A home page that lists seed products (at least 6 everyday items: e.g. headphones, kettle, notebook, coffee beans, USB-C cable, desk lamp).
- Each product shows name, price, and a short description.
- Clicking a product opens a detail page with the same fields.
- Empty-catalog message if the product list is empty.
- FastAPI + vanilla HTML/CSS/JS. Seed data in JSON or a Python module.
- Run with uvicorn on port 8000.

Out of scope:
- Search, cart, checkout, accounts, recommendations, real payments, inventory rules.

Keep the change named add-product-catalog. Specs describe shopper-visible behavior only.
Every scenario needs one automated test. The test name includes the scenario title.
tasks.md must list those tests. Do not write application code or tests during propose.

Claude Code equivalent: start with /opsx:propose add-product-catalog and paste the same body.

Wait until the agent reports that it created a change folder with proposal, specs, design, and tasks. Do not apply yet.

Your Task

In the terminal, from shoplite:

openspec list
openspec show add-product-catalog

Then open these files in the editor:

  • openspec/changes/add-product-catalog/tasks.md

4.1 Two-minute review (do this every time)

Read the plan the way you would read a colleague’s PR description. Ask:

ArtifactQuestions
Proposal Is the intent one sentence? Is search/cart listed as out of scope? Did the AI sneak in extra features?
Specs Can a shopper see the behavior? Does the empty catalog have its own scenario? Does any SHALL name FastAPI or CSS? Does the spec say each scenario needs a test, and do the tasks list those tests?
Design Is the stack what we asked for? Is persistence simple? Any over-engineering (auth, Docker, React)?
Tasks Could you implement from the checkboxes alone? Are they small enough to verify one at a time?
Do not accept the draft because it “looks like Markdown”

Students fail this step by trusting the AI’s first draft. Would you merge a teammate’s spec unread? If the proposal includes search, a cart, or “users must sign in,” edit it now. You can edit the files by hand or ask in the same chat: “Remove search and accounts from the proposal and specs. Catalog only.”

If you want the agent to keep artifacts consistent after a manual edit:

/opsx-update

I edited the proposal to exclude search and cart. Align specs, design, and tasks. Do not write application code.
Explanation — what “healthy” looks like

Walk the table. A pass looks like this:

  • Proposal — one sentence of intent (“shoppers browse a seed catalog”). Search, cart, checkout, accounts are named out of scope. No extra features.
  • Specs — what the shopper can see. The home page lists name and price (and a description if you asked). The empty catalog and an unknown product each have a scenario. No SHALL that names FastAPI or CSS. The spec includes “Test for each scenario.”
  • Design — FastAPI + vanilla HTML/CSS/JS, seed in JSON or a Python module, uvicorn on 8000. Persistence is a file, not Postgres. No auth, Docker, or React.
  • Tasks — small checkboxes you could tick one at a time (scaffold, seed, home grid, detail, empty/not-found). If you cannot implement from the list alone, the tasks are too vague.

If the draft includes search or accounts, edit now — by hand or with the /opsx-update prompt above. Do not apply a plan you would not merge.

4.2 What a healthy catalog spec looks like

Yours will not match word-for-word. The shape should:

## Purpose
Shoppers can browse Nile Retail products and open a product detail page.

## ADDED Requirements

### Requirement: Home catalog
The system SHALL list each available product with name and price.

#### Scenario: Seeded store
- GIVEN the store has multiple available products
- WHEN the shopper opens the home page
- THEN each product is listed with name and price

#### Scenario: No products
- GIVEN the catalog has no products
- WHEN the shopper opens the home page
- THEN the page states that no products are available

### Requirement: Product detail
The system SHALL show name, price, and description for a selected product.

#### Scenario: Open from the grid
- GIVEN a listed product
- WHEN the shopper selects it
- THEN the detail view shows that product’s name, price, and description

#### Scenario: Unknown product
- GIVEN a product id that does not exist
- WHEN the shopper opens its detail URL
- THEN the system shows a not-found message rather than an empty broken page

### Requirement: Test for each scenario
The project SHALL include one automated test for each scenario in this spec.
The test name SHALL include the scenario title.
The test SHALL fail when that scenario's THEN is not met.

5. Apply — in a fresh chat

Planning and implementation compete for the same context window. A long propose conversation is full of rejected ideas. Start implementation clean.

Your Task

Open a new chat. Then apply.

/opsx-apply add-product-catalog

The agent reads tasks.md, the delta specs, and design.md. It should work through checkboxes and mark them done. If it asks to confirm the change name, say yes.

You should see something like

Implementing add-product-catalog...
✓ 1.1 Create FastAPI app scaffold
✓ 1.2 Add seed products
✓ 2.1 Home page product grid
✓ 2.2 Product detail page
✓ 3.1 Empty and not-found states
All tasks complete.

6. Run ShopLite

Your Task

Create a virtual environment, install dependencies the agent added (often requirements.txt or pyproject.toml), and start the server.

python -m venv .venv
# Windows PowerShell
.\.venv\Scripts\Activate.ps1
# macOS / Linux
# source .venv/bin/activate

pip install -r requirements.txt
uvicorn app.main:app --reload --port 8000

Paths may differ (main.py at repo root, or app/main.py). Use whatever design.md and the generated README say. If the agent used a different runner, follow that.

Open http://127.0.0.1:8000. You should see a grid of products. Click one. You should see details.

Manual acceptance
  • At least six products, each with name and price.
  • A detail page for a product.
  • A sensible not-found page if you invent a bad URL (try /products/does-not-exist or similar).
  • No search box, no cart icon that works, no login wall. Extra decorations are okay if they do not invent behavior.
  • The tests pass, and you can point at one test whose name includes a scenario title from the spec.

7. If the app is wrong

Do not immediately paste a new vibe prompt. Trace it:

  1. Is the behavior specified? If no, the spec is incomplete — edit specs, then apply again.
  2. Is the behavior specified but the code ignores it? That is an implementation miss — apply again calling out the task.
  3. Did the agent build search “to be helpful”? That is scope creep — delete it or park it for lesson 05. Update the proposal if needed.

To resume a partial apply in a new chat:

/opsx-apply add-product-catalog

Continue remaining tasks. Do not expand scope.

8. Archive

Only archive when you would be willing to treat the catalog behavior as “how ShopLite works today.”

Your Task

New chat (or the apply chat if it is still focused). Archive and allow spec sync when asked.

/opsx-archive add-product-catalog

Terminal equivalent if you prefer (skips some chat confirmation):

openspec archive add-product-catalog --yes

Check:

openspec list
dir openspec\specs
dir openspec\changes\archive

list should show no active change (or not show add-product-catalog). You should have something like openspec/specs/catalog/spec.md and an archive folder dated today.

9. Why this mattered

You now have two products, not one:

  • A running storefront grid.
  • A spec suite that says what that grid must do.

Tomorrow’s agent can read the spec and will not “forget” that products have detail pages. That is the whole point of the cycle, even when the feature felt small.

10. Challenge (optional)

Challenge

Without starting a new OpenSpec change, read openspec/specs/catalog/spec.md and add one scenario the AI missed (for example: prices show two decimal places). Then decide: is this a spec fix you should have made before archive? If yes, you can still edit the main spec by hand — and you should, because the spec is now the truth. We will do a proper MODIFIED delta in lesson 09.

That hand-edit does not change the running app, and the next /opsx-apply will not implement it. Apply reads an active change’s tasks.md, delta specs, and design.md. After archive, add-product-catalog is gone — there is nothing left to apply. The main spec is documented truth for the next agent (lesson 05 will read it). If the page already matches, you only fixed the spec. If it does not, you have drift: either patch the template yourself, or open a new change later (lesson 09) and apply that.

Solution

Yes — a missing scenario is a spec gap you should have caught in the two-minute review, before archive. After archive the main spec is the truth, so edit openspec/specs/catalog/spec.md by hand. Do not open a new change for a one-line clarification; lesson 09 is the proper MODIFIED delta.

Example scenario you can add under product listing or a new “Price display” requirement:

### Requirement: Price display
The system SHALL show each product price with a currency symbol and exactly two decimal places.

#### Scenario: Seeded prices
- GIVEN a product priced 29.5
- WHEN the shopper views the listing or the detail page
- THEN the price is shown as $29.50

Then glance at the running app. If it already prints $29.50, spec and code still agree. If it prints 29.5, only the Markdown changed — OpenSpec will not notice until you either edit the HTML yourself or create a new change with tasks and apply that one.

11. Common issues

SymptomFix

Agent used React / Next.jsOut of stack. Update design.md and apply again, or revert and re-propose with a firmer constraint.
PowerShell activate failsExecution policy: Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass then activate.

12. Reflection

  1. Which artifact did you actually edit, if any? What would have gone wrong if you had not?
  2. Why apply in a new chat?
  3. After archive, where does “products have a detail page” live?
Check your answers
  1. Honest answer for many first runs: none — and that is the failure mode. If you did edit, it was probably the proposal (strip search/cart/accounts) or the spec (add empty catalog / unknown product). Skipping that edit means apply builds the sneaked feature, or ships a grid with no empty-state.
  2. Planning and implementation share one context window. A long propose thread still contains rejected ideas. A fresh chat makes the agent a constrained reader of tasks.md, the delta spec, and design.md — not a continuation of the Amazon brainstorm.
  3. In the main spec: openspec/specs/catalog/spec.md, under the product-detail requirement. That is today’s truth. The archived folder is decision history. The page at /products/{id} is the implementation, not a replacement for the spec.
