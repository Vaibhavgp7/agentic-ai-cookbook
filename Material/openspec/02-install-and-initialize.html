02 · Install and Initialize

OpenSpec has two places you type. The terminal runs openspec. The chat runs /opsx. Lesson 01 was the homemade version of both.

Lesson 02 of 10 ~50 minutes Hands-on setup
What you will do
  • Install the OpenSpec CLI and verify Node.js.
  • Create the shoplite project folder.
  • Run openspec init and inspect what it wrote.
  • Learn where to type openspec ... vs /opsx:....
What init is actually doing

In lesson 01 you made two things by hand: folders for specs and changes, and three instruction files so you would not paste the same prompt every time. npm install -g @fission-ai/openspec puts the openspec command on your machine. openspec init then does two jobs:

  1. Creates openspec/specs/ and openspec/changes/. They start empty. Those folders are the system.
  2. Writes instruction files into your AI tool’s folder (.cursor/, .claude/, and so on). Those files are the same kind of instructions you pasted in lesson 01, written in the spelling that tool understands.

Nothing stays running in the background. The chat commands work because the editor read those files when it started. That is why you reload the window. If the commands disappear later, openspec update writes the instruction files again so they match the version you installed.

Think

If you were not allowed to install OpenSpec, where would you put the “plan this change” instructions so Cursor still picked them up? A file under .cursor/ is enough. Init writes that file for you, and the matching file for Claude if you selected both tools.

1. Two places to type

This is the mistake I see first. The terminal and the chat are not the same place.

WhereWhat you typeExamples
Terminal (PowerShell, VS Code terminal, iTerm) openspec ... openspec init, openspec list, openspec view
AI chat (Cursor, Claude Code, Copilot…) /opsx:... (or your tool’s spelling) /opsx:propose, /opsx:apply, /opsx:archive 
        YOUR TERMINAL                         YOUR AI ASSISTANT'S CHAT
   ┌──────────────────────┐               ┌──────────────────────────────┐
   │  $ openspec init     │   installs    │  /opsx:propose add-catalog    │
   │  $ openspec list     │  ──────────►  │  /opsx:apply                  │
   │  $ openspec view     │   commands    │  /opsx:archive                │
   └──────────────────────┘    & skills   └──────────────────────────────┘
        run openspec here                       run /opsx:* here

There is no extra program you have to leave running. Open the coding assistant the way you always do, and type the slash command in chat. openspec init is what puts those chat commands into the tool.

How you type slash commands

Canonical name in docs: /opsx:propose

  • Cursor / GitHub Copilot: /opsx-propose (hyphen)
  • Claude Code / Gemini CLI: /opsx:propose (colon)
  • Amazon Q: @opsx-propose
  • Codex: $openspec-propose

openspec init prints the spelling for the tools you selected. Trust that line. When in doubt, type /opsx and use autocomplete.

2. Check Node.js

OpenSpec requires Node.js 20.19.0 or higher.

Your Task

In a terminal, check your Node version.

node --version

If you see v20.19.0 or greater, continue. If not, install a current LTS from nodejs.org or your version manager (nvm, fnm, volta), then open a new terminal.

3. Install the CLI

The CLI is installed once per machine (per Node installation). It does not live inside one project.

Your Task

Install OpenSpec globally with npm, then check the version.

npm install -g @fission-ai/openspec@latest
openspec --version

A version number means the terminal can find the openspec command. pnpm and bun can install it too. If you use Yarn, use npm, pnpm, or bun for this global install. Newer Yarn does not keep a global install command.

Common issue: command not found

On Windows, the folder where npm puts global commands is sometimes missing from PATH. Run npm bin -g, add that folder to PATH, and open a new terminal. On macOS or Linux, install npm packages for your own user. You should not need sudo for this.

Optional: opt out of anonymous telemetry (command names and version only; no paths or source).

openspec config set telemetry.enabled false

Environment alternatives: OPENSPEC_TELEMETRY=0 or DO_NOT_TRACK=1.

4. Continue in the ShopLite project from lesson 01

You already created shoplite with HomeSpec (protocol/ and /homespec-* commands). Stay in that folder. OpenSpec will add openspec/ and /opsx-* beside what you built by hand — that comparison is the point. If you skipped lesson 01, create the folder now.

Your Task

From a terminal, enter the existing project (create it only if it is missing), then initialize git if you have not.

4.1 Python check (used from lesson 04)

Your Task

Confirm Python is available. We will not run an app until the catalog exists.

python --version

5. Initialize OpenSpec in the project

openspec init is interactive. It asks which AI tools you use, then writes skills/commands into that tool’s folders, plus the openspec/ directory.

Your Task

From inside shoplite, initialize OpenSpec. Pick the tool you actually use (Cursor, Claude Code, …). You can select more than one.

cd shoplite
openspec init

Non-interactive variant if you already know the tool id (example: Cursor only):

openspec init --tools cursor

Useful tool ids include: cursor, claude, github-copilot, codex, amazon-q. --tools all is possible but noisy.

Want the AI to do setup?

You can paste this into chat instead of running init yourself:

Fetch https://raw.githubusercontent.com/Fission-AI/OpenSpec/main/install.md and follow it.

Prefer the manual steps at least once so you see what was created.

5.1 Restart the editor

Many tools scan skills and slash commands at startup. After init, reload the window (Cursor: Command Palette → “Developer: Reload Window”) or close and reopen the project. Then type /opsx in chat and confirm autocomplete appears.

6. What init created

You should now see something like this (exact agent folders depend on the tools you picked):

shoplite/
├── README.md
├── .gitignore
├── openspec/
│   ├── specs/              # empty at first — source of truth will grow here
│   ├── changes/            # empty — one folder per in-flight change
│   └── config.yaml         # project context for the AI (may appear after first use / edit)
├── .cursor/                # if you selected Cursor: commands / skills
│   └── ...
└── .claude/                # if you selected Claude Code
    └── ...
Your Task

List the project and browse with the CLI.

openspec --version
openspec list
openspec view

openspec list should show no active changes. openspec view opens a small dashboard for specs and changes. Close it when you have clicked around.

Optional health check:

openspec doctor

6.1 Skills vs commands (you do not have to memorize paths)

Init writes skills (folders like openspec-propose/SKILL.md) and/or command files (tool-specific slash-command markdown). You never edit these by hand for this course. If slash commands vanish later, the fix is: 

openspec update

openspec update refreshes generated agent files to match the installed CLI. Run it in each project after you upgrade the global package, and after you change the workflow profile (lesson 08).

Behind the scenes — a skill file is just Prompt B with a filename

Open one generated file if you like (example: a Cursor command markdown under .cursor/, or .claude/skills/openspec-propose/SKILL.md). You will see English instructions: create a change, write these artifacts, stop before code. That is your homemade Prompt B, checked into the repo so every session loads it. You still talk to the model; the file only sets the job description. The CLI is what the skill is allowed to call for mkdir/templates/status — so the model is not inventing folder names.

7. Core profile vs expanded profile

New installs default to the core profile. That is what we want for lessons 04–07.

ProfileChat commands you get
core (default) explore, propose, apply, update, sync, archive
expanded / custom Above, plus new, continue, ff, verify, bulk-archive, onboard

Do not switch profiles yet. Lesson 08 is when complexity earns the extra commands.

Profile lives in global CLI settings (machine-wide JSON), not in openspec/config.yaml. To peek without changing anything: 

openspec config list

A fresh install should look like this (telemetry lines may differ):

featureFlags: {}
profile: core
delivery: both

Profile settings:
  profile: core (default)
  delivery: both (default)
  workflows: propose, explore, apply, update, sync, archive (from core profile)

One-value check: openspec config get profile should print core. Bare openspec config only prints help and exits with an error — it does not show settings. The interactive switcher is openspec config profile; skip it until lesson 08.

If you already see profile: custom and extra workflows (new, ff, …), this machine was configured earlier. Leave it for now; do not run the picker here.

8. Give the project a voice: config context

OpenSpec can inject short project facts into every planning session via openspec/config.yaml. That file is a safety net: even if the agent did not explore the repo, planning artifacts still mention the real stack.

Your Task

Create or edit openspec/config.yaml so ShopLite’s constraints are always visible.

schema: spec-driven

# Shown to the AI when it plans and implements.
context: |
  ShopLite is Nile Retail's teaching store (mini-Amazon).
  Stack: Python 3.11+, FastAPI, vanilla HTML/CSS/JS (no React).
  Run with: uvicorn app.main:app --reload --port 8000
  Persist data in a local JSON file or SQLite — keep it simple.
  Do not add real payment processors. Checkout is a mock "Place order".
  One intent per change. Prefer small, reviewable deltas.
  Specs describe what a shopper or staff member can see, not framework choices.
  Every scenario in a spec SHALL have one automated test.
  The test name includes the scenario title.
  A scenario with no passing test is not done.

If init already created a config, merge these ideas into it rather than deleting unknown keys.

This file replaces the paragraph you used to paste

In a homemade prompt you might write “We use FastAPI, no React, port 8000” at the top every time. If you forget, the assistant may build a different stack. The context: block is that paragraph. OpenSpec shows it to the assistant when it plans and when it writes code. It is not the spec. The spec still says what the shopper can see. The last lines tell the assistant our class rule: one automated test for each scenario, and the test name includes the scenario title.

9. Upgrade path (bookmark this)

When a new OpenSpec version ships:

npm install -g @fission-ai/openspec@latest
cd shoplite
openspec update

The first line upgrades the machine CLI. The second refreshes this project’s generated skills/commands. They are not the same step.

10. Confirm chat commands

Your Task

Open Cursor (or your agent) on the shoplite folder. In a new chat, type the prefix below and confirm the commands appear. Do not run propose yet.

/opsx

You want to see at least explore, propose, apply, archive. If nothing appears:

  1. Confirm you opened the shoplite folder as the workspace root (not a parent directory).
  2. Run openspec update.
  3. Reload the window.
  4. On skills-only tools (e.g. Codex), /opsx may never autocomplete — use that tool’s skill name from init’s printed instructions.

11. Optional: AI-assisted sanity check

In chat you may ask (this is a normal prompt, not an OpenSpec command):

What OpenSpec files exist in this project? Summarize the folder layout.
Do not create a change and do not write application code.

You should get a tour of openspec/ and the agent folders. If the agent starts building a store, stop it. We are still in setup.
