08 · Expanded Workflow: Order Lifecycle

When one propose is too much to review, write the plan one file at a time. Each status change still needs a scenario and a test.

Lesson 08 of 10 ~90 minutes new / continue / ff / verify
CatalogSearchCart CheckoutOrdersInventory
What you will do
  • Recognize when core propose is not enough.
  • Switch to the expanded command set.
  • Build Amazon-like order status (placed → packed → shipped → delivered) with new + continue.
  • Use verify before archive, and know when ff is acceptable.
The extra commands are pauses between files

In the usual workflow, propose writes the whole plan in one go. That is fine when the change is small. For order status, I would not write the reason, the rules, the design, and the tasks without stopping to look. I would stop after the status diagram. The extra commands are that habit, written down.

OpenSpec calls the pipeline a schema. The default one is named spec-driven. It says which files exist, and which file has to exist before the next one. The commands are moves on that list:

CommandWhat it doesBy hand
newCreate the folder. No documents yet.mkdir changes/add-order-status-lifecycle
continueWrite the next file the list allows, then stop.“Write only the proposal, then show me.”
ffKeep writing until the plan is ready to build.Propose, all at once
verifyCheck the code and the tests against the spec.The checklist you would run before you file the change

openspec config profile and openspec update only install extra instruction files. The openspec/ folders do not change. You are choosing which commands show up when you type /opsx.

Think

Why can’t continue write tasks.md before the spec exists? Because a task list with no behavior is a random checklist. The spec has to come first, for the same reason you would not estimate the work before the rules have names.

1. When the core workflow is not enough

Core workflow (propose → apply → archive) generates all four planning artifacts at once. That is perfect when you could have written the propose prompt in one breath.

Order tracking is not that. Interlocking decisions include:

  • Which statuses exist, and which transitions are legal.
  • Who can change status (shopper vs Nile staff — we will fake an admin action).
  • Whether the shopper can cancel, and until which status.
  • How this relates to checkout’s confirmation (an order already exists).
  • Whether cancelled orders still show in history.

If you dump all of that into one propose, the specs, design, and tasks are generated from a half-wrong proposal. Review gates exist so you catch a bad status model before tasks.md is written on top of it.

2. Expanded commands

CommandCursor spellingPurpose
/opsx:new/opsx-newCreate the change folder; do not draft artifacts yet
/opsx:continue/opsx-continueCreate the next artifact; stop for review
/opsx:ff/opsx-ffFast-forward: write all remaining planning artifacts
/opsx:verify/opsx-verifyCheck implementation vs artifacts (completeness, correctness, coherence)
/opsx:bulk-archive/opsx-bulk-archiveArchive several completed changes; conflict-aware
/opsx:onboard/opsx-onboardGuided tour of the workflow on a codebase

continue vs ff:

SituationUse
Clear remaining scope, time pressureff
You want to inspect the proposal before specs existcontinue
Complex domain, first time through expanded modecontinue (required in this lesson)

Rule of thumb: if you can describe the full remaining scope with confidence, ff is fine. If you are still figuring it out, continue.

3. Switch profile

Your Task

In the terminal, enable expanded workflows, then refresh this project’s generated commands.

openspec config profile

Choose the custom/expanded set so that new, continue, ff, verify, bulk-archive, and onboard are included. Keep the core commands too. Then: 

cd path\to\shoplite
openspec update

Reload the editor. Type /opsx and confirm the new commands appear. If config profile is a TUI you cannot drive here, this equivalent often works (check openspec config --help on your version):

openspec config --help
openspec update

Look under .cursor/ or .claude/commands/opsx/ for new, continue, verify files after update.

4. Scaffold the change

Your Task

New chat. Create the change without generating artifacts.

/opsx-new add-order-status-lifecycle

Create the change named add-order-status-lifecycle.
Do not write proposal.md yet. Wait for continue.

You should have an empty-ish folder openspec/changes/add-order-status-lifecycle/ (maybe only metadata). If the agent jumped ahead and wrote everything, that is ff behavior — still pause and review the proposal as if you had gates.

5. Continue: proposal, then stop

/opsx-continue

Write only the proposal for ShopLite order lifecycle (Amazon "Your Orders", tiny).

Intent: after Place order, the shopper can see the order and its status.
Nile staff (a simple admin action on the same machine is enough) can move status forward.

Statuses: placed → packed → shipped → delivered.
Cancel is allowed only from placed or packed, not after shipped.
Shopper can view a list of their orders (browser-persisted or server-persisted — pick in design later).

Out of scope: carriers, email notifications, returns, refunds, multi-user auth, changing line items after place.

Read checkout specs so we extend existing orders rather than inventing a second order model.
Your Task — review gate 1

Read proposal.md. Fix status names if the AI added “out_for_delivery” or skipped packed. Confirm cancel rules. Only then continue.

6. Continue: specs, then stop

/opsx-continue

Write delta specs only. Include:
- Order list and detail show status
- Legal transitions only
- Cancel rules
- Delivered is terminal
- Cancelled is terminal
- Unknown transition is rejected without corrupting the order

Scenarios for: happy path to delivered; cancel from placed; reject cancel after shipped; reject skipping packed.
End the spec with the test requirement below, unless the orders spec already has it.
If it is already there, do not add a second copy. Still give each new scenario a test task.
### Requirement: Test for each scenario
The project SHALL include one automated test for each scenario in this spec.
The test name SHALL include the scenario title.
The test SHALL fail when that scenario's THEN is not met.
Your Task — review gate 2

Check delta type: this is mostly ADDED on an orders capability. If checkout already defined an order as “confirmation page only,” you may need a MODIFIED requirement — only if a named requirement is actually changing. Do not MODIFIED a requirement that does not exist.

State-machine check: draw the statuses on paper. Every arrow should have a scenario. A missing arrow is a missing spec. Every scenario should have a test task.

placed ──► packed ──► shipped ──► delivered
   │          │
   └── cancel ┘
shipped/delivered: cancel REJECTED

7. Continue: design, then tasks

/opsx-continue

Write design.md only: how we store orders, how we expose shopper vs admin actions
(a hidden /admin/orders page or a status dropdown in teaching mode is fine).
No new frameworks. Persist orders so they survive refresh (JSON or SQLite).

Review: if design invents JWT auth, cut it. Then:

/opsx-continue

Write tasks.md as small checkboxes covering list, detail, transitions, cancel, persistence.

If you are comfortable after specs, you may /opsx-ff to generate design+tasks together. This lesson prefers continue so you feel the gates.

8. Apply, then verify

/opsx-apply add-order-status-lifecycle

Manual path:

  1. Place an order from checkout.
  2. Open “Your orders” (whatever the UI called it).
  3. Status starts at placed.
  4. Advance placed → packed → shipped → delivered.
  5. Place a second order and cancel it from placed.
  6. Try to cancel a shipped order — must fail.
  7. Restart the server — orders still there if you specified persistence.
Your Task

Run verify. It is not a hard gate on archive, but it is the expanded workflow’s quality check.

/opsx-verify add-order-status-lifecycle

Verify typically reports three dimensions:

DimensionMeaning
CompletenessTasks ticked; requirements have code; each scenario has a test whose name includes the scenario title
CorrectnessBehavior matches spec intent and edge cases
CoherenceDesign decisions show up in the code (or design should be updated)

Treat warnings as work. A scenario “cancel after shipped” with no test is useful information. Add the test, or fix the code so the test can pass. If the design said one approach and the code does another, change the code or change the design. Do not leave them disagreeing.

9. Specification silence during verify

You may discover unspecified behavior: can a delivered order be returned? We said returns are out of scope. If the UI still shows a Return button, that is extra. Remove it or specify it as a future change — do not let verify pressure you into building Amazon Returns in the last ten minutes.

If a status was implemented that is not in the spec, that is drift in the other direction. Align them.

10. Archive and look at the suite

/opsx-archive add-order-status-lifecycle

Optional: /opsx-sync first if archive asks. Then browse:

openspec view
openspec list

You now have catalog, search, cart, checkout, and orders. That is a real (tiny) store spec suite. Point at it: this is what a new teammate would read on day one.

11. ff on a small leftover (optional)

If you want to feel the fast path in expanded mode, pick a tiny, clear leftover (e.g. show order date on the list) only if it is truly small:

/opsx-new add-order-placed-timestamp
/opsx-ff
# review quickly
/opsx-apply
/opsx-verify
/opsx-archive

Do not use ff to skip review on the lifecycle itself.

12. Spec drift (preview)

After archive, if someone hotfixes a fifth status in code and never updates specs, the suite becomes a liar the next agent will read. Lesson 10 treats drift as a first-class problem. For now: if you changed behavior while applying, update the artifacts before archive, or use /opsx-update.

13. Common issues

SymptomFix
