05 · Explore and Specify: Search

If you cannot yet say the change in one sentence, talk it through first. Then write the search spec, and a test for each scenario.

Lesson 05 of 10 ~70 minutes Explore + RFC 2119
CatalogSearchCart CheckoutOrdersInventory
What you will do
  • Use /opsx:explore as a no-stakes thinking partner.
  • Turn a fuzzy “we need search” into scoped requirements.
  • Write and review Given / When / Then scenarios, including a search with no results.
  • Make sure the spec asks for one test per scenario, then propose, apply, and archive search on top of the catalog.
Why the thinking step writes no files

The important line in this command is: do not create a change folder, and do not write shop code. The assistant may read the project, compare options, and sketch ideas in chat. The moment those ideas land in proposal.md, they start to look like decisions.

That is why you start a new chat before propose. Take the one-sentence plan with you. Leave the options you already rejected in the old chat. The slash command only sets the assistant’s job. Starting a clean chat is still your habit.

Search is a good feature for this lesson. “Search like Amazon” can grow into a huge system. This step is where we shrink it to a box that filters product names, before propose writes a ranking platform we do not want.

Think

Could you fake explore with a normal chat that says “don’t write files”? Yes. The value of the command is that every teammate’s agent loads the same “don’t write files” skill, instead of a prompt people forget to paste.

1. Why explore exists

In lesson 04 the ticket was clear. Real work often starts as a worry: “shoppers will not find anything if we get more than six products.” That is not yet a change. If you propose too early, the AI will invent a design (Elasticsearch, filters, autocomplete, “people also buy”) because Amazon has those things.

Explore

/opsx:explore reads the codebase, compares options, and sharpens a fuzzy idea. It creates no change folder and writes no production feature. When the picture is clear, you switch to propose in a cleaner chat.

Use explore when:

  • You cannot state the change in one sentence.
  • Several implementations could work and you have not chosen.
  • You need to know how the current catalog actually stores products.

Skip explore when the intent, scope, and out-of-scope are already obvious — like lesson 04.

2. Explore the catalog you already have

Your Task

New chat. Start explore (Cursor: /opsx-explore).

/opsx-explore

Shoppers will need to find products by name, like Amazon's search bar.

Please inspect the current ShopLite catalog (code + openspec/specs).
I am NOT asking you to build yet.

Help me decide:
1. Where products live today (file, API, HTML).
2. The smallest search that still feels like amazon.com: a single query box that filters the catalog.
3. What we should explicitly NOT build (autocomplete, facets, ranking ML, search-as-you-type).
4. Edge cases: empty query, no matches, case differences, extra spaces.

End with a one-sentence propose statement I could paste into /opsx-propose.

Read the answer. Push back if it recommends Elasticsearch for six products. ShopLite should filter in the app (query parameter on the existing list API, or equivalent).

Start a clean chat before you propose

Explore chats are messy on purpose. When you are ready to propose, start a new chat. Take with you only the one-sentence intent plus the edge cases you care about — not the three discarded architectures.

3. What “good search” means here

Amazon search is a company. ShopLite search is a box. Be explicit so the spec cannot balloon.

In scopeOut of scope
A search box on the home page Autocomplete / typeahead
Filter by name (case-insensitive, trim spaces) Search inside reviews, “customers also bought”
Show matches; show a no-results message Facets (brand, price slider), sort by relevance ML
Clearing the query restores the full catalog Separate search index, Elasticsearch, typo-tolerance engine

4. Propose from a clean window

Your Task

New chat. Propose. Paste a tight prompt; do not paste the entire explore transcript.

/opsx-propose add-product-search

Add a catalog search box to ShopLite (Amazon-like find-a-product, tiny).

Behavior:
- Home page has a search box.
- Submitting a query shows only products whose name contains the query, case-insensitive, ignoring surrounding whitespace.
- Empty query (or clear) shows the full catalog.
- Zero matches: a message that no products matched, and the shopper can search again.
- Search does not create a new product database.

Out of scope: autocomplete, facets, ranking, cart, spelling correction, accounts.

Read existing openspec/specs/catalog so the delta fits the current catalog.
Name the change add-product-search.
Every scenario needs one automated test. The test name includes the scenario title.
The spec must say that. tasks.md must list those tests.

5. Review the artifacts like a spec author

Your Task

Open the change folder and walk each artifact. Use this checklist.

5.1 Proposal: four parts of a useful “why”

  1. Intent — shoppers can find a product by name.
  2. Scope — box + filter + empty states.
  3. Out of scope — autocomplete, facets, cart.
  4. Approach — one sentence, not a framework dump.

If any of those four is missing, add it before apply.

5.2 Specs: requirements you could test

Reject these if they appear:

  • “Search SHALL feel fast and intuitive.”
  • “Use SQL LIKE in SQLite.”
  • A requirement that also adds filters by category (scope creep).

Insist on scenarios like:

#### Scenario: Match ignores case
- GIVEN a product named "USB-C Cable"
- WHEN the shopper searches for "usb-c"
- THEN that product is included in the results

#### Scenario: No matches
- GIVEN the catalog has products
- WHEN the shopper searches for a string that matches no name
- THEN the page explains that no products matched
- AND it does not show unrelated products as if they matched

#### Scenario: Empty query
- GIVEN the shopper has filtered the list
- WHEN the shopper submits an empty query (or clears search)
- THEN the full catalog is shown again

### Requirement: Test for each scenario
The project SHALL include one automated test for each scenario in this spec.
The test name SHALL include the scenario title.
The test SHALL fail when that scenario's THEN is not met.

Delta type: search is new behavior. You should see ## ADDED Requirements, probably under a new search capability (or added onto catalog — either can be valid). Prefer a separate search spec if the files went that way; do not fight the AI if catalog grew a search requirement as long as archive will stay readable.

5.3 Design vs spec

Query strings, GET /api/products?q=, and client-side filter belong in design.md. If they leaked into the spec, move them. The spec should still be true if you later switch from client filter to server filter.

5.4 Tasks

You want small checkboxes: add the input, wire the query, the empty state, keep the catalog listing intact, and one test per scenario. If one task says “implement search,” split it with /opsx-update.

Your Task

Make at least one improvement to the generated specs (add a missing scenario, split a fat requirement, or delete an implementation SHALL). Then, if you used the agent to edit, skim design and tasks for consistency.

6. Apply, run, archive

Your Task

New chat. Apply, then click through the running app.

/opsx-apply add-product-search

With the server running:

  1. Search lamp — only matching items.
  2. Search LAMP — same matches (case-insensitive).
  3. Search zzzz-no-product — no-results message.
  4. Clear / empty search — full grid returns.
  5. Open a result’s detail page — still works (catalog spec still holds).
/opsx-archive add-product-search

Confirm openspec/specs/ now includes search behavior (its own folder or merged into catalog).

7. Cross-spec thinking

You now have more than one spec. Search must not break catalog’s “list all available products” — except when a query is active. If those two requirements fight, that is a spec bug, not a CSS bug. We will hit a louder version of this in checkout (lesson 07).

Optional CLI:

openspec validate --all
openspec view

8. Challenge (optional)

Challenge

Decide whether searching by description as well as name is in scope. If you want it, do not silently “just code it.” Either update the change before archive, or create a tiny follow-up change search-matches-description after archive. Practice the rule: behavior changes go through specs.

9. Common issues

SymptomFix
Explore started writing filesStop. Explore should not create a change. Copy the one-sentence intent and propose in a new chat.
Agent added ElasticsearchReject in design review. Update artifacts: in-process filter only.
Empty search shows no productsSpec gap or impl bug. If the spec never said empty query = full catalog, add it, then apply.
Search is a new page that hides navigationFine if specified; if not, it drifted. Align with “box on the home page.”
