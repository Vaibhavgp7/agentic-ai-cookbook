What is still worth installing

You could rebuild most of OpenSpec in a weekend: folders, four Markdown files, four instruction files, and a short program that copies rules by their headings. I want you to believe that. People still install it for a few reasons:

  • Shared words — teammates, and you next month, do not each invent a different prompt.
  • Many tools — init writes the Cursor spelling, the Claude spelling, and the Copilot spelling from one setup.
  • A careful copy — a wrong heading fails loudly, instead of quietly leaving two SHALL lines that disagree.
  • The extra pauses — continue, ff, and verify, without each team inventing its own.
  • A separate planning repo — later, if one feature spans several code repos. You do not need that yet.

Drift is what happens when you treat the tool as a draft generator and then fix the code on Friday without touching the spec. The tool will not stop you. For a team, the pull request should contain both products: the app and the spec, and the tests that match the scenarios.

Think

If your company banned extra command-line tools, what would you still keep from this course? The folders, the habit of reading the plan, a messy chat before you decide, skipping the process for a typo, and a test for each scenario. If the answer is “almost everything,” the tool did its job. It taught a way of working.

1. You already built two products

ShopLite is a small amazon.com. Beside it sits a second product: the spec suite. The suite outlives any chat.

Your Task

Walk the archive. You should be able to tell the story of the store from folder names alone.

dir openspec\changes\archive
dir openspec\specs

A healthy history looks like: catalog → search → cart → checkout → orders → inventory. That is how you explain Nile Retail to a new hire — or to a new model next year.

2. Spec drift

Drift is when code and specs disagree. The next agent will read the spec and “fix” the code back, or will read the code and ignore the spec. Either way you lose the contract.

How drift happens on a store:

  • Hotfix: shipping waiver raised to 75 in code on Friday; specs still say 50.
  • Partial apply: tasks 1–3 done, 4–7 forgotten, then someone archives anyway.
  • Two active changes both edit specs/cart/ and archive in the wrong order.

Invariant to protect: at commit boundaries, specs and code tell the same story. A PR should include archived (or still-open but consistent) spec updates next to the diff.

Your Task — detect a lie

Temporarily break the invariant on purpose: change the shipping waiver in code to 75 without touching specs. In a new chat ask: “What is the free-shipping threshold?” If it cites 50 from specs, you just saw why drift is dangerous. Revert the code (or immediately start a tiny change to MODIFIED the requirement). Do not leave the lie.

3. Sync, archive, bulk-archive

MoveMeaning
/opsx:sync Merge this change’s delta into openspec/specs/ without necessarily filing the folder away.
/opsx:archive File the change under changes/archive/; usually offers sync if needed.
/opsx:bulk-archive Several completed changes at once. Detects two changes touching the same spec and applies in a sensible order.

CLI archive (non-interactive):

openspec archive change-name --yes

Parallel work is allowed: you can have add-reviews and fix-tax-rounding open together. Keep each focused. If both touch checkout specs, talk to each other before bulk-archive.

When to update a change vs start a new one:

  • Update — same intent, narrower MVP, you learned the codebase was different.
  • New change — intent changed, scope exploded, original work could ship without the extra.

4. CLI you should actually use

openspec --help
openspec list
openspec show add-inventory-availability
openspec validate --all
openspec status
openspec view
openspec doctor
openspec update

Agents also call some of these with --json. You do not need that daily. You do need validate when Markdown headings drifted from the expected ADDED/MODIFIED/REMOVED shape.

Other CLI families (know they exist; do not require them for ShopLite):

  • openspec schema ... — custom workflows.
  • openspec store ... — planning repo shared across code repos (beta).
  • openspec workset ... — personal working views.
  • openspec config — language, profile, telemetry.

5. Brownfield: existing projects

OpenSpec’s sweet spot is incrementally improving a codebase that already exists. You do not retro-spec all of amazon.com. You init, write a short config.yaml context, and spec the next change. The suite grows where it hurts. 

cd existing-app
openspec init --tools cursor
# edit openspec/config.yaml context: stack, how to run tests, what not to touch
# then /opsx-explore the one feature you will change this sprint

/opsx:onboard (expanded profile) walks a complete change on your own repo while narrating. Use it once on a scratch branch of a real project this week.

Your Task

Pick a real repository you work on (not ShopLite). Write five bullets: (1) where you would run init, (2) which AI tool, (3) the first change name in kebab-case, (4) whether that change is core propose or expanded, (5) one change you would not write a spec for. You do not have to run it during class.

6. Teams and pull requests

A change maps cleanly onto a branch:

git checkout -b change/add-product-reviews
# propose → review → apply → verify
# commit code AND openspec/ files together
# open PR: reviewers read proposal.md + delta specs, then the diff

Reviewers often catch product issues faster in the spec than in Python. Require spec review for behavior changes the same way you require tests for regressions.

Tooling is not a lock-in: Claude Code, Cursor, Copilot, Codex all share the same openspec/ files. Only the slash spelling differs.

7. Stores (beta) and customization

When one feature spans api-server, web-app, and a mobile repo, a store is a dedicated planning repository with the same openspec/ shape, shared via git. Platform teams can own specs; product teams consume them. Start with the Stores user guide when you actually have that problem — not before.

Customization: config.yaml context, artifact language, custom schemas, community schema bundles. Default spec-driven is enough until your org’s workflow is genuinely different.

Multi-language: you can generate artifacts in a language other than English via init/config. Specs still need the same precision.

8. Comparison recap (for the skeptic at work)

QuestionShort answer
Isn’t this just documentation?Docs describe the past. Specs are a contract upstream of code, consumed by agents.
Isn’t this Jira?Stories are requests in a tracker. Specs live in git and are executable context.
Do I spec every change?No. You fixed a typo without a spec. Behavior changes still get a scenario and a test.
Does this lock us to Cursor?No. 30+ tools. Files are portable.
Can we use it without AI?Yes. The Markdown still helps humans. AI is acceleration.

9. Recommended default rhythm at work

Unsure what to build?     /opsx:explore     then new chat
Know the change?          /opsx:propose     (core)
Too many decisions?       /opsx:new + continue (expanded)
Trivial presentation?     just edit the code
Done and true?            /opsx:verify? then archive
Friday hotfix to specs?   tiny change or honest spec edit in the same PR

One line for chats: think in a messy chat, propose in a clean chat, apply while you stay on the task list, archive only when the spec is true.

10. Capstone (do this to graduate)

Your Task — independent feature

Without copying a prompt from this course, add one of the following to ShopLite using the workflow you now choose (core or expanded). Keep it one intent.

  • Product reviews: 1–5 stars + text, listed on detail; no moderation queue.
  • Order receipt page: printable summary that reuses checkout math (watch spec dependencies).
  • Simple category filter (distinct from search): e.g. Electronics vs Home.

Definition of done:

  1. Change named in kebab-case.
  2. Artifacts reviewed (you edited at least one thing).
  3. App demonstrates the scenarios, and each scenario has a passing test whose name includes the scenario title.
  4. Archived; main specs tell the truth.
  5. You can explain whether you used explore, continue, or no spec at all, and why.

12. What “ready to work” looks like

You are done with this course when you can do the following without the HTML open:

  1. Install and init OpenSpec on a repo.
  2. Explain specs vs changes vs archive to a teammate in two minutes.
  3. Drive explore / propose / apply / archive (and expanded gates when needed).
  4. Reject a vague SHALL and a spec that names a framework.
  5. Trace a bad total to a missing scenario, then add the scenario and its test.
  6. Write a MODIFIED delta when behavior changes.
  7. Skip the workflow for a one-line fix, on purpose.
  8. Keep specs in the same PR as code.
