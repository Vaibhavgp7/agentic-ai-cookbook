09 · Spec Evolution: Inventory

Shops do not only grow. Sometimes a rule changes. A one-word typo still does not need this whole process. When a rule does change, each new scenario still needs a test.

Lesson 09 of 10 ~80 minutes MODIFIED / REMOVED / skip a typo
CatalogSearchCart CheckoutOrdersInventory
What you will do
  • Fix a tiny UI typo without OpenSpec (judgment).
  • Write MODIFIED and REMOVED deltas so the catalog tells the truth about stock.
  • Draft a proposal and delta specs by hand, then let the AI implement.
  • See the spec suite as persistent context across sessions.
Archive copies rules by their headings

ADDED, MODIFIED, and REMOVED tell the copy step what to do with each rule. On archive, the program should:

  • ADDED — add the new rule to openspec/specs/…/spec.md. Create the file if it is missing. Keep ## Purpose if you wrote one.
  • MODIFIED — find the rule with the same title and replace the whole block with the new text.
  • REMOVED — delete that rule. If a whole area of the shop would become empty, retiring the file is a separate, explicit step. We will not do that to the catalog.

If you mark a change as ADDED when that title already exists, the spec ends up with two rules that disagree. If you mark a brand-new title as MODIFIED, there is nothing to replace. We write the inventory spec by hand so you feel those rules before you trust a draft.

Skipping OpenSpec for a typo is a judgment call, the same one from lesson 01. You can skip the process for one change. Once a behavior is promised in the spec, that promise stays until you change it on purpose. A new or changed scenario still needs a test.

Think

Catalog used to say “list every product as for sale.” Stock changes that sentence. Why is that MODIFIED rather than a new spec file called inventory only? (You may still ADD stock quantity somewhere — but the old listing rule must not remain, or archive leaves a lie.)

1. When this process is too much

Lesson 01 promised we would not spec every keystroke. Amazon.com has thousands of copy tweaks a year. OpenSpec would be theatre for “Nile Retial” → “Nile Retail.”

Your Task — fix without a spec change

Find a purely presentational issue: a heading typo, extra padding, a footer line, button label “Add to Basket” vs “Add to Cart.” In a normal chat, do not run propose. Tell the agent: 

Fix the typo / label on the home page heading (describe the exact string).
Do not create an OpenSpec change. Do not edit openspec/specs.
This is a presentation-only fix.

Heuristic you should now feel in your bones:

Would this update openspec/specs/?
  Yes → use the workflow
  No  → just make the change

If you are unsure, ask: “would a future agent need this fact to behave correctly?” Typos, no. Out-of-stock rules, yes.

2. Inventory changes existing behavior

Until now almost every delta was ADDED. Inventory is different:

  • The catalog currently lists products as if they are always for sale.
  • The cart currently allows adding without asking about stock.
  • Amazon shows “Currently unavailable” and blocks add-to-cart. We want a teaching-sized version of that.

That is not a new island of behavior. It modifies catalog and cart contracts.

2.1 ADDED vs MODIFIED vs REMOVED

SectionUse whenArchive effect
## ADDED Requirements Brand-new behavior (stock count exists; unavailable message) Appended to the main spec
## MODIFIED Requirements A named requirement already exists and its rules change (e.g. “list every product” becomes “list available; mark unavailable”) Replaces the old requirement text
## REMOVED Requirements A behavior is going away (e.g. if you had “always show Add to cart”) Deleted from the main spec

MODIFIED must include the full new requirement, not a diff hunk. Copy the old requirement, edit it, put it under MODIFIED, and add a one-line note of what changed.

If you REMOVE the last requirement in a capability, archive may need to retire the whole spec file. That is an advanced edge (sometimes retire_capabilities: true in the change’s YAML). We will not retire catalog.

3. Identify what the current specs assume

Your Task

Search the spec suite for assumptions that stock will break.

openspec view

Or in the editor, search openspec/specs for phrases like “every product,” “add to the cart,” “available.” Write down the exact requirement titles you will MODIFIED.

Typical findings:

  • Catalog: home lists each product — does that include quantity 0?
  • Cart: add from detail always succeeds.
  • Checkout: no mention of stock going to zero between add and place order. We will keep that simple: check stock at add-to-cart and at place-order; if place-order fails, say why and leave the cart.

4. Write the change by hand

Generating specs is convenient. Writing one by hand teaches you what the AI has been producing — and usually produces the reaction “that is more thought than I expected.” Good.

Your Task

Create the folder structure yourself (terminal or editor). You may use /opsx-new add-inventory-availability to scaffold, then replace generated files with your writing. Or create files with no AI at all.

openspec/changes/add-inventory-availability/
  proposal.md
  design.md
  tasks.md
  specs/catalog/spec.md
  specs/cart/spec.md
  specs/checkout/spec.md   # only if you change place-order rules

4.1 proposal.md (write this)

# Proposal: add-inventory-availability

## Intent
Shoppers should not be able to buy products Nile Retail cannot ship.
Unavailable products are still visible (like Amazon's "Currently unavailable")
but cannot be added to the cart.

## Scope
- Each product has an integer stock quantity in seed data.
- At least one seed product starts at 0 so we can demo the state.
- Catalog shows an unavailable state when stock is 0.
- Add to cart is rejected when stock is 0.
- Place order is rejected if any line's quantity exceeds current stock.
- Successful place order reduces stock by the purchased quantities.

## Out of scope
- Warehouse locations, backorders, restock emails, admin stock UI beyond editing JSON/seed,
  overselling protection under concurrency, marketplace sellers.

## Approach
Keep the existing stack. Store stock next to product records. Enforce rules in the
same layer that already mutates the cart and orders.

4.2 Catalog delta (pattern)

Open the live openspec/specs/catalog/spec.md. Copy the requirement that says you list products. Put the new full text under MODIFIED. Example shape (adapt to your real titles):

# Delta for Catalog

## MODIFIED Requirements

### Requirement: Home catalog
The system SHALL list each product that Nile Retail carries, including
products with zero stock.
When stock is zero, the listing SHALL indicate the product is unavailable.
(Previously: listed products as available for sale without a stock concept.)

#### Scenario: In-stock product
- GIVEN a product with stock greater than 0
- WHEN the shopper views the catalog
- THEN the product is listed without an unavailable marker

#### Scenario: Out-of-stock product
- GIVEN a product with stock 0
- WHEN the shopper views the catalog or detail page
- THEN the product is visible
- AND it is marked unavailable
- AND the shopper is not offered a working add-to-cart action

## ADDED Requirements

### Requirement: Stock quantity
Each product SHALL have a non-negative integer stock quantity.

#### Scenario: Seed data
- GIVEN the default ShopLite catalog
- WHEN products are loaded
- THEN each product has a stock quantity
- AND at least one product has stock 0

4.3 Cart delta (pattern)

# Delta for Cart

## MODIFIED Requirements

### Requirement: Add to cart
The system SHALL add a product to the cart only when stock is greater than 0.
(Previously: add always succeeded for any listed product.)

#### Scenario: Add in-stock
- GIVEN a product with stock greater than 0
- WHEN the shopper adds it to the cart
- THEN the product appears in the cart

#### Scenario: Reject out-of-stock add
- GIVEN a product with stock 0
- WHEN the shopper attempts to add it
- THEN the cart does not gain that product
- AND the shopper is told it is unavailable

## ADDED Requirements

### Requirement: Quantity cannot exceed stock
The system SHALL not allow a cart line quantity greater than current stock.

#### Scenario: Cap at stock
- GIVEN a product with stock 2
- WHEN the shopper tries to set quantity to 3
- THEN the quantity remains at most 2
- AND the shopper is told why

4.4 Optional REMOVED

Only if you literally had a requirement like “Add to cart is always shown.” Then:

## REMOVED Requirements

### Requirement: Always-available add action
(Replaced by stock-aware add; unavailable products must not offer a working add.)

Do not REMOVE things you never wrote. Fake REMOVED sections confuse archive.

4.5 design.md and tasks.md

Keep design short: where stock lives, which requests check it, and how you seed one item with zero stock. Tasks: seed stock, catalog page, block add, cap quantity, lower stock when an order is placed, the failed-order message, and one test for each new scenario.

The living specs from earlier lessons should already contain “Test for each scenario.” Do not add that requirement a second time. ADDED would leave two copies. The new scenarios are already covered by that rule. What you add now is a task, and later a test, for each new scenario. If a brand-new spec file has no such requirement yet, add it once.

5. Ask the AI to review your hand-written specs

You wrote them, so they will miss scenarios. That is expected. Now use the agent as a reviewer, not an author.

Review openspec/changes/add-inventory-availability/ as a spec reviewer.
Do not implement yet.
List missing scenarios, missing tests, wrong delta types (ADDED vs MODIFIED), and any
contradiction with openspec/specs/. A scenario with no test task is a gap.
Propose edits; wait for my approval.

Accept the useful gaps. Reject new scope (warehouses, backorders).

If you are in expanded mode you can still /opsx-update after you approve edits. If core-only, just edit files.

6. Implement and archive

/opsx-apply add-inventory-availability

Manual checks:

  1. A zero-stock product is visible and marked unavailable.
  2. Add to cart fails for it.
  3. An in-stock product still adds.
  4. Line quantity cannot exceed stock.
  5. Place order reduces stock; a second order that would oversell is rejected.
  6. Search still finds the unavailable product (unless you specified otherwise — Amazon does show them).
  7. The tests pass, and each new scenario title appears in a test name.
/opsx-verify add-inventory-availability
/opsx-archive add-inventory-availability

Open the main catalog spec. The old “everything is for sale” language should be gone, replaced by your MODIFIED text. If both old and new exist, you used ADDED when you needed MODIFIED — fix the main spec so it does not lie, and remember the lesson.

7. The spec suite is the product

Your Task

Start a brand new chat. Ask:

Do not read our previous conversation (there isn't one).
Using only openspec/specs/, summarize how ShopLite handles:
catalog, search, cart, checkout totals, orders, and stock.
Cite requirement titles.

If the summary is accurate, your suite is doing its job as persistent context. If the agent invents Amazon Prime, the specs are still too thin — or you did not point it at openspec/specs/.

8. Challenge (optional)

Amazon also shows “Only 2 left in stock.” Add a SHOULD (not MUST) requirement: when stock is 1–5, show a low-stock hint. SHOULD means a justified exception is allowed — good practice using RFC 2119 strength on purpose.
