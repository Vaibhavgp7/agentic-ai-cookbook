07 · Apply and Debug: Checkout

When the total looks wrong, open the spec before you open the code. Then write a test for the rule you were missing.

Apply follows the folder, not your first sentence

Apply does not start over from “make it like Amazon.” It treats the change folder as the only description of the work. If tax is vague, and a task says “show tax,” the assistant will still invent a number. A careful apply of a vague spec is how you get a surprising total. When that happens, go back to the spec. Do not start by poking at the page.

/opsx:update rewrites the related files so they still agree. Then you apply again, and the new tasks include a test for each new scenario. By hand you would edit the spec, fix the task list, and say “do the new tax tasks only.”

Checkout has to use the cart subtotal you already wrote down. That only works if the assistant reads openspec/specs/. The project context from lesson 02 helps. Pointing at the files is still your job.

Think

Why must merge/archive wait until the tax rule is written down? If you archive a vague spec, the next agent inherits the guess as truth. Archive is how silence becomes “company policy.”

1. How apply works

When you invoke apply, the agent is supposed to read three things — not improvise from chat vibes:

  1. tasks.md — ordered checklist. Work sequentially, tick boxes.
  2. specs/ (the change’s delta) — what the code must do.
  3. design.md — how to structure the code.

Clear specs produce correct implementations. Vague specs produce confident assumptions. Checkout is where money math makes that painful, the same way a coffee receipt with mystery tax does in other courses.

Apply does not invent a new plan. If the plan is wrong, apply will faithfully build the wrong store.

2. Dependent changes

Checkout is not a green field. It must use the cart subtotal you already specified. Before proposing, feed the agent the existing specs on purpose. That is cross-spec referencing.

Your Task

Skim openspec/specs/cart/spec.md (path may vary). Note the exact words for line subtotal and cart subtotal. Checkout must not redefine those formulas differently.

3. Propose checkout — with a deliberate hole

We will not fully specify tax in the first prompt. That is on purpose. You need to feel the “oh, the spec was incomplete” moment. This is not sloppy teaching; it is the debugging lesson.

Your Task

New chat. Propose. Then apply in a later chat after a reasonable review — but do not add tax rules even if you notice they are thin. Leave the hole.

/opsx-propose add-checkout

Add ShopLite checkout, analogous to Amazon's place-order step (mock payment only).

Please read openspec/specs/cart (and catalog) before drafting.

In scope:
- From the cart, the shopper can start checkout if the cart is not empty.
- Checkout collects a shipping name, address line, city, and postal code (all required).
- The order summary shows: cart subtotal (MUST match the cart spec), a shipping charge, a tax amount, and a grand total.
- Shipping is a flat fee. Tax is a percentage of something — use a simple teaching rule.
- Place order simulates payment success, empties the cart, and shows a confirmation with an order id and the same money breakdown.
- Empty cart cannot start checkout.

Out of scope:
- Real payment processors, promo codes, multiple addresses, accounts, order tracking lifecycle (later lesson), inventory.

Change name: add-checkout.

Review as usual for scope creep (accounts, Stripe, 1-Click). You may tighten address fields. Leave tax as whatever the AI drafted if it is vague — we will use that vagueness. 

/opsx-apply add-checkout

4. Reproduce a surprising total

Your Task

Put two different products in the cart. Go to checkout. Write down:

  • Cart subtotal
  • Shipping
  • Tax
  • Grand total

Then answer: tax is a percentage of what? Subtotal only? Subtotal + shipping? Inclusive in prices already? Is rounding half-up to two decimals?

Compare that answer to the spec. In almost every class, one of these is true:

  • The spec never said whether shipping is taxed.
  • The spec said “add tax” with no rate.
  • The spec said 10% but the UI rounds differently from the API.
  • The confirmation page uses a different formula than the checkout page.
The pedagogical moment

The agent did not maliciously break your store. It made a reasonable guess from silence. That guess is now “the product.” If you jump into Python, you might “fix” a number without ever recording the business rule. Next session the agent will guess again.

5. Debug by identifying spec gaps

Use this triage every time behavior surprises you:

QuestionIf yesIf no
Is the surprising behavior forbidden by a SHALL? Implementation bug — fix code (re-apply or targeted patch against the spec). Continue.
Do two specs / two screens disagree? Spec contradiction — pick a winner, MODIFY or clarify, then code. Continue.
Was the rule never written? Spec gap. Write the requirement, the scenario, and a test for that scenario. Then implement. You do not understand the spec yet — re-read before touching code.
Your Task — close the gap in the still-open change

Do not archive yet. Edit the checkout delta specs (by hand or with /opsx-update) so the following teaching rules are explicit. These are Nile Retail rules, not real tax law:

  • Shipping SHALL be a flat 5.00 in store currency, waived when cart subtotal is 50.00 or more.
  • Tax SHALL be 10% of (cart subtotal + shipping after any waiver), rounded half-up to two decimals.
  • Grand total SHALL equal cart subtotal + shipping + tax.
  • Confirmation SHALL repeat the same four numbers; they MUST match checkout.
/opsx-update add-checkout

Replace vague tax/shipping requirements with Nile Retail's teaching rules:
- Flat shipping 5.00, waived at cart subtotal >= 50.00
- Tax = 10% of (subtotal + shipping), round half-up to 2 decimals
- Grand total = subtotal + shipping + tax
- Confirmation repeats the same numbers

Add scenarios:
1) Subtotal 20.00 → shipping 5.00, tax 2.50, total 27.50
2) Subtotal 50.00 → shipping 0.00, tax 5.00, total 55.00

Also include this requirement, and a task for each scenario's test:
### Requirement: Test for each scenario
The project SHALL include one automated test for each scenario in this spec.
The test name SHALL include the scenario title.
The test SHALL fail when that scenario's THEN is not met.

Keep cart subtotal defined by the existing cart spec.
Then update design.md and tasks.md to match.
Do not implement until I run apply.

Read the new scenarios. If the numbers in the spec are internally inconsistent, fix them before apply. If “Test for each scenario” is already in the spec, do not add a second copy. Add a test task for each new scenario.

/opsx-apply add-checkout

Implement the updated tax and shipping tasks. Do not change catalog or search.

5.1 Worked arithmetic

Use a simple cart you can compute by hand (prices that sum cleanly):

Subtotal 20.00
Shipping 5.00          (under 50)
Tax      2.50          (10% of 25.00)
Total    27.50

Subtotal 50.00
Shipping 0.00          (waiver)
Tax      5.00          (10% of 50.00)
Total    55.00

If the UI shows 2.499999 or 2.4, you have a rounding spec/implementation issue. Specify half-up, then fix code.

6. Spec bug vs code bug

ClueLikely kind
Two reasonable developers would disagree what the total “should” beSpec
Everyone agrees the total should be 27.50; the page shows 22.00Code
Checkout and confirmation disagreeOften spec didn’t require them to match; still a spec gap until you say SHALL
Cart subtotal on checkout ≠ cart pageCode, or checkout reimplemented math instead of reusing cart rules

Never “just tweak the template” to hide a wrong total. The confirmation is part of the contract.

7. Place order and empty cart

Your Task

Place an order. Confirm:

  • You see an order id.
  • Cart is empty afterward.
  • Checkout is blocked from an empty cart.
  • Required address fields cannot be skipped (check at least one missing field).

If “empty cart after order” was never specified, you now know why the agent might have left items in the cart. Add it and re-apply. That is the same muscle as tax.

8. Archive when the numbers are boring

Boring numbers mean the contract is doing its job.

/opsx-archive add-checkout

9. When to start a new chat

This lesson had several phases: propose, apply, discover gap, update, apply again. Recommended rhythm:

Chat A  propose + review artifacts
Chat B  apply (first implementation)
Chat C  update specs for tax rules + apply the gap fill
        archive (C or a short Chat D)

Do not clear context mid-task while apply is halfway through a file. Do clear between features, and after a long failed exploration. If you must hand off, ask the agent to write a short “decisions so far” note into the change’s proposal before you start the new chat.

10. Challenge (optional)

Challenge

Add a scenario: shipping waiver uses cart subtotal before tax, never after. Add a test whose name includes that scenario title. If your implementation accidentally used grand-total thresholds, the test will catch it. Do this as an update to a still-open change, or as a tiny new change clarify-shipping-waiver-base if you already archived.
