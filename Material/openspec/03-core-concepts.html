03 · Core Concepts

Five words you will keep hearing. I will say each one in plain language, then show you the folder and the headings OpenSpec expects.

Lesson 03 of 10 ~60 minutes Read and discuss
By the end of this lesson you should be able to say
  • What a spec is, what a change is, and why they live in different folders.
  • What a delta spec is, and what ADDED, MODIFIED, and REMOVED do when you archive.
  • What the four planning files are, and which question each one answers.
  • Why we write SHALL, SHOULD, and MAY, what a Given / When / Then scenario is for, and why each scenario needs its own test.
A short reminder before the new names

In lesson 01 we kept two piles of notes for Nile Retail, our small teaching shop. One pile said how the shop works today. The other pile held work that was still a draft. OpenSpec uses that same split. This lesson only gives those piles their real names, and shows you the headings the files must use.

The headings look fussy. There is a simple reason. Later, a small program reads the file and copies the new rules into the main spec. If you write “Changed stuff”, that program cannot guess that you meant the heading ## MODIFIED Requirements. So we use the headings it already knows.

Think

Suppose “checkout shows tax” is written in the same file as the rules that are already live. A teammate opens that file on Wednesday. How do they know whether that sentence is already true in the shop, or only a draft you have not finished?

Check your thought

They cannot tell. A half-written sentence looks the same as a finished rule. That is why OpenSpec keeps two folders. specs/ is what the shop does today. changes/ is a proposal, until you archive it and the new rules are copied into specs/.

Two folders. specs/ is what is true today. changes/ is the work you are still proposing. When the work is finished, archive copies the new rules into specs/ and files the change folder away.

2. Idea 1 — A spec says how the shop works today

A spec is a written description of how the shop behaves right now. If a sentence is in the spec, we treat it as true. Specs live in openspec/specs/.

We split them by capability. A capability is one area of the shop. You can also call it a domain. Same idea. For ShopLite we will grow these folders:

  • openspec/specs/catalog/ — looking at products
  • openspec/specs/search/ — finding a product
  • openspec/specs/cart/ — the basket
  • openspec/specs/checkout/ — placing an order
  • openspec/specs/orders/ — what happens after you buy
  • openspec/specs/inventory/ — how many items are in stock

Each folder usually has one file, spec.md. Inside that file you will see two kinds of writing:

  • A requirement is the rule. We usually start it with SHALL or MUST, which means “this has to happen.”
  • A scenario is one concrete example of that rule. We write it as Given / When / Then, so a person can try it without reading the code.

If someone asks “what does this shop do?”, the spec is the answer you both agreed on.

2.1 The words SHALL, SHOULD, and MAY

Everyday English is slippery. “The page should show the price” can mean “it must” or “it would be nice.” People who write internet standards got tired of that argument. They published a short list of words, called RFC 2119, and agreed what each word means. OpenSpec uses the same words. You do not need to read that document. You need these three:

WordWhat I mean when I write itShopLite example
MUST / SHALL This has to happen. There is no exception. The catalog SHALL list each in-stock product with name and price.
SHOULD Do this, unless you have a clear reason not to. Product cards SHOULD show a placeholder image if none is provided.
MAY This is optional. Skipping it is fine. The catalog MAY show a “Nile’s choice” badge.

When you are unsure, write SHALL. Use SHOULD only when you really mean “do this, unless there is a good reason not to.” Words like “gracefully”, “intuitively”, or “Amazon-like” do not tell anyone what to check. Leave them out of a requirement.

2.2 Scenarios

A requirement without a scenario is only a slogan. A scenario is one situation a tester could try. They should be able to follow it without opening the code. 

### Requirement: Catalog listing
The system SHALL display every product that is available for sale,
each showing a name and a price in the store currency.

#### Scenario: Shopper opens the home page
- GIVEN the store has three available products
- WHEN the shopper opens the home page
- THEN all three products are visible
- AND each product shows its name and price

When you write a scenario, I want these habits:

  • Name the situation. “Rejects empty search” tells me the case. “Test 2” tells me nothing.
  • Include a case that goes wrong, as well as the case that goes well. An empty store is a real case. So is a bad input.
  • Make it a specific situation. If you only repeat the requirement in different words, you have not added an example.

2.3 Each scenario gets a test

A scenario is a promise. A test is how we check that the promise is still true after the code changes. I want the spec itself to say this, so a later chat does not treat the scenarios as optional reading.

Put this requirement in every spec, once:

### Requirement: Test for each scenario
The project SHALL include one automated test for each scenario in this spec.
The test name SHALL include the scenario title.
The test SHALL fail when that scenario's THEN is not met.

Then, in tasks.md, give each scenario its own checkbox: write that test and make it pass. If a scenario has no test, the change is not finished. When you archive, this requirement stays in the main spec, next to the scenarios it covers.

In lesson 01 the page is a single HTML file, so the test can be a small script that opens that file and checks the text. From lesson 04 onward the app is Python, and the usual tool is pytest. The rule is the same either way: one scenario, one test, and the test name says which scenario it covers.

3. Idea 2 — A change is one piece of work

When you want to add behavior, change behavior, or remove behavior, you create a change. A change is one folder inside openspec/changes/. You should be able to say what that folder is for in one sentence.

A name I can understandA name that hides the work
add-product-catalogfeature-1
add-product-searchupdate
add-shopping-cartwip
fix-checkout-tax-roundingchanges

If you hear yourself say “and also” several times, you have more than one change. “Add the catalog, and also the cart, and also checkout” is three changes. Split them. A small change is easier to read, easier to finish in one sitting, and easier to file away when you are done.

4. Idea 3 — A delta is only the difference

Inside a change, you do not copy the whole spec and rewrite it. You write a delta. Delta here just means “the difference”: what this change adds, what it changes, and what it removes.

This is why the tool works on a shop that already exists. If you only want to change the cart, you write the cart difference. You do not first have to describe every page on the site. 

# Delta for Catalog

## ADDED Requirements

### Requirement: Catalog listing
The system SHALL ...

## MODIFIED Requirements

### Requirement: Product price display
The system SHALL show prices with exactly two decimal places.
(Previously: integer rupees only.)

## REMOVED Requirements

### Requirement: Guest price hiding
(Prices are now visible without signing in.)

When you archive, this is what those three headings do:

  • ADDED — the new rule is copied onto the end of the main spec. If that spec file does not exist yet, archive creates it.
  • MODIFIED — the old rule with the same heading is replaced. Write the full new requirement. A short note like “now use two decimals” is not enough for the program to rebuild the rule.
  • REMOVED — the old rule with that heading is deleted from the main spec.

The heading you choose matters, because the program trusts it. If an old rule changed and you mark the new text as ADDED, the old rule stays and the new rule is added beside it. Now the spec says two different things. If a brand-new rule is marked MODIFIED, there is no old heading to replace, so the update does not land. When you are unsure, open the current spec and look for the heading.

When a capability is new, start the delta with a short ## Purpose section. If you skip it, archive can leave the words “TBD” sitting in the file. In lessons 04 to 08 we will mostly add new rules. Lesson 09 is where we practice changing a rule and removing a rule.

Think

Look at the delta above. On archive, the program finds the old rule by the heading ### Requirement: Product price display, then replaces that whole block. Suppose you wrote loose notes instead: “tweak tax”, “also shipping”. Two changes both say “tweak checkout”. What goes wrong when you archive?

Check your thought

The program that copies the rules is not a person reading your notes. It matches a rule by its heading. A bullet with no heading has no name, so the program cannot tell which old paragraph to replace, which line is new, or whether the two changes are even about the same behavior. You can end up with two rules that disagree, the wrong paragraph replaced, or a merge that fails. Give every requirement a name. That name is how the old file and the new file are matched.

5. Idea 4 — Each change has a few planning files

Each change folder holds a few Markdown files. I will call them artifacts. That word only means “the documents for this change.” You write them in an order, because each one uses the one before it: 

proposal ──► specs ──► design ──► tasks ──► implement
   why        what       how       steps      do it
FileThe question it answersShopLite catalog example
proposal.md Why are we doing this, what is included, and what is left out? Shoppers need a home page grid of products. Search and cart wait for later changes.
specs/ What can a shopper see or do? This file is the delta. The home page SHALL list products with name and price. An empty catalog SHALL say there are no products.
design.md How will we build it? FastAPI, a Python library for web apps, serves / and /api/products. We start with 6 household items in a JSON file.
tasks.md What are the steps, as a checklist? 1.1 Set up the FastAPI app. 1.2 Add the seed data. 2.1 Home page HTML. 2.2 Product cards.

In the usual setup, /opsx:propose drafts all of these planning files in one go. You still read them before you run /opsx:apply. Apply is the step where the assistant writes the code.

5.1 You can go back and edit

The order is a guide

Some older ways of working finish every planning document, and only then allow you to write code. Going back is painful. OpenSpec does not lock you like that. The order proposal → specs → design → tasks tells you what you are ready to write next. If you learn something later, you go back and edit.

Say you are coding and you notice the tax rounding is wrong. Edit the spec and design.md, then continue. There is also a command, /opsx:update, that helps you refresh the plan from the files you changed. If you notice that search does not belong in the catalog change, make the proposal smaller. These files do not lock you out of an edit.

I like this because real work changes as you learn. The cost is that nothing pushes you forward for you. You have to keep one change about one thing.

6. Idea 5 — Archive copies the change into the spec

When the work is done, three things happen:

  1. The delta is copied into openspec/specs/.
  2. The change folder moves to openspec/changes/archive/YYYY-MM-DD-change-name/. The date is the day you archived it.
  3. The spec now describes the shop as it is after this change. You can start the next feature.

After we archive the catalog, you can open a new chat. That chat can read openspec/specs/catalog/ and see that the store already lists products. In lesson 01, a new chat guessed a different tax rule because the rule lived only in the old conversation. The spec file is what stops that.

Archive often asks you to sync first, if the new rules have not been copied into the main spec yet. Sync is the copy. Archive is filing the change folder away. When you run /opsx:archive, both often happen together.

7. The loop you will actually type

This is the loop. Explore is optional. The other three are the normal path.

/opsx:explore                 →  talk it through first (writes no files)
/opsx:propose add-product-catalog
        (you read the plan and fix it)
/opsx:apply                   →  the assistant writes the code from the tasks
/opsx:archive                 →  specs updated, change folder filed away

In Cursor, the same commands use a hyphen:

/opsx-explore
/opsx-propose add-product-catalog
/opsx-apply
/opsx-archive

/opsx:explore only talks with you. It writes no planning files and no code. Use it when you cannot yet say the change in one sentence. If you already know what you want, skip it. Lesson 04 skips explore, because I will give you the scope. Lesson 05 is where we slow down and practice explore.

8. Looking at the work from the terminal

The assistant does the writing in chat. You can still look at the changes from the terminal. These commands are for looking. They do not build the feature. 

openspec list                 # changes that are still open
openspec list --specs         # the main specs (if this flag differs, try openspec list --help)
openspec show add-product-catalog
openspec validate add-product-catalog
openspec status
openspec view                 # a small dashboard in the browser

Command flags can differ by version. If one of these fails, run openspec --help and openspec list --help and use the names your version prints.

9. Write a small catalog delta by hand

In lesson 04 the assistant will write these files for you. Before that, I want you to write a small one yourself. You need an eye for a bad sentence, because your job in the next lesson is to read what the assistant drafted.

Your Task

On paper, or in a scratch file, write two requirements and three scenarios for ShopLite’s first catalog. Write what the shopper can see. Leave out FastAPI, JSON, and CSS. Those are build choices, and they belong in the design.

  • In scope: a home page that shows products for sale.
  • Out of scope: search, cart, login, and recommendations.
  • Cover these cases: at least one product is visible, the store can be empty, and each card shows a price.

A good answer looks like this. Your wording can be different. The shape should be close.

## Purpose
The catalog lets shoppers see what Nile Retail currently sells.

## ADDED Requirements

### Requirement: Product grid
The system SHALL display each available product with its name and price.

#### Scenario: Store has products
- GIVEN at least one available product exists
- WHEN the shopper opens the home page
- THEN every available product is listed
- AND each listing shows name and price

#### Scenario: Empty store
- GIVEN no products exist
- WHEN the shopper opens the home page
- THEN the page explains that no products are available
- AND it does not show an empty broken grid of missing images

### Requirement: Product identity
Each product SHALL have a stable identifier so the same product can be opened again.

#### Scenario: Open a product from the grid
- GIVEN a listed product
- WHEN the shopper selects it
- THEN a detail view shows that product’s name and price

### Requirement: Test for each scenario
The project SHALL include one automated test for each scenario in this spec.
The test name SHALL include the scenario title.
The test SHALL fail when that scenario's THEN is not met.

Notice what the sample leaves out. It does not say “use Bootstrap” or “store the data in SQLite.” Those sentences are about how we build it. They belong in design.md. The spec says what the shopper can see.

Your Task — mark these

If you were reviewing a spec, which of these would you send back, and why?

  1. “The home page SHALL look modern and Amazon-like.”
  2. “The system SHALL use a Python list named PRODUCTS.”
  3. “The system SHALL show a name and price for every available product.”

Here is how I would mark them. (1) Send it back. “Modern” and “Amazon-like” are opinions. A tester cannot check them. (2) Send it back. A Python list named PRODUCTS is a decision about the code. That belongs in the design. (3) Keep it. It says what the shopper sees.

10. How big should a change be?

A change is too big when:

  • The proposal is a list of features that do not depend on each other.
  • Reading it would take an afternoon, so nobody will read it.
  • Half of the tasks could be finished and shipped on their own.

The writing can also be too heavy for the work. A one-line typo does not need three requirements and a design document.

Match the amount of writing to the size of the change. In this course we will try a small change and a larger one, so you can feel the difference.

11. Check yourself

Answer these in your own words
  1. What lives in openspec/specs/, and what lives in openspec/changes/?
  2. Why do we write a delta, instead of rewriting the whole spec every time?
  3. Name the four planning files, and the question each one answers.
  4. When you archive, what happens to a requirement you marked ADDED?
  5. What does the spec say must exist for each scenario, and what should the test name include?
