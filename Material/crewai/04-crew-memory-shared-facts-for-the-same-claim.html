Let the Crew Remember

The same Suraksha chat. The two workers still run in order. This time the team keeps short facts from earlier questions about the same file.

How to follow this page. You already have two agents, two tasks, the database lookups, and the chat. Do the steps in order. The only code you change is a few lines in crew.jsonc. Copy those lines exactly. Do not rewrite the agents or the chat. After each step, check what you should see before you continue. New words are explained in parentheses the first time they appear.

The story, in plain words

You are still the claims officer (the human at the keyboard). The coverage officer agent opens the database and writes the coverage opinion (a first reading of whether the contract seems to cover the accident). The examiner brief agent then writes the brief (the short note for the meeting). Neither note pays anyone. A senior examiner (a more senior human, not in this chat) still decides the money.

Each question still starts from the accident story and the database. If you tell the agent something new, the next question does not know you said it. The chat window also forgets the bubbles (the messages on the page) when you switch claims. A person at a claims desk does not work like that. If the surveyor (the person who looks at the damaged car and reports what the photos show) phones and says the photos show rear damage only, the next person who opens that same file should still know.

CrewAI calls that store memory (short facts saved after an answer, then searched before the next answer). With memory on, the crew saves short facts after each task. Before the next task, it looks those facts up and hands the matching ones to the agent. Both agents share this one memory. Neither agent file has a private memory of its own. Memory is not the database, and it is not the chat bubbles.

Memory is not the database. Policy Record and Earlier Claims are still the records. A remembered fact is something said in an earlier question. The agent must say it came from that earlier question. It must not pretend the fact was in the policy table.
A fact about one claim must stay on that claim. Both agents share the same memory, and the memory is still there after you switch files in the sidebar. A note about CLM-20481 must not be used when the question is about CLM-10021 or CLM-10044. The task text below says so.

Step 1: Turn memory on

In this step you switch memory on. You do not add a new file. Open crew.jsonc and add one line, as the green box says. Leave the agents, the tasks, and the sequential process (tasks running one after another, in the order written) as they are. Save the file.

Change crew.jsonc

Open crew.jsonc. Next to "tracing": true, add "memory": true. Leave the agents, the tasks, and the sequential process as they are.

"process": "sequential",
"verbose": true,
"tracing": true,
"memory": true,

"memory": true tells the crew to keep one shared memory for every agent that does not bring a memory of its own. After a task finishes, CrewAI pulls short facts out of that answer and saves them. At the start of the next task, it searches those facts for ones that resemble the new question and adds them to what the agent can read.

The first question after you turn this on has nothing saved yet, so the answers look like the ones you already know. The second question is where memory shows up. Saving and searching use the OpenAI key already in your .env file. You do not add another key.

Step 2: Tell both tasks how to use a memory

In this step you tell both workers the rule for a remembered fact. A remembered sentence is not permission to mix files. A fact about CLM-20481 must not be used when the question is about CLM-10021. In crew.jsonc, paste the block below into both task descriptions, immediately above the line that starts CONSTRAINTS:. Do not delete the lines that are already there.

MEMORY:
- You may use a remembered fact only when it names claim {claim_id}.
- If a memory names a different claim, ignore it.
- Say that a remembered fact came from an earlier question. It is not a row from Policy Record or Earlier Claims.

Then change one line in each description so a same-claim memory counts as known.

In the coverage opinion task, the line that tells the agent to say a missing fact is not on file should read:

desk.py and app.py stay as they are. The crew is loaded from crew.jsonc, so memory turns on with that file. The chat still only calls respond.

In this step you delete the saved facts and confirm the phone call is gone. The database stays. Stop the chat with Ctrl+C first. A reset while the chat is still open does not stick. From suraksha_claims_desk run:

That deletes the crew's saved facts. Start the chat again with uv run streamlit run app.py. Select CLM-20481 and ask the surveyor question once more, without sending the phone-call sentence first. Both parts should now say that what the surveyor said is not on file.

How a fact is filed

The steps above are enough to finish the exercise. Read this part only after Step 5 worked. It explains what CrewAI does with the surveyor sentence after you send it. You do not add another file for this. An embedding (a list of numbers that stands for the meaning of a sentence, so two sentences can be compared even when the words differ) is used in the search. You do not write that list yourself.

CrewAI keeps one memory for the crew. After a task finishes, it pulls short sentences out of that answer and saves each one. Before the next task starts, it searches those sentences and adds the closest ones to the prompt the agent already has. The agent does not call a memory tool. Policy Record and Earlier Claims are still the only tools.

Take the phone call on CLM-20481:

  1. The coverage task writes the opinion. CrewAI asks the model to split that opinion into short sentences that can stand on their own. One of them is the surveyor line about rear damage. The same split runs again after the brief.
  2. Each sentence is saved in the background, so the brief can start while the save is still finishing. A search waits until those saves have landed. When the crew ends, any save still in flight is finished before the run is treated as done. That is why a follow-up in a new question can still see the phone call.
  3. On the way in, the model also suggests a folder, a few category words, and an importance from 0 to 1. If that suggestion fails, the sentence is still saved, under the crew's root folder, with importance 0.5.
  4. The next question searches with the new task text. The best matches, up to ten, are placed in the prompt. The coverage officer and the brief writer both receive that search, once each, because both tasks run with memory on.

Two nearly identical sentences are folded together. Inside one batch, a sentence that is almost a copy of another (similarity 0.98 or higher) is dropped before it is stored. Against what is already on disk, similarity above 0.85 asks the model to keep the old sentence, rewrite it with the new detail, delete it, or keep both. The opinion and the brief can both mention rear damage. You will often end up with one stored sentence.

The filing step also calls the model. The answer itself uses openai/gpt-4o-mini. Saving a fact, and searching with a long task, send that text to the same OpenAI key in .env. Keep using the fictional claims. A real customer's file does not belong in this store.

What "memory": true sets up

"memory": true in crew.jsonc tells CrewAI to build that memory for you. The weights, the embedding model, and the folder layout below are the defaults. This page leaves them there. A custom memory, with different weights, is a Memory(...) object built in Python and handed to the crew. desk.py does not do that.

Folders inside the memory

Saved sentences are arranged like directories. CrewAI calls each directory a scope. The crew's root is fixed. The child folders are not. When a sentence is saved without a folder name, the model reads the sentence and the folders that already exist, then picks a place under /crew/suraksha-coverage-desk. A new folder is created when none of the old ones fit. You do not design that tree in crew.jsonc.

/crew/suraksha-coverage-desk the model may add children, for example a claims folder every search from this crew starts here

A search from this crew looks inside that root. It can still return a sentence about CLM-20481 while the question on screen is CLM-10021, because the words "surveyor" and "photos" resemble each other. The folder is a hint for the search. The MEMORY block in the task is the rule the agent must follow: use a remembered fact only when it names {claim_id}.

A private folder is a different object, a scope view. You would attach memory.scope("/agent/coverage_officer") to one agent so that agent could read and write only that branch. The brief writer would not see it. This page does not do that. Both agents stay on the shared crew memory, and the task text keeps the claims apart.

How a matching fact is chosen

Each stored sentence gets one score from three parts. The highest score is the one handed back:

score = 0.5 × similarity + 0.3 × decay + 0.2 × importance

decay = 0.5 ^ (age in days / 30)
PartDefault weightOn the surveyor sentence
Similaritysemantic_weight 0.5How close the task text is to the stored sentence in meaning. "What did the surveyor say about the photos?" can match "the photos show rear damage only" even though the wording is different. This is the largest share of the score.
Recencyrecency_weight 0.3, half-life 30 daysA sentence saved today scores 1.0 on freshness. The same sentence at 30 days scores 0.5, and at 60 days scores 0.25. Today's phone call outranks a similar note from last quarter.
Importanceimportance_weight 0.2A number from 0 to 1 chosen when the sentence was saved. It stays on the record. A line the model treats as central to the file can still surface after the freshness has faded.

There is a faster search, depth="shallow", which compares vectors and applies the score above, with no extra model call. "memory": true uses deep. For a long task, the model first picks likely folders and may search a second time when the first pass looks unsure. This page leaves that as it is, which is why the follow-up question takes longer than the first.
