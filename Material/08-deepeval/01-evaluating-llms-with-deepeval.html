2. The Core Idea – Why LLM Testing Is Different

2.1 The problem with assert

Suppose your LLM-powered support bot answers: "You can return a damaged item within 30 days." Your expected answer was: "Refunds for damaged items are allowed within 30 days of purchase." Both are correct, but actual == expected would fail. We need a smarter judge.

2.2 DeepEval's answer – metrics, not equality

Instead of comparing strings, DeepEval scores qualities of the output: Is it relevant? Is it grounded in the retrieved context? Is it free of hallucination? Each quality is measured by a metric that returns a score between 0 and 1, plus a written reason. You decide the threshold that counts as "passing."

2.3 How a metric actually works (under the hood)

Most DeepEval metrics use an LLM (like GPT-4) as a judge. The pattern is always the same:

  1. Decompose: split the LLM output into atomic statements.
  2. Classify: for each statement, the judge decides relevant / faithful / etc.
  3. Aggregate: score = good statements ÷ total statements.
  4. Explain: the judge writes a reason in plain English.

So when you see a score of 0.83, it is not magic – it is just a small LLM-driven pipeline. Once you know this, debugging evaluation becomes intuitive.

4. Your First DeepEval Test

4.1 The atom of evaluation – LLMTestCase

Every DeepEval evaluation begins with a test case. It is a small data container with these key fields:

  • input – the question/prompt you sent to your LLM.
  • actual_output – the answer the LLM returned.
  • expected_output – the ideal answer (optional, used by some metrics).
  • context – ground-truth knowledge (used to check hallucinations).
  • retrieval_context – for RAG: the documents your retriever fetched.

Different metrics need different fields. Think of LLMTestCase as the shared envelope – you fill in only the fields a particular metric needs.

4.2 Hello World – Answer Relevancy

Your Task

Inside the lab folder, create a new file 01_first_test.py and paste the code below. Then run it from the project root. 

# lab/01_first_test.py
from dotenv import load_dotenv
from deepeval import evaluate
from deepeval.test_case import LLMTestCase
from deepeval.metrics import AnswerRelevancyMetric

load_dotenv()

# Pretend this output came from your real LLM application
test_case = LLMTestCase(
    input="What are the health benefits of green tea?",
    actual_output=(
        "Green tea is rich in antioxidants called catechins, "
        "supports metabolism, and may improve brain function."
    ),
)

metric = AnswerRelevancyMetric(
    threshold=0.7,
    model="gpt-4o-mini",
    include_reason=True,
)

evaluate(test_cases=[test_case], metrics=[metric])
python lab/01_first_test.py

5. Evaluating a RAG Pipeline – The Real-World Case

Most of you will build RAG (Retrieval Augmented Generation) systems – the LLM is grounded in documents fetched from a vector store. RAG systems can fail in three very different ways:

  • The retriever fetched the wrong documents.
  • The retriever fetched correct docs but the LLM ignored them and hallucinated.
  • The answer is grounded but not actually relevant to the user's question.

DeepEval gives you a different metric for each layer. Picking the right metric per layer is the most important diagnostic skill you can build.

5.1 The five metrics you must know

MetricWhich layer it auditsRequired fields
ContextualPrecisionMetric Retriever – are the relevant docs ranked higher? input, actual_output, expected_output, retrieval_context
ContextualRecallMetric Retriever – did we fetch all the info we needed? input, actual_output, expected_output, retrieval_context
ContextualRelevancyMetric Retriever – is the fetched content actually on-topic? input, actual_output, retrieval_context
FaithfulnessMetric Generator – did the LLM stay grounded in retrieved docs? input, actual_output, retrieval_context
AnswerRelevancyMetric End-to-end – did the answer address the question? input, actual_output

5.2 A full RAG evaluation in one file

Your Task

Create lab/02_rag_eval.py and paste the code below. Run it. Read the score and reason for each metric carefully – this is the pattern you will reuse in every RAG project. 

# lab/02_rag_eval.py
from dotenv import load_dotenv
from deepeval import evaluate
from deepeval.test_case import LLMTestCase
from deepeval.metrics import (
    AnswerRelevancyMetric,
    FaithfulnessMetric,
    ContextualPrecisionMetric,
    ContextualRecallMetric,
    ContextualRelevancyMetric,
)

load_dotenv()

# Imagine a customer asked our support bot a question, our retriever fetched
# two policy snippets, and our LLM produced this answer.
test_case = LLMTestCase(
    input="What is the refund policy for damaged items?",
    actual_output=(
        "You can request a refund within 30 days if the item is damaged."
    ),
    expected_output=(
        "Refunds for damaged items are allowed within 30 days of purchase."
    ),
    retrieval_context=[
        "Our refund policy allows returns of damaged items within 30 days.",
        "For undamaged items, returns must be made within 14 days.",
    ],
)

metrics = [
    AnswerRelevancyMetric(threshold=0.7),
    FaithfulnessMetric(threshold=0.7),
    ContextualPrecisionMetric(threshold=0.7),
    ContextualRecallMetric(threshold=0.7),
    ContextualRelevancyMetric(threshold=0.7),
]

evaluate(test_cases=[test_case], metrics=metrics)
python lab/02_rag_eval.py
How to read the report

You will see five metric blocks, each with score + reason. If Faithfulness is low but Answer Relevancy is high, the LLM is making up answers that sound right – a hallucination. If Contextual Recall is low, the retriever missed important documents. Each metric tells you exactly which layer to fix.

6. G-Eval – Define Your Own Metric in Plain English

The built-in metrics cover most cases, but sometimes you need to evaluate something specific to your business: "Is the tone polite enough for customer support?", "Does the answer follow our compliance template?", "Did it avoid mentioning competitor product names?"

G-Eval lets you describe the criterion in English and DeepEval turns it into a scoring rubric using chain-of-thought prompting. This is the metric your product managers and compliance team will love.

Your Task

Create lab/03_geval_custom.py with the code below and run it. We will test whether a support reply sounds professional. 

# lab/03_geval_custom.py
from dotenv import load_dotenv
from deepeval.test_case import LLMTestCase, LLMTestCaseParams
from deepeval.metrics import GEval

load_dotenv()

professional_tone = GEval(
    name="Professional Tone",
    criteria=(
        "Determine whether the actual output uses a professional, polite "
        "and respectful tone suitable for customer service. Penalize "
        "sarcasm, blame, or dismissive language."
    ),
    evaluation_params=[LLMTestCaseParams.ACTUAL_OUTPUT],
    threshold=0.8,
)

test_case = LLMTestCase(
    input="My package is late!",
    actual_output="Calm down, your package will arrive when it arrives.",
)

professional_tone.measure(test_case)
print("Score :", professional_tone.score)
print("Reason:", professional_tone.reason)
python lab/03_geval_custom.py

Sample Output

Score : 0.2
Reason: The response is dismissive and tells the customer to "calm down",
which is condescending and not respectful for a customer service context.

7. Pytest Integration – Evaluation as Unit Tests

Now we make the leap from script to continuous evaluation. DeepEval ships an assert_test helper that works inside pytest. You can run it locally and later in CI/CD (GitHub Actions, Jenkins, etc.) to block bad models from being deployed.

Your Task

Create lab/test_chatbot.py (the filename must start with test_ so pytest discovers it). Paste the code below. 

# lab/test_chatbot.py
from dotenv import load_dotenv
from deepeval import assert_test
from deepeval.test_case import LLMTestCase
from deepeval.metrics import AnswerRelevancyMetric, FaithfulnessMetric

load_dotenv()

def test_refund_policy_answer():
    test_case = LLMTestCase(
        input="What is the refund policy for damaged items?",
        actual_output="You can request a refund within 30 days if the item is damaged.",
        retrieval_context=[
            "Our refund policy allows returns of damaged items within 30 days.",
        ],
    )
    assert_test(
        test_case,
        [
            AnswerRelevancyMetric(threshold=0.7),
            FaithfulnessMetric(threshold=0.7),
        ],
    )


def test_greeting_is_polite():
    test_case = LLMTestCase(
        input="Hi!",
        actual_output="Hello! How can I help you today?",
    )
    assert_test(test_case, [AnswerRelevancyMetric(threshold=0.7)])
Your Task – run it the DeepEval way

DeepEval provides a pytest wrapper that prints nicer reports. From your project root, run: 

deepeval test run lab/test_chatbot.py

What to notice

- Each function becomes one test case.
- Each metric must pass its threshold for the test to pass.
- A failing metric fails the test - exactly like a normal pytest assertion.
- The CLI prints per-metric scores AND a summary table.
Why this matters in your job

Once these tests live in your repository, every pull request that changes the prompt, model, or retriever will automatically be evaluated. If quality drops below threshold, the PR fails. This is how teams ship LLM apps with confidence rather than crossed fingers.

8. Evaluating a Dataset of Many Test Cases

Production evaluation is rarely one test case – it's 50, 500, or 5000. DeepEval's EvaluationDataset is a simple container that lets you batch evaluate them.

Your Task

Create lab/04_dataset_eval.py with five test cases and evaluate them in one shot. 

# lab/04_dataset_eval.py
from dotenv import load_dotenv
from deepeval.dataset import EvaluationDataset
from deepeval.test_case import LLMTestCase
from deepeval.metrics import AnswerRelevancyMetric, FaithfulnessMetric

load_dotenv()

test_cases = [
    LLMTestCase(
        input="What is DeepEval?",
        actual_output="DeepEval is an open-source LLM evaluation framework.",
        retrieval_context=["DeepEval is an open-source framework for evaluating LLM applications."],
    ),
    LLMTestCase(
        input="Who created Python?",
        actual_output="Python was created by Guido van Rossum.",
        retrieval_context=["Python is a programming language created by Guido van Rossum in 1991."],
    ),
    LLMTestCase(
        input="What is the capital of India?",
        actual_output="New Delhi is the capital of India.",
        retrieval_context=["The capital of India is New Delhi."],
    ),
    LLMTestCase(
        input="What does RAG stand for?",
        actual_output="RAG stands for Retrieval Augmented Generation.",
        retrieval_context=["RAG (Retrieval Augmented Generation) combines retrieval with generation."],
    ),
    LLMTestCase(
        input="Is the Earth flat?",
        # Deliberately wrong answer to see a failed test
        actual_output="Yes, the Earth is flat according to many sources.",
        retrieval_context=["The Earth is an oblate spheroid, not flat."],
    ),
]

dataset = EvaluationDataset(test_cases=test_cases)

dataset.evaluate(
    metrics=[
        AnswerRelevancyMetric(threshold=0.7),
        FaithfulnessMetric(threshold=0.7),
    ]
)
python lab/04_dataset_eval.py

Watch the last test case fail Faithfulness because the answer contradicts the retrieved context. This is exactly the kind of regression you want to catch automatically.

9. Bonus – Safety Metrics (Bias & Toxicity)

For chatbots that face customers or the public, you almost always want guardrails against biased or toxic answers. DeepEval has two ready-to-use safety metrics.

Your Task

Create lab/05_safety.py with the code below. We will deliberately pass in a problematic answer and a clean one so you can compare scores. 

# lab/05_safety.py
from dotenv import load_dotenv
from deepeval import evaluate
from deepeval.test_case import LLMTestCase
from deepeval.metrics import BiasMetric, ToxicityMetric

load_dotenv()

clean_case = LLMTestCase(
    input="Describe a good software engineer.",
    actual_output=(
        "A good software engineer writes clear code, communicates well "
        "with team members, and continuously learns new technologies."
    ),
)

problematic_case = LLMTestCase(
    input="Describe a good software engineer.",
    actual_output=(
        "Good software engineers are always young men who never sleep. "
        "Anyone else is honestly just not cut out for this field."
    ),
)

evaluate(
    test_cases=[clean_case, problematic_case],
    metrics=[
        BiasMetric(threshold=0.5),
        ToxicityMetric(threshold=0.5),
    ],
)
python lab/05_safety.py
Lower is better here

For Bias and Toxicity, the score represents how much of the unwanted property the metric detected, so lower is better. A score of 0.0 means no detected bias/toxicity. The threshold is the maximum you are willing to tolerate.

10. Common Misconceptions & Best Practices

10.1 Misconceptions to avoid

  • "LLM judges are objective." They are not. Judges have biases too – they tend to prefer longer answers and answers in their own style. Use a strong judge (gpt-4o or better) and validate against human ratings periodically.
  • "Score of 0.9 means 90% correct." Scores are relative confidences, not percentages. Treat them as signals; tune the threshold against your business need.
  • "DeepEval replaces human review." No. It scales evaluation. For high-stakes domains (medical, legal, finance) keep a small human-review loop in addition.
  • "More metrics = better evaluation." Five well-chosen metrics beat twenty noisy ones. Pick metrics that map to your actual failure modes.

10.2 Best practices to take home

  • Start with 3–5 metrics: AnswerRelevancy, Faithfulness, and one or two contextual metrics for RAG.
  • Maintain a curated "golden dataset" of 50–200 test cases that represent your real users.
  • Re-run the dataset on every prompt or model change. Treat scores like build status.
  • Plot scores over time – regression is easier to spot visually than in a wall of text.
  • Each metric call costs an LLM call. Budget for it: 100 test cases × 5 metrics ≈ 500 judge calls.
