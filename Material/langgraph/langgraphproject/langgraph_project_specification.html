LangGraph Multi-Agent E-commerce Support System
Capstone Project Specification

Purpose of this document

This document is the requirements and specification for your LangGraph capstone project. It describes a sophisticated multi-agent system that demonstrates LangGraph's advanced capabilities including: parallel processing, subgraphs, LLM-supervised agents, fan-out/fan-in patterns, state management, and human-in-the-loop interactions. This project builds upon the LangChain 1.x concepts you learned and elevates them to a production-ready multi-agent architecture.

1. Project Overview

You will build a Multi-Agent E-commerce Support System using LangGraph, demonstrating advanced orchestration patterns. Unlike the single-agent LangChain project, this system features:

  • Supervisor-Worker Pattern: An LLM-based supervisor coordinates multiple specialized agents.
  • Parallel Processing: Multiple agents work simultaneously on independent tasks (e.g., checking inventory and payment status).
  • Subgraphs: Complex workflows are encapsulated as reusable subgraphs (e.g., returns processing workflow, fraud detection workflow).
  • Dynamic Routing: The supervisor intelligently routes requests based on context and conversation history.
  • State Management: LangGraph's built-in state management with reducers for parallel updates.
  • Human-in-the-Loop: Interrupts for admin approval in critical workflows.
  • Streamlit UI: Customer chat interface and admin dashboard with real-time graph visualization.
Key Architectural Improvements over LangChain 1.x
  • Multi-Agent vs. Single Agent: Instead of one agent with many tools, we have specialized agents with focused responsibilities.
  • Parallel Execution: LangGraph's fan-out/fan-in enables concurrent operations for better performance.
  • Subgraphs for Modularity: Complex workflows (returns, fraud detection) are self-contained and reusable.
  • Supervisor Intelligence: An LLM supervisor makes dynamic routing decisions, not just predefined rules.
  • Built-in Checkpointing: LangGraph provides native state persistence with better resume capabilities.
🎓 Learning Focus: 3-Level Nested Subgraph Architecture

This project demonstrates nested subgraph composition - a critical pattern for building complex AI systems:

  • Level 1 - Main Graph: Supervisor routes to specialized worker agents (Order, Inventory, Policy)
  • Level 2 - Returns Subgraph: Order Agent invokes returns workflow as a tool (includes HITL approval)
  • Level 3 - Fraud Detection Subgraph: Returns workflow invokes fraud detection as a node (4 parallel checks via Send API)

Result: Main Graph → Returns Subgraph → Fraud Detection → 4 Parallel Checks

This architecture teaches two invocation patterns (tool vs node), state management across levels, and dynamic parallel processing with Send API. See ARCHITECTURE.md for detailed diagrams and implementation guide.

3. Multi-Agent System Components

3.1 Supervisor Agent (LLM-Based Orchestrator)

The supervisor is the "brain" of the system. It analyzes each user message and the current state to decide which specialized agent should handle the request next.

Responsibilities:

  • Analyze incoming messages and conversation context
  • Route to appropriate worker agent: OrderAgent, InventoryAgent, or PolicyAgent
  • Determine when the task is complete (return "FINISH")
  • Maintain conversation coherence across multiple agent interactions

Important: The supervisor does NOT directly invoke subgraphs or send notifications. Worker agents (primarily OrderAgent) invoke subgraphs as needed during their processing.

Implementation: Use with_structured_output() to ensure the supervisor returns a Pydantic model with routing decisions.

3.2 Specialized Worker Agents (Supervisor Routes To These)

The supervisor routes to these three agents only. These agents may invoke subgraphs as needed.

a) Order Agent

  • Purpose: Handle all order-related queries and operations
  • Tools: SQL toolkit for querying orders, order_items, payments tables
  • Capabilities:
    • Query order status, history, and details
    • Check payment information
    • Handle cancellations directly: Validate business rules (order not yet shipped), update status, call notification agent to send email - no HITL needed
    • Handle returns via subgraph: Invoke Returns Workflow subgraph (includes HITL for admin approval)

Note: OrderAgent distinguishes between cancellations (simple, immediate) and returns (complex, requires admin approval via HITL). It calls the notification agent when emails need to be sent.

b) Inventory Agent

  • Purpose: Manage product availability and inventory queries
  • Tools: SQL toolkit for products and inventory tables
  • Capabilities:
    • Check product availability
    • Query product details and specifications
    • Check estimated delivery times
    • Provide product recommendations

c) Policy Agent

  • Purpose: Answer policy and FAQ questions using RAG
  • Tools: ChromaDB vector store retriever
  • Capabilities:
    • Answer questions about returns, refunds, shipping policies
    • Provide FAQ information
    • Explain terms and conditions
Note on Notifications

Unlike the three worker agents above that the supervisor routes to, notification handling is done by a reusable utility agent with Gmail tools. This agent is not part of the main graph routing - instead, other agents (primarily OrderAgent and within Returns Subgraph) directly invoke the notification agent when they need to send emails. This keeps notification logic centralized and reusable.

3.3 Notification Agent (Reusable Utility)

Purpose: Handle all email communications - invoked by other agents as needed

Tools: Gmail toolkit (GmailSendMessage, etc.), SQL toolkit for email_logs

Capabilities:

  • Send emails using Gmail API via LangChain's GmailToolkit
  • Support different email types: order confirmation, cancellation, return request, return status updates
  • Use email templates with dynamic content population
  • Automatically log all sent emails to email_logs table
  • Handle failures gracefully and return status

Implementation: Create this agent once and make it callable by other agents. OrderAgent can invoke it with email details, and it returns success/failure status.

4. Subgraph Workflows

What are Subgraphs?

Subgraphs are self-contained LangGraph workflows that can be embedded within larger graphs. They enable modular design, code reuse, and clear separation of concerns. Each subgraph has its own state schema and can be tested independently. Use subgraphs for complex multi-step workflows, not for simple operations.

4.1 Returns Processing Subgraph (with Human-in-the-Loop)

Purpose: Handle the complete returns workflow from request to resolution

Important: This subgraph handles RETURNS only (items already delivered). Order cancellations (before shipment) are handled directly by OrderAgent without HITL, as they're simpler operations with just business rule validation.

Workflow Steps:

  1. Validate Return Request: Check if order is eligible for return (30-day window, delivered status)
  2. Create Return Record: Insert into returns table with PENDING status
  3. Run Fraud Detection: Invoke fraud detection subgraph (Level 3)
    • Spawns 4 parallel checks using Send API
    • Frequency (35%), Value (35%), Reason (15%), Timing (15%)
    • Returns fraud score (0-100) and risk level (LOW/MEDIUM/HIGH)
  4. Request Approval (HITL): Pause workflow with fraud score displayed
    • Admin sees color-coded risk indicator: 🟢 LOW / 🟡 MEDIUM / 🔴 HIGH
    • Fraud score and individual check details shown in dashboard
    • Interrupt point using interrupt()
  5. Admin Decision: Admin approves or rejects based on fraud assessment
  6. Process Decision: Update return status, calculate refund if approved
  7. Notify Customer: Send final email notification with outcome

State Schema: Return request details, validation results, fraud score, fraud details, admin decision

Fraud Detection Integration Flow:

validate_return → create_return_record → run_fraud_detection → request_approval (HITL) → process_approved/rejected → notify_customer

The fraud detection runs before admin approval, so admins can see the fraud risk assessment when making their decision.

4.2 Fraud Detection Subgraph (Parallel Processing with Send)

Purpose: Analyze return requests for potential fraud patterns using dynamic parallel processing

✅ IMPLEMENTED - Nested Subgraph Architecture

The Fraud Detection Subgraph is invoked as a NODE within the Returns Subgraph, demonstrating a 3-level nested architecture:

  • Level 1: Main Graph (Supervisor + Workers)
  • Level 2: Returns Subgraph (invoked as tool by Order Agent)
  • Level 3: Fraud Detection Subgraph (invoked as node in Returns workflow)

This creates: Main Graph → Returns Subgraph → Fraud Detection Subgraph → 4 Parallel Checks

See ARCHITECTURE.md for detailed diagrams and implementation patterns.

Parallel Checks (35%/35%/15%/15% weighted scoring):

  • Check 1 - Return Frequency (35%): Count returns in last 30 days
    • >5 returns = HIGH (80-100 score)
    • 3-5 returns = MEDIUM (40-60 score)
    • <3 returns = LOW (0-30 score)
  • Check 2 - Order Value Patterns (35%): Analyze return value and history
    • >$1000 return = HIGH (70-100 score)
    • $500-1000 return = MEDIUM (40-60 score)
    • +20 score if user has multiple high-value returns in history
  • Check 3 - Return Reason Analysis (15%): Detect suspicious patterns
    • Vague reasons ("changed mind", "don't need") = +30 score
    • Short reasons (<10 characters) = +25 score
    • Repeated patterns across user's returns = +20 score
  • Check 4 - Timing Patterns (15%): Days between order and return
    • ≤2 days = HIGH (85 score) - very quick return
    • ≤7 days = MEDIUM (50 score)
    • ≥20 days = MEDIUM (35 score) - deadline gaming
    • 8-19 days = LOW (15 score) - normal usage time

Implementation Pattern:

# File: src/ecommerce_support/subgraphs/fraud_detection.py

def spawn_fraud_checks(state) -> list[Send]:
    """Router function for dynamic parallelization"""
    return [
        Send("check_frequency", state),
        Send("check_value", state),
        Send("check_reason", state),
        Send("check_timing", state)
    ]

# Graph setup
graph.add_conditional_edges(
    START,
    spawn_fraud_checks,  # Router function (NOT added as node!)
    ["check_frequency", "check_value", "check_reason", "check_timing"]
)

# All 4 checks execute simultaneously!
# Results aggregated with operator.add reducer

Invocation in Returns Subgraph:

# File: src/ecommerce_support/subgraphs/returns_subgraph.py

def run_fraud_detection_node(state: ReturnsState):
    """Invoke fraud detection as a node in returns workflow"""
    fraud_graph = create_fraud_detection_subgraph()
    result = fraud_graph.invoke({
        "return_id": state["return_id"],
        "order_id": state["order_id"],
        "user_email": state["user_email"],
        "return_reason": state["return_reason"],
        "return_items": state["return_items"]
    })
    return {"fraud_score": result["fraud_score"]}

# Workflow: validate → create_record → fraud_detection → request_approval
graph.add_edge("create_return_record", "run_fraud_detection")
graph.add_edge("run_fraud_detection", "request_approval")

Output:

  • fraud_score: Weighted average (0-100)
  • risk_level: LOW (<30), MEDIUM (30-60), HIGH (≥60)
  • fraud_details: Individual check scores, reasons, and recommendation

Performance: 4x speedup over sequential checks (~1 second vs ~4 seconds)

Test Data: Database includes two user profiles for fraud detection validation:

  • Good User: sivaprasad.valluru@gmail.com - 1 legitimate return in 30 days, expected LOW score
  • Bad User: fraudster@example.com - 7 suspicious returns in 30 days, expected HIGH score

5. Parallel Processing Demonstrations

Cancellations vs Returns - Different Workflows

Cancellations: OrderAgent handles directly with simple validation (order not shipped yet). No HITL needed. Quick operation: validate → update DB → send notification.

Returns: Complex workflow requiring Returns Subgraph with HITL. Items already delivered, fraud risk assessment needed, admin approval required.

Don't confuse these - they have very different complexity and approval requirements!

Parallelization in LangGraph

LangGraph supports two types of parallelization:

  • Fan-out/Fan-in: Fixed parallel paths defined at graph build time (e.g., check last order details AND current inventory AND current pricing simultaneously)
  • Dynamic Parallelization with Send: Create parallel tasks dynamically at runtime based on data (e.g., send multiple fraud checks, one per return item)

5.2 Dynamic Parallelization with Send

Use the Send API for dynamic parallel processing scenarios:

✅ IMPLEMENTED - Fraud Detection Parallel Checks

The fraud detection subgraph demonstrates dynamic parallelization using Send API:

  • 4 fraud checks spawn simultaneously: Frequency, Value, Reason, Timing
  • Router function: spawn_fraud_checks() returns list[Send]
  • Conditional edges: add_conditional_edges(START, spawn_fraud_checks, [node_list])
  • State reducer: fraud_checks: Annotated[list, operator.add] aggregates results
  • Performance gain: ~1 second (parallel) vs ~4 seconds (sequential) = 4x speedup

See src/ecommerce_support/subgraphs/fraud_detection.py for complete implementation.

Other potential uses for Send API:

  • Batch notifications: When admin approves multiple returns, send parallel notification emails
  • Inventory checks: When user asks about multiple products, check availability in parallel
  • Multi-item validation: For orders with many items, validate each item in parallel

6. State Management and Reducers

6.1 State Schema Design Requirements

You must design typed state schemas for your main graph and all subgraphs. Understanding how state flows between graphs is critical.

Main Graph State Requirements:

  • Extend MessagesState from LangGraph (includes messages list with built-in reducer)
  • User context: user_email, conversation_id
  • Routing decisions: field to track which agent supervisor routes to next (use Literal type for valid options)
  • Parallel processing results: list with operator.add reducer to combine results from parallel tasks
  • Workflow metadata: current workflow type, HITL flags
  • Subgraph Input Fields: Fields needed to invoke subgraphs (order_id, return_items, return_reason, etc.)
  • Subgraph Output Fields: Fields to receive results from subgraphs (return_id, ticket_id, fraud_score, refund_amount, etc.)
Important: State Flow Between Main Graph and Subgraphs

When a worker agent invokes a subgraph:

  • Input: The agent passes relevant data from main state to the subgraph (e.g., user_email, order_id, return_items)
  • Subgraph Processing: The subgraph works with its own detailed state schema internally
  • Output: When the subgraph completes, it returns results that get merged back into the main state (e.g., return_id, fraud_score, ticket_id)

Your main state doesn't need ALL the internal subgraph fields (like validation_result, intermediate steps, etc.) - only the inputs you pass TO subgraphs and the outputs you receive FROM subgraphs.

Returns Subgraph State Requirements:

  • Input from main graph: user_email, order_id, return_reason, return_items
  • Internal processing state: validation_result, return_id, ticket_id
  • Fraud detection results: fraud_score (float), fraud_details (dict) - returned from Level 3 subgraph
  • HITL state: approval_status, admin_decision (approved/rejected), admin_notes
  • Output to main graph: return_id, ticket_id, fraud_score, final_status, notification_status

Fraud Detection Subgraph State Requirements:

  • Input from returns subgraph: return_id, order_id, user_email, return_reason, return_items

State Design Guidelines:

  • Use TypedDict or Pydantic models for all state schemas
  • Use Annotated[list, operator.add] for any fields that need to accumulate results from parallel nodes
  • Use Literal types for fields with fixed valid options (e.g., agent names, statuses)
  • Keep main state focused on coordination - don't duplicate all subgraph internal fields
  • Subgraph states can be more detailed - they don't pollute the main state
  • Document in docstrings what each state field represents and where it's used

7. Human-in-the-Loop (HITL) Implementation

LangGraph Interrupts

LangGraph provides built-in support for human-in-the-loop workflows through interrupts. When a graph encounters an interrupt, it pauses execution and persists its state to the checkpointer. Later, when a human provides input, the graph resumes from exactly where it paused.

7.1 Return Request Approval Flow

  1. Customer requests return via chatbot
  2. Returns subgraph validates request and runs parallel processing (fraud checks, email, refund calculation)
  3. Graph pauses execution using an interrupt to wait for admin approval
  4. Admin sees ticket in dashboard with:
    • Customer details and conversation ID
    • Return items and reason
    • Fraud risk score
    • Estimated refund amount
  5. Admin makes decision: Approve / Reject / Request More Info
  6. Graph resumes with admin decision (using Command(resume=...))
  7. Final processing: update database, send notification, close ticket
Implementation Note

Use LangGraph's interrupt() function within your returns subgraph nodes to pause execution. The interrupt can return approval details to the caller (for display in admin UI), and when resumed, the admin's decision becomes the return value of interrupt(). Study the interrupts tutorial notebook for implementation patterns.

8. Roles and User Journeys

8.1 Customer Journey with Multi-Agent System

  1. Login: Customer authenticates with email and password
  2. Start Conversation: New UUID conversation_id generated
  3. Complex Query Example: "Can I reorder my last order?"
    • Supervisor routes to OrderAgent
    • OrderAgent triggers parallel fan-out:
      • Fetch last order details (SQL query)
      • Check current inventory for those items (coordinates with InventoryAgent)
      • Calculate new total with current prices (SQL query)
    • Results aggregated: availability status, current pricing, items out of stock
  4. Order Cancellation Example: "I want to cancel order #123"
    • Supervisor routes to OrderAgent
    • OrderAgent validates: order exists, status is PLACED or PROCESSING (not yet SHIPPED)
    • If valid: updates status to CANCELLED, calls notification agent to send cancellation email
    • Customer receives: "Order #123 cancelled successfully. Confirmation email sent."
    • Note: No HITL needed - cancellations are immediate if business rules pass
  5. Return Request Example: "I want to return item X from order #123"
    • Supervisor recognizes return intent, routes to OrderAgent
    • OrderAgent validates order eligibility
    • OrderAgent invokes Returns Subgraph
    • Returns subgraph processes in parallel: fraud check (calling fraud subgraph), email (calling notification agent), refund calculation
    • Graph pauses at HITL interrupt
    • Customer sees: "Your return request has been submitted. A support agent will review it shortly."
  6. Policy Question: "How long does a refund take?"
    • Supervisor routes to PolicyAgent
    • PolicyAgent queries RAG system with ChromaDB
    • Returns policy information

8.2 Admin Journey with Graph Resume

  1. Login: Admin authenticates
  2. View Dashboard: See all pending return tickets with:
    • Customer email
    • Conversation ID (for resuming graph)
    • Order and return details
    • Fraud risk score
    • Estimated refund
  3. Review Ticket: Click on a ticket to see full details
  4. Make Decision: Approve / Reject / Request More Info
  5. Graph Resumes: System uses conversation_id to:
    • Load paused graph state from checkpointer
    • Inject admin decision
    • Resume returns subgraph execution
    • Update database and send notification
  6. Optional: Resume customer conversation to explain decision

amount REAL NOT NULL Payment amount
payment_date TIMESTAMP NOT NULL When payment was processed
status TEXT NOT NULL 'SUCCESS', 'FAILED', 'REFUNDED'

Table 6: returns

Purpose: Return requests (one row per item being returned)

Column Type Description
return_id TEXT PRIMARY KEY Return request ID (e.g., 'RET001')
order_id TEXT NOT NULL Foreign key to orders.order_id
order_item_id INTEGER NOT NULL Foreign key to order_items.order_item_id - specific item being returned
user_email TEXT NOT NULL Customer requesting the return
return_reason TEXT NOT NULL Reason for return (e.g., 'Defective', 'Wrong size', 'Changed mind')
quantity INTEGER NOT NULL Number of units being returned
refund_amount REAL Calculated refund amount (populated by returns subgraph)
fraud_score REAL Fraud risk score 0-100 (populated by fraud detection subgraph)
status TEXT NOT NULL 'PENDING', 'APPROVED', 'REJECTED' (updated after HITL)
created_at TIMESTAMP NOT NULL When return request was created
updated_at TIMESTAMP When status was last updated

Table 7: tickets

Purpose: Support tickets for return requests requiring HITL approval

Column Type Description
ticket_id TEXT PRIMARY KEY Ticket ID (e.g., 'TKT001')
return_id TEXT NOT NULL Foreign key to returns.return_id
user_email TEXT NOT NULL Customer who initiated the return
conversation_id TEXT NOT NULL CRITICAL: UUID from customer conversation - used to resume paused graph from checkpointer
subject TEXT NOT NULL Ticket subject (e.g., "Return Request for Order #ORD123")
description TEXT Additional details about the return request
fraud_score REAL Copy of fraud score from returns table (for quick dashboard display)
status TEXT NOT NULL 'OPEN', 'RESOLVED', 'CLOSED'
workflow_status TEXT NOT NULL 'PAUSED' (waiting for admin), 'RESUMED' (admin decided), 'COMPLETED'
admin_decision TEXT 'APPROVED', 'REJECTED', 'REQUEST_MORE_INFO' (set by admin)
admin_notes TEXT Admin's comments or reasoning for decision
created_at TIMESTAMP NOT NULL When ticket was created
updated_at TIMESTAMP When ticket was last updated
resolved_at TIMESTAMP When admin made a decision

Table 8: email_logs

Purpose: Track all emails sent by the notification agent

Column Type Description
email_log_id INTEGER PRIMARY KEY Auto-increment unique ID
recipient_email TEXT NOT NULL Who received the email (user_email)
email_type TEXT NOT NULL 'ORDER_CONFIRMATION', 'CANCELLATION', 'RETURN_REQUEST', 'RETURN_APPROVED', 'RETURN_REJECTED'
subject TEXT NOT NULL Email subject line
body_preview TEXT First 200 characters of email body (for logging purposes)
related_order_id TEXT Order ID if email is order-related
related_return_id TEXT Return ID if email is return-related
sent_at TIMESTAMP NOT NULL When email was sent
status TEXT NOT NULL 'SENT', 'FAILED' (track email delivery status)
Key Design Decisions
  • user_email as foreign key: We use email (not user_id) as the identifier throughout the system for simplicity and consistency with LangGraph thread IDs
  • tickets.conversation_id: This is the UUID that links the ticket to the paused LangGraph state in the checkpointer - essential for HITL resume
  • returns vs tickets: Returns table stores the actual return data; tickets table stores HITL workflow metadata
  • fraud_score in both: Stored in returns (source of truth) and copied to tickets (for admin dashboard performance)
  • workflow_status: Tracks whether the LangGraph workflow is paused, resumed, or completed

13. Demonstration Scenarios

Your README should include detailed walkthroughs of these scenarios:

13.1 Simple Query (Single Agent)

Customer: "Show me my last 3 orders"
→ Supervisor routes to OrderAgent
→ OrderAgent queries SQL
→ Returns order list
(Demonstrates: Basic routing, single agent)

13.2 Complex Query with Multiple Agents (Parallel Processing)

Customer: "Can I reorder everything from my last order?"
→ Supervisor routes to OrderAgent
→ OrderAgent triggers parallel fan-out:
   • Fetch last order details (SQL query)
   • Check current inventory availability for each item (InventoryAgent)
   • Calculate current total price based on latest pricing (SQL query)
→ Results aggregated
→ Response: "Your last order had 3 items. 2 are in stock (Laptop, Mouse). 
   Keyboard is out of stock. Current total would be $1,099.98 (up from $1,029.98)"
(Demonstrates: Fan-out/fan-in, multiple agents coordinating, parallel execution, real-world use case)

13.3 Return Request (Subgraph + HITL)

Customer: "I want to return items from order #123"
→ Supervisor routes to OrderAgent
→ OrderAgent validates eligibility and invokes ReturnsSubgraph
→ Returns subgraph:
   • Validates return eligibility
   • Creates return and ticket in DB
   • Parallel processing:
     - Send confirmation email (NotificationAgent)
     - Run fraud detection (Send API spawns 4 parallel checks)
     - Calculate refund (OrderAgent)
   • Graph PAUSES at HITL interrupt
→ Customer sees: "Return request submitted. Awaiting review."
→ Admin reviews in dashboard (sees fraud score, refund amount)
→ Admin approves
→ Graph RESUMES from checkpoint
→ Final processing: update status, send final email
→ Customer gets notification
(Demonstrates: Subgraphs, Send API, parallel processing, HITL, graph resume)

13.4 Policy Question (RAG)

Customer: "What's your return policy?"
→ Supervisor routes to PolicyAgent
→ PolicyAgent queries ChromaDB
→ Returns policy information
(Demonstrates: RAG, agent specialization)
