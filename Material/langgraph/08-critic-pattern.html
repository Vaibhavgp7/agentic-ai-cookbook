Evaluator-Optimizer Pattern – Suspicious Transaction Report (STR) Drafting

This lab was prepared for your LangGraph cohort. You will apply the evaluator-optimizer pattern to a compliance workflow that banks actually run: drafting a Suspicious Transaction Report (STR) for FIU-IND.

Open (or create) a Jupyter notebook named 08-str-drafting.ipynb in the 03-langgraph folder. Work cell by cell. A complete notebook with the same steps is also provided so you can execute and test immediately.

Why this lab exists

In production, the evaluator-optimizer loop is used where a weak first draft is dangerous — not merely “not good enough.”

An STR is one of those documents. If the narrative says “layering pattern” but only quotes two transfers, FIU-IND cannot act on it, and your bank’s compliance team will send it back. The evaluator-optimizer pattern is how we keep a generator from shipping an incomplete report.

What you will build

  1. A Generator (AML Analyst) that drafts the STR from a flagged case file
  2. An Evaluator (STR Quality Reviewer) that checks the draft against FIU-IND standards
  3. A feedback loop that sends the draft back until the report is submission-ready

You will see the loop run at least once, often twice. That is intentional. The first draft is written as a hurried first-cut (the way a busy analyst actually starts). The reviewer is strict. You should watch the draft get rejected, then improved.

Terminology you need before you code

Read this once. The rest of the lab assumes these words. AML is not a software framework — it is the bank process this graph is automating.

Who does what
AML — Anti-Money Laundering
The bank’s process for spotting and reporting activity that looks like criminal money being hidden or moved. In India this sits under the Prevention of Money Laundering Act. Horizon Bank does not prove a crime. It detects suspicion and files a report.
AML transaction-monitoring system
Software that watches payments automatically. When a pattern looks wrong (amounts just under ₹10 lakh, money hopping banks in 48 hours, funds returning to a spouse), it raises an alert. In this lab the alert id is AML-2026-0819-4471.
Case file
The fact pack that comes with the alert: customer KYC, account numbers, the five flagged transfers, counterparties, and system-suggested red flags. The monitoring system produces it; an AML operations desk assigns it to an analyst. In a real bank it would come from the AML platform. In the notebook, CASE_FILE is that pack — hardcoded so both agents see the same facts. The case file is input. The STR is output.
AML Analyst (your generator)
The person (here, an agent) who reads the case file and drafts the STR. They do not file with the government. They write the narrative.
STR Quality Reviewer (your evaluator)
Internal compliance. They check the draft before anyone sends it out. If the draft is thin, they send it back to the analyst — not to FIU-IND.
Reporting entity
The institution that must file if suspicion stands. Here that is Horizon Bank.
The report and the regulator
STR — Suspicious Transaction Report
The formal narrative the bank files when activity looks suspicious. It is not a police charge sheet and it is not a conviction. FIU-IND cannot act on “we think this is layering.” They need dates, amounts, account numbers, and the full chain.
FIU-IND — Financial Intelligence Unit – India
The government body that receives STRs from banks and other reporting entities. They analyse, then may share with enforcement. Horizon Bank files the STR with FIU-IND only after internal review is satisfied.

The path from a customer payment to a filing looks like this:

Customer payments ↓ AML monitoring system → raises alert → builds case file ↓ AML Analyst (generator) → drafts STR from the case file ↓ STR Quality Reviewer (evaluator) → approve or send back ↓ Horizon Bank files STR → FIU-IND
Words inside the case file
Flagged transaction
A payment the monitoring system marked. This case has exactly five (TXN-001 through TXN-005). If the STR mentions only two, the case is incomplete.
Red flag
A named suspicion pattern, not a feeling. This lab uses three you must see in the final draft:
Structuring
Splitting money into amounts just below a reporting threshold — here, several payments around ₹9.7–9.8 lakh.
Layering
Moving the same value through several accounts or banks so the origin is hard to see. A layering claim needs the full 5-leg chain, not two outbound payments.
Rapid movement
Hops in a very short window — here, about 48 hours across four institutions.
Round-tripping
Money leaves and comes back to a related party. Here: Vikram Rao → … → Priya Rao (his spouse).
Beneficiary
Who received the money. For TXN-004 that is Ananya Sethi, account 2200198845, bank, and PAN. First drafts often skip this. The reviewer is told to catch it.
KYC — Know Your Customer
Who the bank believes Vikram Rao is: business, turnover, related parties. The case file uses it to show that Ananya Sethi is not a declared related party, which makes the hop more suspicious.
Grounds of suspicion
The FIU-IND-style section: facts plus why they look suspicious, without writing “he is a criminal.”
Recommended action
What the bank proposes next: file the STR, extra monitoring, a freeze recommendation, and so on. The analyst drafts this. In real life a human still decides.
How this maps to the two agents

The case file is input. The STR is output. The loop exists because a first-cut STR that says “layering” after citing only two transfers is not something the bank should send to FIU-IND.

The business scenario

Horizon Bank — AML Alert AML-2026-0819-4471

Horizon Bank’s AML transaction-monitoring system has flagged a chain of 5 transfers linked to Mr. Vikram Rao, proprietor of Rao Agro Exports, Bengaluru. Your generator must draft the STR. Your evaluator must refuse it until the narrative can survive a FIU-IND review.

Evaluator must fail the draft if any of these are true:

  • Not all 5 flagged transactions are accounted for in the narrative
  • The report does not cite specific red flags: structuring, round-tripping, rapid movement / layering
  • The language is too vague for FIU-IND (opinions without facts, slang, missing amounts/dates/accounts)
  • Any conclusion is unsupported by the transaction data — especially claiming a “layering pattern” without the full 5-leg chain

Typical loop triggers you should expect to see:

  • “Report mentions ‘layering pattern’ but only cites 2 transactions — need at least the full chain of 5 flagged transfers to substantiate.”
  • “Missing the beneficiary details for transaction #4.”

The state carries the case, the current STR draft, the reviewer’s verdict, and the iteration counter. We also keep max_iterations so a stubborn disagreement cannot loop forever.

class State(TypedDict):
    """Shared state for the STR evaluator-optimizer loop."""
    case_file: str
    str_draft: str
    evaluation_result: str   # "approved" | "needs_improvement"
    feedback: str
    iteration_count: int
    max_iterations: int
    missing_items: str       # concrete gaps the reviewer found

print("✅ State schema defined.")

Step 4: Define the structured evaluation schema

The reviewer must not return a paragraph we have to parse with string matching. Structured output gives the router a reliable grade and gives the generator a checklist it can actually fix.

class STREvaluation(BaseModel):
    """FIU-IND quality review of an STR draft."""

    grade: Literal["approved", "needs_improvement"] = Field(
        description=(
            "approved = submission-ready for FIU-IND. "
            "needs_improvement = return to the analyst with specific fixes."
        )
    )
    all_five_transactions_cited: bool = Field(
        description="True only if TXN-001, TXN-002, TXN-003, TXN-004 and TXN-005 all appear in the narrative."
    )
    red_flags_named: bool = Field(
        description="True only if structuring, round-tripping, and rapid movement/layering are explicitly named."
    )
    language_fiu_ready: bool = Field(
        description="True only if language is precise, factual, and suitable for FIU-IND (dates, amounts, account numbers)."
    )
    conclusions_supported: bool = Field(
        description="True only if every conclusion (especially 'layering') is backed by the cited transfers."
    )
    txn4_beneficiary_complete: bool = Field(
        description="True only if TXN-004 names Ananya Sethi with account number and bank/PAN or equivalent identifiers."
    )
    missing_items: str = Field(
        description=(
            "Bullet list of concrete gaps. Use FIU-IND reviewer voice. Examples: "
            "Report mentions 'layering pattern' but only cites 2 transactions — need at least "
            "the full chain of 5 flagged transfers to substantiate. "
            "Missing the beneficiary details for transaction #4."
        )
    )
    feedback: str = Field(
        description="Actionable revision instructions for the AML analyst. Be specific: which TXN, which field, which sentence to change."
    )
    strengths: str = Field(
        description="What the draft already does well — keep these."
    )


evaluator_llm = reviewer_llm.with_structured_output(STREvaluation)
print("✅ STR evaluation schema and structured reviewer ready.")

GENERATOR_SYSTEM_PROMPT = """You are a Senior AML Analyst at Horizon Bank Ltd., Bengaluru.

Your sole job is to draft Suspicious Transaction Reports (STRs) for submission to
FIU-IND (Financial Intelligence Unit - India) under the Prevention of Money Laundering Act.

RULES YOU MUST FOLLOW
1. Use only facts from the case file. Never invent counterparties, amounts, dates, or PANs.
2. Write in formal compliance English. No slang, no speculation presented as fact.
3. Preferred phrasing: "grounds of suspicion", "red flags observed", "transaction chain",
   "recommended action". Avoid "obviously money laundering" or "the customer is a criminal".
4. When you describe a pattern (structuring, layering, round-tripping, rapid movement),
   you MUST cite every transfer that forms that pattern. A layering claim needs the full chain.
5. For every flagged transfer, include: TXN ID, date/time, amount, from account, to account,
   mode, and narration. For TXN-004 you MUST include beneficiary name, account number, bank,
   and PAN if present in the case file.
6. End with: (a) red flags cited, (b) grounds of suspicion, (c) recommended action
   (file STR with FIU-IND, consider account monitoring / freeze recommendation as appropriate).

FIRST-CUT BEHAVIOUR (iteration 1 only)
Write a hurried first-cut STR of about 2–3 short paragraphs.
Focus on the two most obvious outbound payments from Vikram Rao (TXN-001 and TXN-002).
You may use the word "layering" at a high level.
Do NOT yet enumerate TXN-003, TXN-004 beneficiary identifiers, or TXN-005.
Compliance review will send this back — that is expected. Produce a first cut, not a final filing.

REVISION BEHAVIOUR (iteration 2+)
The quality reviewer has rejected your draft. Fix EVERY item in the feedback.
Expand the narrative so that all five flagged transfers appear, with identifiers.
If the reviewer said the layering claim is unsupported, either cite the full 5-leg chain
or withdraw the word "layering". Do not argue. Revise.
"""

EVALUATOR_SYSTEM_PROMPT = """You are the STR Quality Reviewer in Horizon Bank's AML Compliance unit.

You review STR drafts BEFORE they are submitted to FIU-IND. You are stricter than a helpful
colleague. A flattering review that lets a thin report through is a compliance failure.

YOU MUST GRADE "needs_improvement" IF ANY OF THE FOLLOWING IS TRUE
A. Not all five flagged transactions (TXN-001 through TXN-005) are accounted for in the narrative.
B. The draft claims "layering" / "layering pattern" but cites fewer than the full chain of 5 transfers.
   In that case your missing_items MUST include a sentence in this spirit:
   "Report mentions 'layering pattern' but only cites 2 transactions — need at least the full chain of 5 flagged transfers to substantiate."
   (Adjust the number if they cited 1, 3, or 4 — but the message stays the same: full chain of 5 required.)
C. TXN-004 is mentioned without beneficiary details (name Ananya Sethi, account 2200198845, bank/PAN).
   In that case missing_items MUST include:
   "Missing the beneficiary details for transaction #4."
D. Red flags are missing. The draft must explicitly name:
   - structuring
   - round-tripping
   - rapid movement (or layering, if the full chain is cited)
E. Language is not FIU-IND ready: vague adjectives, missing amounts/dates/account numbers,
   or conclusions such as "customer is guilty" that the transaction data cannot support.
F. Any conclusion is unsupported by the cited data.

GRADE "approved" ONLY WHEN ALL OF A–F ARE SATISFIED.

FIRST-PASS POLICY
On the analyst's first draft (iteration 1), you almost certainly must reject.
First drafts in this workflow are hurried. Find the real gaps. Do not rubber-stamp.

TONE
Write missing_items and feedback as a compliance reviewer, not as a teacher.
Short, specific, operational. Name the TXN IDs.
"""

print("✅ System prompts loaded for AML Analyst (generator) and STR Quality Reviewer (evaluator).")
Why the first-cut instruction exists

If both agents try to be “perfect” on pass one, you will not see the loop — and you will not learn the pattern. Banks also work this way: the analyst dumps a first narrative, compliance marks it up, the analyst files the complete version. We encoded that operating rhythm in the prompts.

Step 6: Create the STR generator node

The node reads iteration_count. On the first visit it asks for a first-cut. On later visits it pastes the rejected draft plus the reviewer’s feedback and asks for a revision.

def str_generator(state: State) -> dict:
    """Draft or revise the Suspicious Transaction Report."""
    iteration = state.get("iteration_count", 0)
    case_file = state["case_file"]
    feedback = state.get("feedback", "")
    previous_draft = state.get("str_draft", "")

    if iteration == 0:
        human = f"""Prepare the FIRST-CUT STR for the following alert.

{case_file}

Remember: this is iteration 1 — a hurried first-cut is required, not a complete filing.
"""
        print("✍️  AML Analyst: writing first-cut STR (expected to be incomplete)...")
    else:
        human = f"""REVISE the STR. The quality reviewer rejected the previous draft.

CASE FILE (facts — do not invent beyond this):
{case_file}

PREVIOUS DRAFT:
{previous_draft}

REVIEWER FEEDBACK (fix every item):
{feedback}

Produce a complete, FIU-IND-ready STR. All 5 flagged transfers must appear.
TXN-004 beneficiary details must be complete. Do not claim layering without the full chain.
"""
        print(f"✍️  AML Analyst: revising STR (iteration {iteration + 1}) from reviewer feedback...")

    response = generator_llm.invoke(
        [SystemMessage(content=GENERATOR_SYSTEM_PROMPT), HumanMessage(content=human)]
    )

    return {
        "str_draft": response.content,
        "iteration_count": iteration + 1,
    }

print("✅ STR generator node created.")

The reviewer receives the case file and the draft so it can check facts rather than style. If a first pass somehow comes back approved, we still force one revision with the two canonical loop triggers. That guarantees you will see the cycle in class even if the model writes a surprisingly complete first draft.

def str_evaluator(state: State) -> dict:
    """Review the STR draft against FIU-IND completeness and supportability rules."""
    iteration = state.get("iteration_count", 0)
    draft = state["str_draft"]
    case_file = state["case_file"]

    human = f"""Review this STR draft. Iteration number: {iteration}

CASE FILE (source of truth):
{case_file}

STR DRAFT UNDER REVIEW:
{draft}

Apply the grading rules from your system prompt. Return structured output only.
"""

    print(f"🔍 STR Quality Reviewer: reviewing draft from iteration {iteration}...")
    evaluation = evaluator_llm.invoke(
        [SystemMessage(content=EVALUATOR_SYSTEM_PROMPT), HumanMessage(content=human)]
    )

    grade = evaluation.grade
    missing = evaluation.missing_items

    # Pedagogical safety net: first review cannot close the file.
    if iteration == 1 and grade == "approved":
        grade = "needs_improvement"
        missing = (
            "Report mentions 'layering pattern' but only cites 2 transactions — "
            "need at least the full chain of 5 flagged transfers to substantiate.\n"
            "Missing the beneficiary details for transaction #4."
        )
        print("   ↳ First-pass policy: sending the draft back for a full-chain revision.")

    comprehensive_feedback = f"""EVALUATION SUMMARY
Grade: {grade.upper()}
Iteration reviewed: {iteration}

CHECKLIST
- All 5 transactions cited : {evaluation.all_five_transactions_cited}
- Red flags named          : {evaluation.red_flags_named}
- FIU-IND language         : {evaluation.language_fiu_ready}
- Conclusions supported    : {evaluation.conclusions_supported}
- TXN-004 beneficiary OK   : {evaluation.txn4_beneficiary_complete}

STRENGTHS
{evaluation.strengths}

MISSING / GAPS
{missing}

REVISION INSTRUCTIONS
{evaluation.feedback}
"""

    print(f"   Grade: {grade.upper()}")
    print(f"   Gaps : {missing[:180]}{'...' if len(missing) > 180 else ''}")

    return {
        "evaluation_result": grade,
        "feedback": comprehensive_feedback,
        "missing_items": missing,
    }

print("✅ STR evaluator node created.")

Step 8: Create the routing function

Routing is what turns two nodes into a loop. Two extra rules keep that loop useful in class:

  • Minimum one revision — if we have only generated once, go back to the analyst
  • Maximum iterations — stop after 4 generate-review cycles so the graph cannot run away

Create a new cell and run the router.

def route_str(state: State) -> Literal["approved", "needs_revision"]:
    """Decide whether the STR can be filed or must go back to the analyst."""
    result = state["evaluation_result"]
    iteration = state.get("iteration_count", 0)
    max_iterations = state.get("max_iterations", 4)

    if iteration >= max_iterations:
        print(f"⚠️  Max iterations ({max_iterations}) reached. Filing the current draft as-is.")
        return "approved"

    # Guarantee at least one generate → review → generate cycle
    if iteration < 2:
        print(f"🔄 Minimum review cycle not yet complete (iteration {iteration}). Returning to analyst.")
        return "needs_revision"

    if result == "approved":
        print(f"✅ STR approved for FIU-IND filing after {iteration} iteration(s).")
        return "approved"

    print(f"🔄 STR needs revision (iteration {iteration}). Returning to AML Analyst.")
    return "needs_revision"

print("✅ Routing function created.")
Expected path in class
  1. Generator writes a thin first-cut (mostly TXN-001 and TXN-002, maybe a loose “layering” claim)
  2. Evaluator rejects — full chain missing, TXN-004 beneficiary missing
  3. Generator revises with all 5 legs and Ananya Sethi’s identifiers
  4. Evaluator either approves, or asks for one more language/support pass, then approves

You should see one or two loops, not zero and not ten.

workflow = StateGraph(State)

workflow.add_node("str_generator", str_generator)
workflow.add_node("str_evaluator", str_evaluator)

workflow.add_edge(START, "str_generator")
workflow.add_edge("str_generator", "str_evaluator")
workflow.add_conditional_edges(
    "str_evaluator",
    route_str,
    {
        "approved": END,
        "needs_revision": "str_generator",
    },
)

str_workflow = workflow.compile()

print("✅ STR evaluator-optimizer graph compiled.")
print("START → str_generator → str_evaluator → [approved: END | needs_revision: str_generator]")
